# コンピュート分離 (ECS / Lambda / Fargate) Q&A

記録日: 2026-08-07

## Q1: ECSやLambdaは物理的に他テナントと同じマシン上で動いているはずだが、どうやって完全にisolatedに見せているのか？

答えは「1つの技術ではなく、**独立した3つの層**を重ねている」。
そして Docker で気になる「ホストが透けて見える」問題は、AWS では**そもそもコンテナ技術で分離していない**ことで解決している。

### 全体像

```
┌─────────────────────────────────────────────┐
│ 物理サーバ (bare metal)                      │
│  └ Nitro Hypervisor + Nitro Card (専用ハード) │ ← 層1: ハード支援の仮想化
│     ├ microVM (ゲストカーネル込み) ← 顧客A     │ ← 層2: Firecracker
│     │   └ コンテナ / 関数プロセス              │ ← 層3: namespace/cgroup/seccomp
│     └ microVM ← 顧客B
└─────────────────────────────────────────────┘
```

重要なのは **層2 で切っている**点。Docker の分離が弱く感じるのはカーネルをホストと共有しているから
（`/proc`、`/sys`、`uname`、dmesg、カーネル脆弱性が全部共有面）。
Lambda / Fargate はここに**ゲストカーネルごと別の VM** を置くので、「ホストの何か」が見える経路がそもそも存在しない。
中で見えている `/proc/cpuinfo` や `uname -r` は、その microVM 専用の Linux カーネルのもの。

### 層1: Nitro System（EC2 の土台）

昔の EC2 は Xen ハイパーバイザ（＝ソフトウェア）が I/O もネットワークもエミュレートしていた。Nitro では役割を分けている。

- **Nitro Card** — ネットワーク、EBS、インスタンスストレージ、監視を専用ハードにオフロード。CPU からは PCIe デバイスとして見え、SR-IOV で VM に直接パススルーされる
- **Nitro Security Chip** — マザーボードの全 I/O 経路を仲介。ファームウェアの書き込みを物理的にブロック（永続化バックドアの遮断）
- **Nitro Hypervisor** — KVM ベースの極小ハイパーバイザ。I/O を持たないのでメモリ管理と CPU スケジューリングだけ

ポイントは **AWS のオペレータ自身もホスト OS に対話的にログインできない**設計になっていること
（そもそも汎用 OS もシェルも載っていない）。管理は API 経由のみで、人が踏み台にできる経路を消している。

### 層2: Firecracker microVM（Lambda / Fargate の本体）

Rust 製の極小 VMM（Virtual Machine Monitor）。QEMU の代替。

- デバイスは **virtio-net / virtio-block / vsock / シリアル / 1ボタンキーボード（リセット用）だけ**。BIOS も PCI も USB も VGA もない → 攻撃面が桁違いに小さい
- 起動 **約 125ms**、オーバーヘッド **数 MB/VM**。だから「1リクエスト単位の実行環境」に VM を割り当てても採算が合う
- **jailer** という別プロセスが、Firecracker 自身を chroot + namespace + cgroup + seccomp で囲む。**VMM を突破されても、まだコンテナの中**という二重底

Lambda では **microVM 1つ ＝ 実行環境（execution environment）1つ**。
これは「1アカウントの1関数バージョン」専用。同時実行 100 なら microVM が 100 個。
使い回されるのは同じ関数の連続リクエスト間だけなので、他人のコードとメモリ空間を共有することはない
（`/tmp` が温まっているのはこの再利用のため）。

Fargate も同じで、**タスク1つ＝microVM 1つ**。同じ物理ホスト上に別アカウントの microVM が同居するが、境界はハイパーバイザ。

### 層3: ネットワーク（「独立して設定できる」理由の本体）

VPC は物理ネットワークを切り分けているのではなく、**オーバーレイ**。

1. インスタンス/タスクが出したパケットは、**Nitro Card 上で**カプセル化され、VPC の識別子が付く
2. **Mapping Service** が「この VPC のこの IP は、どの物理ホストのどのスロットか」を解決し、物理ネットワークでトンネリング
3. 受け側の Nitro Card がデカプセル化して届ける

このカプセル化と送信元 IP の詐称チェック（アンチスプーフィング）を**ハードウェアが強制**するので、ゲスト側からは抜けられない。
だから 10.0.0.0/16 を全顧客が同時に使っても衝突しないし、セキュリティグループ（ステートフルなフィルタ）も Nitro Card 側で評価される。

- **ECS の awsvpc モード** — タスクに **ENI が1本まるごと**割り当たる。だからタスクが独自のプライベート IP とセキュリティグループを持てる（bridge モードだと EC2 のホスト側 ENI を共有し、ポートマッピングになる）
- **Lambda の VPC 接続** — 2019年以降 **Hyperplane** を使い、「ENI ↔ 関数」ではなく **VPC-to-VPC NAT** を挟んで ENI を全同時実行で共有。昔あった「スケール時に ENI 作成待ちで数十秒のコールドスタート」はこれで解消された

### ストレージ

- EBS は**ネットワーク越しのブロックデバイス**。暗号化・鍵管理も Nitro Card 側。ゲストは平文しか見ないが、物理ディスクには顧客ごとの鍵で暗号化されて置かれる
- Lambda の `/tmp` は microVM 専用のブロックデバイス。実行環境が破棄されれば消える

### 実務上の注意: ECS on EC2 は話が別

同じ EC2 インスタンスに載った複数タスクは、**普通の Docker と同じくカーネルを共有**する（分離は namespace/cgroup レベル）。
他アカウントからは Nitro で守られているが、自分のアカウント内のタスク同士は隣接している。

| | 他テナントとの境界 | 自アカウントのタスク間 |
|---|---|---|
| ECS on EC2 | Nitro Hypervisor | **namespace/cgroup のみ** |
| Fargate | Firecracker microVM | Firecracker microVM |
| Lambda | Firecracker microVM | Firecracker microVM |

（Lambda / Fargate の Worker はベアメタル EC2 なので、経路に Nitro Hypervisor はいない。詳細は Q3）

→ 「マルチテナントの信頼できないコードを動かす」「ワークロード間の強い分離が要件」なら Fargate。
コスト最適化や常駐デーモンが要るなら ECS on EC2、という選び分けになる。

### まとめ

**Docker の弱点（カーネル共有・ホストの可視性）を、より下の層の VM で丸ごと打ち消し、
その VM を成立させるために Firecracker で軽量化した**というのが AWS の答え。
ネットワークの独立性はコンテナ技術ではなく、Nitro Card 上のオーバーレイが担っている。

## Q2: 全体像を普通のPC、Docker / containerd と比較すると？

「どこで切っているか」を層で並べると違いがはっきりする。

### 1. 普通のPC（Linux 直）

```
[プロセスA] [プロセスB]        ← 分離境界はここ
─────────────────────
     Linux カーネル (1個)
─────────────────────
     物理ハードウェア
```

分離しているのは **MMU による仮想メモリ空間と UID** だけ。
プロセスAはプロセスBのメモリを読めないが、カーネルは完全に共有。root を取られたら全部見える。

### 2. Docker / containerd

```
[コンテナA] [コンテナB]
     ↓ syscall (フックなし、直接カーネルへ)
 namespace / cgroup / seccomp / capabilities   ← 「見え方」のフィルタでしかない
─────────────────────
     Linux カーネル (ホストと共有・1個)
─────────────────────
     物理ハードウェア
```

要点は **「コンテナ」という実体は存在しない**こと。
あるのは「普通のプロセスに、カーネルの機能でフィルタを掛けたもの」。

- **namespace**（PID, NET, MNT, UTS, IPC, USER, cgroup）— カーネル内部の識別子テーブルを分割し「見える範囲」を狭める
- **cgroup** — CPU/メモリの使用量を制限する（*隠す*のではなく*制限する*）
- **seccomp / capabilities** — 呼べる syscall を減らす

ランタイム階層は Docker CLI → dockerd → **containerd**（イメージ管理・ライフサイクル）→ **runc**（`clone(2)` で namespace を作りプロセス起動）。
containerd 単体で使っても最下層は同じ runc なので**分離の強さは変わらない**。

#### ホストが透ける理由

| 見えてしまうもの | 理由 |
|---|---|
| `uname -r` がホストのカーネル版数 | カーネルは1個しかない |
| `/proc/cpuinfo` がホストの全コア | cgroup で制限しても表示は隠れない（`nproc` が嘘をつく） |
| `free -m` がホストの全メモリ | 同上（`lxcfs` 等で騙す必要がある） |
| `/sys` の一部、dmesg | namespace 化されていない領域が残っている |

最大の問題は **syscall インターフェースがそのまま攻撃面**であること。
Linux の syscall は 350 種以上あり、どれかにバグがあれば（Dirty COW、Dirty Pipe 等）**コンテナからホストの root を取れる**。
カーネルのバグ＝脱獄経路、という構造。

#### ネットワークがホストに依存する理由

```
[コンテナ] ── veth ── docker0 (Linux bridge) ── iptables ── ホストの物理NIC
             (netns境界)      172.17.0.1        MASQUERADE/DNAT
```

network namespace で NIC は分かれているが、その先は **ホストの bridge・iptables・ルーティングテーブル**を必ず経由する。

- IP は Docker が決めた `172.17.0.0/16` で、外部から到達可能なアドレスではない
- 外に出すには `-p 8080:80` で **ホストのポートを消費** → ホスト内でポート衝突する
- ホスト側の iptables ルールや MTU、ルーティングの影響を受ける

### 3. 従来の VM（VirtualBox / VMware / KVM+QEMU）

```
[ゲストアプリ]
─────────────────────
   ゲストカーネル (別物！)        ← 決定的な違い
─────────────────────
   仮想ハードウェア (QEMU がエミュレート)
   BIOS, PCI, USB, VGA, IDE, サウンド... ← 巨大
─────────────────────
   ハイパーバイザ (KVM = CPUのVT-x/EPTを使う)
   ホストカーネル
   物理ハードウェア
```

分離境界が **CPU のハードウェア機構（VT-x / EPT）** に上がる。
ゲストが syscall を投げる先は自分のゲストカーネルなので、ホストのカーネルバグは無関係。

代償は起動数十秒・メモリ数百MB、そして **QEMU のデバイスエミュレーションコードが新たな攻撃面**になること
（VENOM: フロッピーコントローラのバグで VM 脱獄）。

### 4. Firecracker（Lambda / Fargate）

VM の構造そのままで、**QEMU の部分だけを極小に置き換えた**もの。

```
[関数コード / コンテナ]
─────────────────────
   ゲストカーネル (専用・最小構成)
─────────────────────
   virtio-net / virtio-block / vsock / シリアル のみ ← BIOSもPCIもUSBもVGAもない
─────────────────────
   Firecracker VMM (Rust, 約5万行) ← QEMUの1/100規模
     └ jailer が chroot + namespace + cgroup + seccomp で包む ← 二重底
─────────────────────
   KVM / Nitro Hypervisor
   Nitro Card (ネットワーク・EBSを専用ハードにオフロード)
   物理ハードウェア
```

VM の強い境界を保ったまま **起動 125ms・オーバーヘッド数MB** に落としたので、コンテナと同じ粒度で使える。これが発明。

### 横並び比較

| | 普通のPC | Docker/containerd | 従来VM | Firecracker |
|---|---|---|---|---|
| **分離境界** | MMU + UID | カーネル内 namespace | CPU (VT-x/EPT) | CPU (VT-x/EPT) |
| **カーネル** | 1個 | ホストと共有（1個） | ゲスト専用 | ゲスト専用 |
| **起動時間** | ms | 〜100ms | 数十秒 | **〜125ms** |
| **メモリ増分** | — | ほぼ0 | 数百MB | **数MB** |
| **`uname -r`** | ホスト | **ホストが見える** | ゲスト固有 | ゲスト固有 |
| **脱獄に必要なもの** | root取得 | **カーネルの1バグ** | ハイパーバイザ突破 | VMM突破 + jailer突破 |
| **攻撃面** | — | syscall 350+ | QEMU 全デバイス | virtio 4種 + seccomp |
| **NIC** | 物理 | veth→ホストbridge | 仮想NIC→ホストbridge | virtio-net→**Nitro Card** |
| **IPアドレス** | 物理LANのIP | Dockerが払い出す私設IP | 多くはNAT | **VPCの本物のIP** |
| **ポート公開** | そのまま | ホストポートを消費 | ポートフォワード | **不要（自前のIPを持つ）** |

### 「独立して設定できる」の正体

- **Docker** — コンテナはホストのネットワークスタックに *相乗り* している。だから設定はホストの bridge / iptables に従属する
- **Fargate (awsvpc)** — タスクが **ENI（仮想NIC）を1本まるごと**持つ。VPC の本物の IP と独自のセキュリティグループを持ち、ホストのポート空間とは無関係

さらに ENI の先の「スイッチ」自体がソフトウェア定義（Nitro Card 上のオーバーレイ + Mapping Service）なので、
**全顧客が `10.0.0.0/16` を同時に使っても衝突しない**。
Docker が「ホストの上に橋を架けている」のに対し、AWS は「ネットワーク機器そのものを仮想化している」。

### 中間解（実務で出てくる）

| | 方式 | 位置づけ |
|---|---|---|
| **gVisor** | Go 製のユーザ空間カーネルが syscall を代理受信 | ホストカーネルへの syscall を ~50 種に絞る。GKE Sandbox。互換性に穴あり |
| **Kata Containers** | コンテナ1つごとに軽量VM（QEMU or Firecracker） | OCI 互換のまま VM 分離。Fargate の思想を自前で |

## Q3: 分離のキモになるのはどこ？Nitro Hypervisor？Firecracker？

どちらか一方ではなく、**サービスによって担当が入れ替わる**。そして両方の下に、本当のキモがもう一段ある。

### 結論

| | テナント境界を張っているもの |
|---|---|
| EC2 / ECS on EC2 | **Nitro Hypervisor** |
| Lambda / Fargate | **Firecracker + KVM** |
| ネットワーク・ストレージの分離 | **Nitro Card**（ハイパーバイザではない） |
| AWSオペレータからの分離 | Nitro Security Chip + ホストにシェルが無い設計 |
| ↑ 全部の土台 | **CPU のハードウェア機構（VT-x/EPT, IOMMU）** |

### Lambda では Nitro Hypervisor は経路にいない

Firecracker の論文（NSDI '20）によれば、**Lambda の Worker は EC2 のベアメタルインスタンス**（i3.metal 等）。
ベアメタル＝ハイパーバイザ無しなので、こうなる。

```
物理サーバ (bare metal)
 ├─ Nitro Card ────────── ネットワーク・EBS・ルートオブトラスト
 └─ ホストLinux + KVM
     ├─ Firecracker → microVM (顧客A)   ← ★テナント境界はここ
     ├─ Firecracker → microVM (顧客B)
     └─ Firecracker → microVM (顧客A の別関数)
```

なぜベアメタルかというと、**普通の EC2 上だと KVM を動かすのに nested virtualization が要る**から。
ベアメタルなら Firecracker が第一級のハイパーバイザとして CPU の仮想化支援を直接使える。

一方 ECS on EC2 はこう。

```
物理サーバ
 ├─ Nitro Card
 └─ Nitro Hypervisor
     ├─ EC2インスタンス (顧客A)  ← ★テナント境界はここ
     │   └─ runc コンテナ × N  ← ここはただの namespace
     └─ EC2インスタンス (顧客B)
```

つまり **Nitro Hypervisor と Firecracker は競合関係ではなく、同じ役割（VMM）を別の場所で担当している**。

### 本当のキモ: 分離を*強制*しているのは CPU

Firecracker も Nitro Hypervisor も、実は**分離を実行していない**。
やっているのは「CPU のハードウェア機構を正しく設定すること」。

- **EPT / NPT（拡張ページテーブル）** — ゲスト物理アドレス → ホスト物理アドレスの変換表。ゲストは**自分に割り当てられていないメモリをアドレスとして表現する手段がない**。これが分離の根本
- **VMX root / non-root モード** — ゲストが特権命令を叩くと自動的にハイパーバイザにトラップする
- **IOMMU（VT-d）** — DMA の分離。デバイスが勝手に他 VM のメモリを読み書きするのを防ぐ。SR-IOV で NIC を直接パススルーできるのはこれのおかげ

Docker との差が決定的なのはここ。
namespace は**カーネルがコードで「見せない」と判断している**だけなので、判断ロジックにバグがあれば破れる。
EPT は**そもそもアドレスが存在しない**ので、バグの入る余地がソフトウェア側にない。

### では VMM の役割は何か → 「自分自身が抜け穴にならないこと」

VMM はホスト上のプロセス（Firecracker はただのユーザ空間プロセス）。
ゲストからの virtio リクエストを処理するのは VMM のコードなので、**そこにバグがあればゲスト → ホストの脱獄が成立**する。VENOM がまさにこれ。

だから両者とも、**取った戦略は同じ「持ち物を捨てる」**。

| | やったこと | 結果 |
|---|---|---|
| **Firecracker** | デバイスを virtio 4種だけに絞り、BIOS/PCI/USB/VGA を全部捨てた | QEMU 140万行 → **5万行** |
| **Nitro Hypervisor** | I/O 処理を Nitro Card（専用ハード）に追い出した | メモリ管理と CPU スケジューリングだけの極小コードに |

**「攻撃面はコードの量に比例する。だからコードを消す」**という同じ思想の、別の実装。

さらに Firecracker には二重底がある。**jailer** が Firecracker プロセス自体を chroot + namespace + cgroup + seccomp で包むので、
VMM を突破しても攻撃者はまだコンテナの中。「VM の中のコンテナ」ではなく「**コンテナの中の VM**」という入れ子。

### まとめ

- **強制しているのはハードウェア（CPU）** — 共通で、置き換え不能なキモ
- **Nitro Hypervisor と Firecracker は同じ役割の別実装** — EC2 なら前者、Lambda/Fargate なら後者
- **両者の設計思想も同じ** — 「VMM 自身が穴になる」ので、機能を削って攻撃面を消す
- **Nitro Card は別軸** — CPU 分離とは独立に、ネットワークとストレージの分離を担当。VPC が独立して見えるのはこっちの功績

「1個のキモ」を選ぶなら **CPU の EPT**、「AWS が作ったものの中で」なら **Nitro Card**
（ハイパーバイザではなく I/O を丸ごとハードに追い出した点が他社と一番違う）。

## Q4: CPUが分離しているとはどういうこと？コア数は柔軟に対応できる？

**CPU は「分割」されていない。** 同じコアが顧客Aと顧客Bのコードを**時分割で交互に実行**している。
分離されているのは実行資源ではなく、**実行の瞬間ごとの「状態」**。

### 物理コアの10ミリ秒

```
物理コア #7
├─ 0.0ms  顧客A の microVM の vCPU0 を実行
│          EPTポインタ = Aのテーブル / レジスタ = Aの値
├─ 2.3ms  ★VM exit → ホストのスケジューラに制御が戻る
│          VMCS を丸ごと差し替え（レジスタ、EPTポインタ、割り込み状態）
├─ 2.4ms  顧客B の microVM の vCPU1 を実行   ← 同じ物理コア、別人格
│          EPTポインタ = Bのテーブル / レジスタ = Bの値
├─ 5.1ms  ★VM exit
└─ 5.2ms  顧客A の別の microVM を実行 ...
```

CPU は **VMCS（Virtual Machine Control Structure）** という「この VM の全状態」を記録した構造体を持ち、
切り替えのたびにこれをロードする。ロードした瞬間、そのコアは**別の顧客のマシンそのもの**になる。

> **同じコアが、マイクロ秒単位で人格を切り替えている**

顧客Aのコードが動いている間、そのコアから顧客Bのメモリは**アドレスとして表現不能**（EPT にエントリがない）。

### vCPU とは何か

**vCPU = 物理コアの割り当てではなく、スケジューリング単位。**
Firecracker では **vCPU 1つ ＝ ホスト Linux の 1スレッド**。

```
64コアの物理ホスト
 └─ ホストLinux のスケジューラ (CFS)
     ├─ Firecracker プロセス#1 ── vCPUスレッド × 2  (顧客A)
     ├─ Firecracker プロセス#2 ── vCPUスレッド × 2  (顧客B)
     ├─ ... × 128個
     └─ 合計 256 スレッドを 64 コアで回す
```

**ホスト OS から見れば、ただのマルチスレッドプログラムの集まり**。
だから 128 個の microVM を 64 コアのホストに載せるのは特別なことではない（関数は大半の時間 I/O 待ちでアイドル）。

### サービスごとの割り当てポリシー

| | オーバーサブスクライブ | vCPU の指定 |
|---|---|---|
| **EC2 (m5, c5 等)** | **しない**（vCPU は専有） | インスタンスタイプで決まる |
| **EC2 T系（バースタブル）** | **する**（CPUクレジット方式） | ベースライン % で制御 |
| **Fargate** | する | タスク定義で 0.25〜16 vCPU を指定 |
| **Lambda** | する | **指定できない**（後述） |

AWS の定義では **1 vCPU = 1 ハードウェアスレッド**（HT の片側）。`m5.xlarge` の 4 vCPU は **2 物理コア × 2 HT**。

### Lambda の CPU は「メモリで買う」

**Lambda は vCPU を直接指定できず、メモリ量に比例して CPU が割り当てられる。**

| メモリ設定 | 割り当てられる CPU |
|---|---|
| 128 MB | 約 0.07 vCPU |
| 1,024 MB | 約 0.58 vCPU |
| **1,769 MB** | **ちょうど 1 vCPU** |
| 3,538 MB | 2 vCPU |
| 10,240 MB（上限） | 約 6 vCPU |

**1,769 MB 未満では 1 コアすら使い切れない。**
CPU バウンドな処理（画像変換、圧縮、暗号処理）でメモリを増やすと劇的に速くなるのはこれが理由。
しかも実行時間が短くなる分、**総額が下がることすらある**（課金は GB-秒なので、2倍のメモリで3倍速くなれば安い）。

注意: **microVM に見える CPU 数と、実際に使える CPU 時間は別物**。
Lambda 内で `nproc` は 2 などと返すが、実際は cgroup の CPU quota で絞られている。
Docker の `--cpus=0.5` と同じ現象が microVM の**外側**で起きている。マルチスレッド化しても quota は変わらない。

### 穴: マイクロアーキテクチャは共有されたまま

EPT が分離するのは **アーキテクチャ的状態**（レジスタとメモリ）だけ。
物理コアの中の以下は切り替えても共有されたまま:

- L1 / L2 キャッシュ
- 分岐予測器（BTB）
- TLB
- ストアバッファ、ラインフィルバッファ

**Spectre / Meltdown / L1TF / MDS の根本はここ。**
「メモリの中身は読めないが、キャッシュに残った痕跡のタイミング差から推測できる」ので EPT では防げない。
分離の前提が「アドレスできない」であって「痕跡が残らない」ではないため。

AWS の対策:
- **Hyper-Threading を顧客間で跨がせない** — 同一物理コアの2つの HT スレッドは必ず同じ顧客に割り当てる（Firecracker 論文に明記）。HT ペアは L1 キャッシュを共有するので最も危険
- VM entry 時の L1D フラッシュ、マイクロコード更新
- ベアメタルインスタンス / Dedicated Host は物理サーバごと専有

### まとめ

| 資源 | 分離されているか |
|---|---|
| **メモリ** | ✅ 完全（EPT により物理的にアドレス不能） |
| **I/O（ネットワーク・ストレージ）** | ✅ 完全（Nitro Card が担当） |
| **CPU の実行時間** | ❌ 共有（時分割）— ただし状態は毎回入れ替わる |
| **キャッシュ・分岐予測器** | ❌ 共有 ← **サイドチャネルの穴はここ** |

- 「実質的に別マシン」と言い切れるのは**メモリと I/O** について
- **CPU の実行資源そのものは共有**している。分離しているのは実行の瞬間ごとの状態
- **コア数は非常に柔軟** — vCPU は物理コアの割り当てではなくスケジューラのスレッドなので、ホスト全体では物理コア数を超える vCPU を発行できる（1つの VM に物理コア数を超えて割り当てることはできない）

## Q5: 顧客はメモリの一部を占有している？Nitro と Firecracker はそれぞれに割り当てられている？インスタンスが落ちるとは？

### CPU は時分割、メモリは空間分割

| | 分け方 | 他人と共有するか |
|---|---|---|
| **CPU** | 時分割（同じコアを交代で使う） | ✅ する。状態だけ毎回入れ替える |
| **メモリ** | 空間分割（物理ページを取り置く） | ❌ しない。他人のページはアドレス不能 |

メモリのアドレス変換は**二段**:

```
ゲスト仮想アドレス
   ↓ ゲストのページテーブル（ゲストカーネルが管理）
ゲスト物理アドレス      ← ゲストは「これが物理アドレス」だと信じている
   ↓ EPT（ハイパーバイザが管理・ゲストは触れない）
ホスト物理アドレス      ← 本物のDRAMの番地
```

**この2段目がすべて。** EPT にエントリのない番地は「存在しないメモリ」なので、他顧客のページはアクセス不能。

### ただし「取り置き」は遅延評価

microVM のメモリの実体は、**ホスト上の Firecracker プロセスが `mmap` した匿名メモリ領域**。
ホストから見ればただの巨大な malloc 領域。

Linux の demand paging が効くので、**実際に触ったページにしか物理 RAM は割り当たらない**。
1GB 設定の Lambda を 1000 個起動しても物理 RAM 消費は 1TB にならない。
Firecracker 論文でも、Lambda のフリートでは CPU・メモリともにオーバーサブスクライブしていると述べられている。

一方 **EC2 の通常インスタンスはメモリをオーバーサブスクライブしない**。m5.large の 8GB は本当に確保されている。

### Nitro と Firecracker の割り当てられ方は対称ではない

| | 個数 | 割り当て単位 |
|---|---|---|
| **Firecracker プロセス** | **microVM ごとに1個**（1:1） | 128 microVM なら 128 プロセス。それぞれ独立した jailer に包まれる |
| **Nitro Card** | **ホストに数枚（物理カード）** | 全 VM で**共有**。ただし SR-IOV で Virtual Function を切り出す |
| **Nitro Hypervisor** | ホストに1個 | 全 VM を統括（Lambda worker はベアメタルなので不在） |

**SR-IOV** により1枚の物理 NIC が複数の **Virtual Function (VF)** に分割され、各 VM に1つずつ PCIe パススルーされる。
ゲストからは「自分専用の物理 NIC」に見えるが、実体は1枚のカードの中の論理区画。

- **Firecracker は「顧客ごとの門番」** — プロセスが1対1で対応する
- **Nitro Card は「共用の交換機」** — 1台を全員で使うが、ハードが区画を強制する

### 「インスタンスが落ちている」とは、どの層が死んだか

EC2 のステータスチェックが2つに分かれているのは、この階層をそのまま反映している。

| チェック | 死んだ層 | 誰が直すか |
|---|---|---|
| **System status check** | 物理ホスト / ハイパーバイザ / 電源 / ネットワーク | **AWS**（自分では直せない） |
| **Instance status check** | ゲスト OS の内部 | **自分**（カーネルパニック、FS破損、設定ミス） |

#### 落ち方のパターン

**① ゲストのカーネルパニック / OOM**
VM は生きている。Firecracker プロセスも動いている。中の Linux が止まっているだけで、CPU は `HLT` 相当。
→ *instance* status check だけ失敗。**シリアルコンソールのログは読める**（シリアル出力は VMM を通るため）。
EC2 Serial Console や `get-console-output` が使えるのはこれが理由。

**② `stop` した場合**
ゲストに ACPI シャットダウン信号 → OS が正常終了 → VM プロセス終了 → **物理ホストとの結びつきが切れる**。

`start` すると**別の物理ホストに配置される**。
だから「ハードウェア障害っぽいときは stop/start しろ」が定石（reboot はホストが変わらないので効かない）。
同時にインスタンスストア（ローカル NVMe）は消え、パブリック IP も変わる。EBS はネットワーク越しなので残る。

**③ 物理ホストの障害**
Firecracker / VM プロセスごと消滅。ゲストから見ると**電源プラグを引っこ抜かれた**のと同じで、ACPI も来ないし終了処理も走らない。
→ 事前に分かれば「retirement（廃止予定）」通知が出る。突然死なら Auto Recovery が別ホストで再起動。

**④ VMM プロセスが kill された場合**
③ と同じく即死。ここに本質がある:

> **VM はホスト上のただのプロセスなので、`kill` 一発で物理サーバの電源断と同じことが一瞬で起きる**

ゲスト側は自分が消されたことを知る手段すらない。
「クラウドのインスタンスはペットではなく家畜」の技術的な裏付けがここ。

#### Lambda / Fargate では見え方が変わる

**Lambda には「インスタンスが落ちる」という概念がユーザーに露出しない。**

- 実行環境（microVM）はアイドル後に**黙って破棄される** — 障害ではなく正常動作。次のリクエストがコールドスタートになるだけ
- ホスト障害が起きてもリクエストは別 Worker にルーティングされるだけで、呼び出し元は気づかない
- 関数コードのクラッシュは実行環境の死ではなく、1回の呼び出しの失敗

**Fargate** は中間。タスク停止時に `stoppedReason` に理由が入り、ホスト障害なら `Host EC2 instance terminated` のように
**「下の層が死んだ」ことが API から見える**設計。

## Q6: ECS は仮想マシンを買っているというより、巨大なマシンのプロセスを1つ買っている、という認識で合っている？

半分正解。**どの視点から見るか**で答えが変わり、さらに**「ECS」がどちらを指すか**で話が根本的に変わる。

### ホスト目線では、まさにその通り

物理ホストで `ps` を叩けば、Fargate タスクは**本当に1行のプロセス**として並んでいる。

```
PID    COMMAND
8821   firecracker --api-sock /srv/jailer/.../api.sock   ← 顧客Aのタスク
8934   firecracker --api-sock /srv/jailer/.../api.sock   ← 顧客Bのタスク
9102   firecracker --api-sock /srv/jailer/.../api.sock   ← 顧客Aの別タスク
```

ホストのスケジューラから見ればただのマルチスレッドプロセス。`kill` できるし、`mmap` した領域を持っているだけ。

### ただしプロセスが持てないものを持っている

| | 普通のプロセス | Fargate タスク / Lambda |
|---|---|---|
| カーネル | ホストのを借りる | **自前で持つ** |
| IP アドレス | ホストのを借りる | **自前で持つ（ENI）** |
| ブロックデバイス | ホストの FS の一部 | **自前で持つ** |
| 中で動くプロセス数 | 1 | **何個でも**（フルの Linux） |

**「ホストのプロセステーブルに1行載っている」は正しいが、「プロセスの機能しか持たない」は誤り。**
中身は完全な1台のコンピュータ。

この二重性 —— **ホストから見れば1プロセス、中から見れば1台のマシン** —— が仮想化の定義そのもの。

### 「ECS」がどちらかで全然違う（重要）

#### ECS on EC2 の場合

**AWS に払っているのは EC2 の料金だけ。ECS 自体は無料。**

```
買っているもの = EC2インスタンス（Nitro上のVM）
                  ↓
   その中を、自分でコンテナ（＝ただのプロセス）に分けている
```

ECS は**オーケストレーター（制御プレーン）**でしかない。「どのインスタンスにどのコンテナを置くか」を決めるスケジューラであって実行基盤ではない。

- AWS から買っているのは **VM**（EC2）
- プロセスに分けているのは **自分**（ECS Agent が containerd を叩く）

→ 「巨大なマシンのプロセスを買っている」ではなく、
**「巨大なマシンの中の1台の VM を買って、その中を自分でプロセスに分けている」**。

#### Fargate の場合

こちらは認識に近い。

```
買っているもの = タスク1つ = microVM 1つ = ホスト上の Firecracker プロセス1つ
```

EC2 インスタンスという概念が消え、vCPU × メモリ × 時間で直接課金される。

### 正確な言い方は「区画（スロット）を買っている」

「プロセスを買う」だと**資源が動的に融通される**印象になるが、実際は**固定サイズの区画**。

| | 何を買っているか | 課金単位 |
|---|---|---|
| **EC2** | 物理マシンの時間区画（VM） | インスタンス時間 |
| **ECS on EC2** | （EC2 のみ。ECS は無料） | インスタンス時間 |
| **Fargate** | タスク単位の区画 = microVM 1個 | vCPU × メモリ × 秒 |
| **Lambda** | 実行時間だけの区画 | GB × ミリ秒 |

下に行くほど**区画の粒度が細かく、寿命が短くなる**。
Lambda が究極形で「リクエストを処理している間だけ存在する区画」を買っている。

本質的には、**買っているのは計算資源そのものより「他の顧客に邪魔されない保証」**。
Nitro も Firecracker も EPT も、全部そのための機構だった。

### 「巨大なマシン」の限界

**資源は物理サーバをまたいでプールされていない。** タスクは必ず1台の物理サーバに収まる。だから上限がある。

- **Fargate は最大 16 vCPU / 120 GB** — これ以上は1台の物理ホストに収まらない
- **Lambda は最大 10,240 MB（約6 vCPU 相当）**

「巨大なマシンの一部」ではなく、**「たくさんある普通のサイズのマシンのうち1台の、一部」**が実態。
「1台に収まらないサイズは買えない」という制約がこの現実を露出させている。

## Q7: Lambda に限定すると、全体像はどうなる？

### 買っているもの

**「実行環境が起きている時間の区画」。** プロビジョニングという概念がなく、課金は **GB × ミリ秒**。

Lambda 固有の重要な性質として、**課金されるのは microVM が動いている間だけ**で、**存在している間ではない**。
実行環境はアイドル中も裏で生き残る（＝次がウォームスタート）が、そこは無課金。AWS が在庫リスクを持っている。

### 物理から見た全体像

```
Worker (EC2 ベアメタルインスタンス)
├─ Nitro Card ──── ネットワーク / ストレージ / ルートオブトラスト
└─ ホストLinux + KVM
    ├─ jailer → Firecracker → microVM 【顧客A / 関数X / v3】 ← 実行環境1つ
    ├─ jailer → Firecracker → microVM 【顧客A / 関数X / v3】 ← 同時実行2つ目
    ├─ jailer → Firecracker → microVM 【顧客A / 関数Y / v1】
    ├─ jailer → Firecracker → microVM 【顧客B / 関数Z / v7】
    └─ ... 数百個
```

**microVM 1個 = 実行環境1つ = 同時実行1つ。** これが Lambda の全部。同時実行 100 なら microVM が 100 個。

各 microVM は **「1アカウントの、1関数の、1バージョン」専用**に固定される。
使い回しは同じ関数バージョンの連続リクエスト間だけ。他人のコードと同居することはない。

### microVM の中身

```
microVM
├─ ゲストカーネル（最小構成 Linux）
├─ init プロセス（Lambda が用意）
├─ Runtime（Node.js / Python / JVM ... or 自前）
│    ↕ Runtime API (HTTP: 127.0.0.1)
└─ あなたのハンドラコード
```

**Runtime API** が特徴的で、Lambda はコードを「呼び出す」のではなく、**ランタイムが HTTP で次のイベントを取りに行く**構造。

```
GET  /2018-06-01/runtime/invocation/next        ← ここでブロックして待つ
POST /2018-06-01/runtime/invocation/{id}/response
```

環境変数 `AWS_LAMBDA_RUNTIME_API` にエンドポイントが入る。
カスタムランタイム（`provided.al2023`）が作れるのはこの API が公開されているから。**このループを回すバイナリを置けば何語でも動く**。

### 実行環境の一生

```
[コールドスタート]
 ① microVM 起動（Firecracker が ~125ms で boot）
 ② コードのダウンロードと展開
 ③ INIT — ハンドラの外側のコードが走る（DB接続、SDK初期化など）
     ↓
 ④ INVOKE — ハンドラ実行
     ↓
 ⑤ ★フリーズ★  ← 最重要
     ↓（次のリクエストが来たら ④ に戻る = ウォームスタート）
 ⑥ SHUTDOWN — 一定時間アイドルで破棄
```

#### ⑤ のフリーズが Lambda 最大の落とし穴

ハンドラが return した瞬間、**microVM の vCPU が丸ごと停止する**。
プロセスが終了するのではなく、**時間が止まる**。

- ハンドラが `await` していないバックグラウンド処理は、**実行途中のまま凍結される**
- `setInterval` やバックグラウンドスレッド（メトリクス送信、ログのフラッシュ）は動かない
- 凍結された処理は、**次の呼び出しが来たときに、その続きから再開される** — 数分後かもしれないし、永遠に来ないかもしれない

「ローカルでは動くのに Lambda だとログが飛ばない」「たまに前回のリクエストの処理結果が混ざる」の正体。
**ハンドラが返る前に全部 await する**しかない。
Node.js の `context.callbackWaitsForEmptyEventLoop = false` はこの凍結を明示的に許可するフラグ。

#### コールドスタートを消す手段

| | やること |
|---|---|
| **Provisioned Concurrency** | microVM を事前に起動し、INIT 済みの状態で待機させる（起きている分だけ課金） |
| **SnapStart** | INIT 完了時点の **microVM のメモリスナップショット**を取り、以降はそれを復元して起動する |

SnapStart は Firecracker のスナップショット機能そのもので、③ を丸ごとスキップする。
ただし**復元された全 microVM が同じメモリ状態から始まる**ので、INIT 中に生成した乱数シードや UUID が全インスタンスで重複する
（`beforeCheckpoint` / `afterRestore` フックで再生成が必要）。

### CPU とメモリ

**vCPU は指定できず、メモリ設定に比例する。**

| メモリ | CPU |
|---|---|
| 128 MB | 約 0.07 vCPU |
| 1,024 MB | 約 0.58 vCPU |
| **1,769 MB** | **1 vCPU** |
| 10,240 MB | 約 6 vCPU |

CPU バウンドな処理でメモリを増やすと、速くなった上に**総額が下がることがある**（GB-秒課金）。
`/tmp` は microVM 専用のブロックデバイスで 512 MB〜10,240 MB。実行環境が破棄されれば消える。

### ネットワーク

デフォルトでは **microVM は自分の VPC の中にいない**。Lambda サービスが管理するネットワークにいて、そこから NAT で外に出る。

```
microVM (virtio-net)
   ↓
ホストの tap デバイス
   ↓
【デフォルト】Lambda サービスの管理ネットワーク → NAT → インターネット
【VPC接続時】Hyperplane (VPC-to-VPC NAT) → 自分のVPC
   ↓
Nitro Card → VPCオーバーレイ → 物理ネットワーク
```

- デフォルト: 設定なしでインターネットに出られるが、RDS 等のプライベートリソースには届かない
- VPC 接続時: Hyperplane 経由。**ENI を関数ごとに作るのではなく、VPC-to-VPC NAT で全同時実行が共有**するのでスケールしても ENI は増えない（2019年以前の「ENI 作成待ちで数十秒のコールドスタート」は解消済み）
- ただし **VPC に入れるとインターネットへの直接の出口を失う** → NAT Gateway か VPC エンドポイントが別途必要。今も普通に踏む罠

### 「落ちる」という概念がない

| 起きたこと | ユーザーから見えるもの |
|---|---|
| 実行環境がアイドルで破棄された | 何も。次がコールドスタートになるだけ |
| Worker（物理ホスト）が死んだ | 何も。別 Worker にルーティングされる |
| ハンドラが例外を投げた | その1回の呼び出しが失敗（`errorType` が返る） |
| メモリ超過 / タイムアウト | その1回が失敗し、**実行環境ごと破棄**される |

「インスタンスの死」が「1回の呼び出しの失敗」まで粒度が下がっているので、
**監視すべきは実行環境ではなくエラー率と `Duration`**。

### 理解チェック（よくある誤解の整理）

| 認識 | 判定 |
|---|---|
| Lambda は microVM を占有している | ✅ 正しい（1アカウント/1関数/1バージョン専用） |
| **ウォームスタートの間はずっと「起動している」** | ⚠️ **存在しているが、動いていない（フリーズ）** |
| メモリは他の microVM からアクセスされない | ✅ 正しい（EPT によりアドレス表現不能） |
| ネットワークは Nitro Card がよしなにしている | ⚠️ 物理層としては正しいが、Lambda 固有の層は **Hyperplane** |
| microVM はカーネル自体を起動している | ✅ 正しい。**Docker との決定的な差** |

「起動している」ではなく「**凍結保存されている**」が正確。

| | 保持される | 動く |
|---|---|---|
| グローバル変数、DB接続プール | ✅ | — |
| `/tmp` の中身 | ✅ | — |
| **バックグラウンドスレッド、`setInterval`** | ✅（状態は残る） | **❌ 止まる** |

ウォームスタートが速いのは**メモリが保持されているから**であって、「プロセスが動き続けているから」ではない。

## Q8: Hyperplane は microVM のネットワーク設定を見て、通信を特定の VPC に流すか判断している？

**「判断している」のではなく「事前に配線されている」**が正確。

### 判断ではなく、設定時の配線

Hyperplane がパケットごとに「これはどの VPC 行きか？」と判断しているわけではない。
**関数に VPC 設定を入れた時点で、行き先が固定的に配線される。**

```
[関数に VPC 設定を入れる]     ← ここで配線が起きる（invoke時ではない）
      ↓
AWS が VPC の中に Hyperplane ENI を作る
      ↓
その関数の microVM は、全部そのENIに紐づけられる
```

invoke のたびに何かを判断する処理は入らない。**すでに繋がっている管を通るだけ**。
昔は同時実行が増えるたびに ENI を作っていたので数十秒かかっていた。

### microVM 側に VPC の設定は無い

**microVM は自分がどの VPC に繋がっているか知らない。**
持っているのは普通の `virtio-net` インターフェースとデフォルトルートだけ。
VPC の情報は **Hyperplane 側のマッピングに存在**し、ゲストからは完全に不可視。

```
microVM
  └ eth0 (virtio-net) — ただのNIC。VPCのことは何も知らない
       ↓ tap デバイス
   Lambda管理ネットワーク
       ↓
   ★Hyperplane★  ← ここにマッピングがある（VPC-to-VPC NAT）
       ↓
   VPC内の Hyperplane ENI（本物のENI、SGが付いている）
       ↓
   VPCのサブネット
```

### ENI が作られる単位

**ENI は関数ごとでも同時実行ごとでもない。**

> **ENI 1本 = (サブネット × セキュリティグループ) の組み合わせ 1つ**

同じ subnet + SG を使う関数が 50 個あっても、同時実行が 1000 あっても **ENI は1本**。
だからスケールしても ENI が増えず、アカウントの ENI 上限にもぶつからない。

逆に **SG を1個変えただけで新しい ENI が作られる**（VPC 設定の変更に数十秒〜数分かかるのはこのため）。

### 「特定の VPC に流すかどうか」は全か無か

**宛先ごとの振り分けは Lambda 側では一切していない。**

| | 通信の行き先 |
|---|---|
| **VPC 設定なし** | 全部 Lambda 管理ネットワーク → NAT → インターネット |
| **VPC 設定あり** | **全部** Hyperplane → 自分の VPC |

「VPC 内の宛先だけ VPC に流し、インターネット宛てはそのまま外に出す」という動きは**しない**。
VPC を有効にした瞬間、**全トラフィックが VPC に入る**。

だからインターネットへの直接の出口を失い、NAT Gateway か VPC エンドポイントが必要になる。
**「VPC に入れたら S3 も DynamoDB も叩けなくなった」**という定番の事故はこれ（対処は VPC エンドポイント）。

そして **ルーティングの判断をしているのは自分の VPC のルートテーブル**。
Hyperplane はただの入口で、その先は普通の VPC のルーティングに従う。

### 観測できる帰結

- **VPC Flow Logs で送信元 IP が1つに見える** — 1000 並列でも Hyperplane ENI の IP から来たことになる。同時実行を送信元 IP で区別することは**できない**
- **セキュリティグループは ENI に効く** — microVM 個別ではなく共有 ENI 単位。同じ subnet+SG の関数は全部同じ通信ポリシーになる
- **RDS の接続元 IP も1つ** — DB 側の接続元制限は書きやすい

### 余談: Hyperplane は Lambda 専用ではない

Hyperplane は AWS 内部の**分散ネットワーク機能基盤**で、多くのサービスの下敷きになっている。

- **NAT Gateway**
- **Network Load Balancer**
- **EFS**
- **PrivateLink**

いずれも「大量のフローを状態を持って処理し、単一障害点を作らない」という同じ要求があり、その共通基盤。
Lambda の VPC 対応は、**既にあった Hyperplane に相乗りすることで実現された**というのが経緯。

### まとめ

- ❌ Hyperplane が microVM の設定を見て、通信ごとに行き先を判断している
- ✅ **関数の設定時に配線が決まり、Hyperplane はその管を通す NAT。microVM は何も知らない。宛先の判断は VPC のルートテーブルがする**

## Q9: ECS on Fargate の仕組みは？Lambda とどう違う？

### 一行で言うと

**土台は完全に同じで、microVM に何を載せて、どう繋ぐかだけが違う。**

```
どちらも:  ベアメタルEC2 → KVM → jailer → Firecracker → microVM
                                                            ↑ ここから先が違う
```

Nitro / Firecracker / EPT の話はそのまま Fargate にも当てはまる。以下は差分。

### 違い①: microVM の中身

**Lambda**
```
microVM
├─ ゲストカーネル
├─ init プロセス
├─ Runtime（Node/Python/…）  ← Runtime API をポーリングするループ
└─ ハンドラ関数                ← 1つのコード
```

**Fargate**
```
microVM
├─ ゲストカーネル
├─ Fargate agent（ECS制御プレーンと通信）
├─ containerd                 ← ★ここ！
└─ コンテナ × N               ← タスク定義に書いた複数コンテナ
     ├─ app
     ├─ envoy（サイドカー）
     └─ datadog-agent（サイドカー）
```

**Fargate の microVM の中では、本物の containerd が動いてコンテナを起動している。**
つまり Fargate は「**microVM の中の Docker**」。だから:

- **サイドカーが動く**（Envoy、FireLens、各種 agent）
- 同一タスク内のコンテナは **`localhost` で通信できる**（同じ network namespace を共有）
- コンテナ間で**ボリュームを共有できる**

対照的に **Lambda はコンテナイメージをサポートしていても、コンテナとして動かしていない**。
イメージを展開してファイルシステムとして使うだけで、microVM の中に containerd はいない。
だから Lambda ではサイドカーを立てられない（拡張は Lambda Extensions という別の仕組み）。

### 違い②: ネットワーク ← 最重要

Q8 の Hyperplane の話と真逆になる。

| | Lambda | Fargate |
|---|---|---|
| VPC 内にいるか | **いない**（デフォルト） | **いる**（常に） |
| ENI | Hyperplane ENI を**全同時実行で共有** | **タスクごとに1本、専用** |
| IP アドレス | 全並列で同一（NAT の出口） | **タスクごとに別の VPC プライベート IP** |
| セキュリティグループ | (subnet × SG) 単位の共有 ENI に付く | **タスク単位** |
| インバウンド通信 | **受けられない** | **受けられる** |

**Fargate の ENI は microVM に直接アタッチされる**（awsvpc モード）。Hyperplane を経由しない。
タスクは VPC の正規の一員で、自分の IP を持ち、自分で listen できる。

帰結:
- **ALB のターゲットに直接なれる**（Lambda もターゲットになれるが実体は Lambda サービス経由の invoke）
- **VPC Flow Logs でタスクを個別に識別できる**（Lambda は送信元 IP が1つで区別不能）
- **WebSocket や gRPC ストリーミングのサーバになれる**

**Lambda が本質的にインバウンドの口を持たない**のが両者の性格を決めている。
Lambda は必ず Lambda サービスが呼び出す側、Fargate は自分で待ち受ける側。

### 違い③: フリーズしない

Lambda 最大の落とし穴だった凍結が **Fargate には存在しない**。

```
Lambda:   INVOKE → ★フリーズ★ → INVOKE → ★フリーズ★ → 破棄
Fargate:  起動 → ずっと動き続ける → 停止
```

Fargate のタスクは**普通のサーバと同じ**。だから遠慮なく使える:

- バックグラウンドスレッド、`setInterval`、cron ライブラリ
- インメモリキャッシュ、コネクションプール（**本当に効く**）
- グレースフルシャットダウン（`SIGTERM` を受けて処理中のリクエストを捌ける）

### 違い④: 起動時間 — なぜ Fargate は遅いのか

microVM の boot はどちらも ~125ms なのに、体感は Lambda 数百ms、Fargate 数十秒。
**差は microVM の外側にある。**

```
Fargate タスク起動の内訳（典型例）
├─ キャパシティのプロビジョニング     数秒
├─ ★コンテナイメージの pull★        10〜60秒  ← 支配的
├─ ENI のアタッチと VPC 設定          5〜10秒  ← 意外と重い
├─ microVM boot + containerd 起動     1秒未満
└─ ヘルスチェック通過待ち             数秒〜
```

**ボトルネックはイメージの pull。** 500MB のイメージを毎回引くので Firecracker の速さが効かない。

Lambda が速いのは、コードパッケージがキャッシュされ、**ENI が事前配線済み**（Q8）だから。
ここでも「配線は設定時に済ませてある」という設計が効いている。

対策は **SOCI（Seekable OCI）**。イメージ全体の pull を待たず、
**必要なファイルだけを遅延ロードして起動する**仕組みで、大きいイメージだと起動時間が半分以下になる。

### 違い⑤: スケーリングの主体

| | 誰がスケールさせるか |
|---|---|
| **Lambda** | **AWS**。リクエストが来たら microVM が増える。設定不要 |
| **Fargate** | **自分**。ECS Service の desired count / Application Auto Scaling |

Fargate は **CloudWatch メトリクスを見て閾値を超えたらタスクを増やす**という古典的な方式。
メトリクス収集間隔 + タスク起動時間が乗るので、**負荷の急増への追随に数分かかる**。

### 比較表

| | Lambda | Fargate |
|---|---|---|
| **分離** | Firecracker microVM | Firecracker microVM（**同じ**） |
| **microVM の中** | ランタイム + 関数 | **containerd + コンテナ群** |
| **サイドカー** | ❌（Extensions で代替） | ✅ |
| **VPC** | 外（デフォルト）/ Hyperplane 経由 | **常に中、専用 ENI** |
| **IP** | 全並列で同一 | **タスクごと** |
| **インバウンド** | ❌ | ✅ |
| **フリーズ** | ✅ する | ❌ しない |
| **起動** | 〜数百 ms | **数十秒**（イメージ pull） |
| **最大実行時間** | **15 分** | 無制限 |
| **サイズ上限** | 10 GB / 約 6 vCPU | **120 GB / 16 vCPU** |
| **課金** | GB × ミリ秒、**アイドル無課金** | vCPU × メモリ × 秒、**アイドルも課金** |
| **スケール** | 自動・即時 | 自分で設定・数分 |
| **ペイロード上限** | 6 MB（同期） | なし |

### 使い分け

**Lambda が向く**
散発的なイベント処理、S3/SQS/EventBridge 起動、トラフィックに波がある API、アイドル時間が長い

**Fargate が向く**
常時稼働のサーバ、15分を超える処理、WebSocket や長時間接続、大きな依存関係（MLモデル、ヘッドレスブラウザ）、
既存の Docker 資産をそのまま動かしたい、サイドカーが要る

判断軸を1つ選ぶなら **「アイドル時間の割合」**。
暇な時間が長いほど Lambda が有利（無課金）、常に働いているなら Fargate のほうが単価が安い。

### まとめ

**AWS は Firecracker という1つの基盤の上に、粒度と繋ぎ方を変えて2つのプロダクトを載せている。**

## Q10: ENI とはどういうもの？実態は？

**ENI は「仮想 NIC」というより、分散データベースの1レコード。**

### 実態は台帳のレコード

`CreateNetworkInterface` を叩いても**物理的には何も作られない**。
作られるのは **Mapping Service**（VPC を支える AWS 内部の分散データベース）に登録される1行。

```
ENI レコード
├─ eni-0a1b2c3d4e5f
├─ MAC アドレス        02:5f:a1:...     ← AWS が払い出す（実在の NIC のものではない）
├─ プライベート IP      10.0.1.47 (+セカンダリIPを複数可)
├─ 所属                 vpc-xxx / subnet-yyy / AZ-a
├─ セキュリティグループ  sg-aaa, sg-bbb
├─ ソース/宛先チェック   有効
└─ ★アタッチ先★        i-0123... / 物理ホスト H の スロット 3   ← ここが肝
```

**ENI は「VPC 内での住所と身分証」であって、ハードウェアではない。**

証拠として分かりやすいのが、**ENI は誰にもアタッチされていない状態で存在できる**こと（`available` ステート）。
IP を確保したままどこにも刺さっていない NIC が存在する。物理的なモノならありえない。

### アタッチすると何が起きるか

```
① Mapping Service のレコードを更新
     「eni-0a1b... は 物理ホストH のスロット3 にいる」
② その物理ホストの Nitro Card に、ENI の状態をロード
     IP、MAC、SGルール、詐称チェックの許可リスト
③ SR-IOV の Virtual Function を1つ切り出し、PCIe デバイスとしてVMに見せる
④ ゲストの Linux が ena ドライバでそれを掴み、eth0 として認識
```

**ENI のデタッチ＆別インスタンスへのアタッチは、台帳の書き換え。**
物理的に何かを引き抜いているわけではないので、IP も MAC も SG もそのまま付いてくる。

### パケットが出るときに起きていること

```
① ゲストが eth0 にパケットを書く
       ↓
② Nitro Card が受け取る
       ↓
③ ★送信元IPがこのENIのものか検証★     ← ハードウェアで強制。詐称は不可能
       ↓
④ セキュリティグループを評価（ステートフル、コネクション追跡）
       ↓
⑤ Mapping Service に「宛先IPはどの物理ホスト？」を問い合わせ（キャッシュあり）
       ↓
⑥ カプセル化して物理ネットワークへ送出
```

**「セキュリティグループは ENI に付く」の意味がここで分かる。**
SG はサブネットでもインスタンスでもなく、**Nitro Card 上で ENI のコンテキストとして評価される**。だから ENI 単位。

同じインスタンスに ENI を2本刺して別々の SG を付ければ、**同一 OS の中で NIC ごとに通信ポリシーが変わる**。

### なぜこの抽象が必要だったのか

**インスタンスと IP を切り離すため。**

- **インスタンスを作り直しても IP と MAC を維持できる** — MAC アドレス縛りのライセンスを持つソフトが動く
- **フェイルオーバー** — ENI を待機系に付け替えるだけで IP ごと引っ越せる（DNS 伝播を待たなくていい）
- **1インスタンスに複数 ENI** — 管理用サブネットと本番用サブネットの両方に所属できる
- **タスク/Pod 単位の所属** — awsvpc モードや EKS の VPC CNI の土台

### 「見覚えのない ENI」の正体

AWS のサービスが顧客の VPC の中に足を生やしているもの。

| 説明欄の見え方 | 正体 |
|---|---|
| `ELB app/xxx` | ALB / NLB がサブネットごとに置く |
| `RDSNetworkInterface` | RDS インスタンスの実体 |
| `VPC Endpoint Interface` | PrivateLink のエンドポイント |
| `AWS Lambda VPC ENI` | **Hyperplane ENI**（Q8 の主役） |
| `Interface for NAT Gateway` | NAT Gateway |
| `aws-K8S-i-xxxx` | EKS の VPC CNI が Pod 用に作ったもの |

これらは **requester-managed ENI** と呼ばれ、**顧客からは削除できない**（マネージドサービス側が管理）。

「サブネットを削除できない」「VPC を消せない」トラブルの原因はほぼこれ。
**先に本体のサービスを消さないと ENI が残り続ける。**

### ENI の変種

| 種類 | 用途 |
|---|---|
| **通常の ENI** | 普通のやつ |
| **Hyperplane ENI** | Lambda の VPC 接続用。顧客アカウントに見えるが AWS 管理。全同時実行で共有 |
| **Trunk ENI** | 1本の ENI の中に複数の **branch ENI** を VLAN タグで多重化。ECS の ENI Trunking を有効にすると、インスタンスあたりの awsvpc タスク数を大幅に増やせる |

Trunk ENI は「ENI 数の上限」というハードウェア由来の制約を、**論理的な多重化で回避**している。

### 数の上限が牙を剥く場所

ENI は Nitro Card のリソースを消費するので、**インスタンスタイプごとに上限がある**。

- インスタンスあたりの **ENI 本数**
- ENI あたりの **セカンダリ IP 数**

最も有名な形で表面化するのが **EKS の Pod 密度**。
VPC CNI は Pod ごとに ENI のセカンダリ IP を割り当てるので:

```
最大Pod数 = (ENI本数 × (ENIあたりIP数 - 1)) + 2
```

`m5.large` なら 3 ENI × 10 IP で **29 Pod が上限**。
CPU もメモリも余っているのに Pod がスケジュールできない現象の正体
（対策は Prefix Delegation か Trunk ENI 系の仕組み）。

もう1つ、**ENI はサブネットに属するので AZ をまたげない**。
フェイルオーバーで ENI を付け替える構成が同一 AZ 内に限られるのはこのため。

### まとめ

- **ENI の実態は Mapping Service 上の1レコード**（住所と身分証）
- **アタッチすると Nitro Card に状態がロードされ、SR-IOV の VF としてゲストに見える**
- **SG が ENI 単位なのは、Nitro Card がその ENI のコンテキストで評価するから**
- **付け替え = 台帳の書き換え**なので、IP も MAC も丸ごと移動できる

## Q11: Nitro Card はどこに所属している？インスタンスは必ず特定の Nitro Card と関連づくのか？

**所属は物理サーバのマザーボード。そして Nitro Card はインスタンス専属ではなく、物理サーバ専属。**

### Nitro Card は物理サーバに刺さった PCIe カード

顧客ごとに用意されるものではない。
**1台の物理サーバに数枚刺さっていて、その上に載っている全 VM（数十〜数百個）を1枚が担当する。**

| カード | 担当 |
|---|---|
| **Nitro Card for VPC** | ネットワーク。**ENI を実装しているのはこれ** |
| **Nitro Card for EBS** | ネットワーク越しの EBS を、ローカル NVMe に見せかける |
| **Nitro Card for Instance Storage** | ローカルの物理 NVMe SSD |
| **Nitro Card Controller** | 全体の統括、ハードウェアのルートオブトラスト |
| **Nitro Security Chip**（カードではなくチップ） | マザーボードの I/O 経路を仲介、ファームウェア書き込みをブロック |

### インスタンスとの関係は「スロット単位」で、固定ではない

> **インスタンスは特定の Nitro Card と永続的に紐づかない。
> 「今たまたま乗っている物理サーバの Nitro Card」に、その都度紐づく。**

```
インスタンス i-0123 を stop
   → 物理ホストH1 から剥がれる。H1のNitro Cardから状態が消える
インスタンス i-0123 を start
   → 全然別の物理ホストH7 に配置される
   → H7のNitro Card に、同じENIの状態（IP/MAC/SG）がロードされる
```

**それでもインスタンスからは何も変わって見えない。** 同じ `eth0`、同じ IP、同じ MAC、同じ EBS。
ENI が台帳のレコード（Q10）だからこそ、ハードウェアを乗り換えても身分証がそのまま付いてくる。

Nitro Card 側から見れば、**ENI の状態は「今このスロットにいる VM のために一時的にロードされている設定」**でしかない。

### 「振り分け」の正確な姿

> ❌ Nitro Card が ENI レコードを見て、ネットワーク全体のルーティングを決めている

**Nitro Card は自分の物理サーバに載っている VM の分しか担当しない。**
**両端の Nitro Card が対になって仕事をしている。**

```
VM-A (10.0.1.20, 物理ホストH1)  →  VM-B (10.0.2.30, 物理ホストH7)

【H1のNitro Card — 送信側】
 ① 送信元IPが、このVMのENIのものか検証   ← 詐称チェック
 ② セキュリティグループ（アウトバウンド）を評価
 ③ Mapping Service に問い合わせ「10.0.2.30 はどこ？」
      → 「物理ホストH7 のスロット5」（結果はキャッシュされる）
 ④ カプセル化（外側の宛先 = H7の物理IP）して物理ネットワークへ

        ～ 物理ネットワークはただのL3。中身のVPCのことは知らない ～

【H7のNitro Card — 受信側】
 ⑤ デカプセル化
 ⑥ 宛先ENIを特定し、セキュリティグループ（インバウンド）を評価
 ⑦ 該当VMのキューに投入
```

役割分担:

- **Mapping Service** = 「その IP がどの物理ホストにいるか」を知っている**全体の住所録**（分散DB）
- **Nitro Card** = 自分のサーバの**玄関の門番 兼 郵便の仕分け係**。住所録に問い合わせて封筒に宛先を書き、届いた封筒を開けて正しい部屋に配る

Nitro Card は住所録を「持って」おらず、「引く」だけ。

### 1枚のカードが複数 VM を担当できる仕組み

**SR-IOV。** 1枚の物理カードが PCIe レベルで複数のデバイスに分身する。

```
Nitro Card for VPC （物理1枚）
├─ PF (Physical Function)      … ホスト側が管理
├─ VF (Virtual Function) #1 ──→ VM-A に PCIe パススルー → VM-Aからは eth0 に見える
├─ VF #2 ─────────────────→ VM-B に パススルー
├─ VF #3 ─────────────────→ VM-C に パススルー
└─ ... 数百
```

各 VM は**自分専用の物理 NIC を持っていると信じている**（Linux は `ena` ドライバで普通の NIC として扱う）。
実体は1枚のカードの中の論理区画で、カードの内部で **VF ↔ ENI のマッピング**が保持されている。

**VF が他 VM のメモリを DMA で触れないことを保証しているのが IOMMU（VT-d）**。
Q4 で出てきたハードウェア機構がここでも効いている。

### 引っ越すとどうなるか

| | Nitro Card | 起きること |
|---|---|---|
| **reboot** | 同じ | ゲストOSの再起動だけ。ホストは変わらない |
| **stop → start** | **変わる** | 別の物理ホストに再配置。ENI の状態が新しいカードにロードし直される |
| **ホスト障害** | 変わる | Auto Recovery で別ホストに。ENI レコードのアタッチ先が書き換わる |

「ハードウェア障害っぽいときは reboot ではなく stop/start」の理由がここで明確になる。
**reboot ではカードもホストも変わらないので、ハードウェア起因の問題は直らない。**

なお Nitro 世代では**ハイパーバイザやカードのファームウェアをインスタンスを止めずに更新できる**ようになっており、
「メンテナンスによる再起動が昔より圧倒的に減った」理由になっている。
ただしユーザーとの契約上は今も retirement 通知ベースなので、**ライブマイグレーションを前提に設計してはいけない。**

### 帯域が共有されることの帰結

**1枚のカードを、そのサーバ上の全 VM で共有している。** だからカードの帯域は有限な共有資源で、これが表に出る。

- **インスタンスタイプごとにネットワーク帯域の上限がある**（`m5.large` = 最大10Gbps だが実際はベースライン + バースト）
- **小さいインスタンスはバーストクレジット制** — カードの取り分を絞られている
- **EBS の帯域も別枠で上限がある**（EBS 最適化）— こちらは別のカードなのでネットワークとは独立枠

「インスタンスサイズを上げたらネットワークが速くなった」のは、CPU が増えたからではなく
**Nitro Card 上の取り分が増えたから**。

### まとめ

- **Nitro Card は物理サーバのハードウェア**。顧客にもインスタンスにも属さない
- **インスタンスとの紐づきは一時的**（今いる物理ホストのカード）。引っ越せば別のカードになるが、ENI が台帳なので見え方は不変
- **全体のルーティングは Mapping Service**、Nitro Card は**両端で門番と仕分けをする**役
- **1枚を全 VM で共有**するので、帯域が有限で、インスタンスタイプごとの上限として表れる
