# DynamoDB / 分散KVストア Q&A

記録日: 2026-08-07

## Q1: そもそも KV ストアはどういう仕組みで、なぜその設計になったのか？

DynamoDB の挙動は、**「分散 KV ストアが何を捨てて何を得たか」**を知らないと丸暗記になる。

### 出発点: RDB は分散すると何が困るのか

1台なら RDB は極めて優秀。困るのは横に並べたときで、**強みだった柔軟性がそのままコストになる**。

| RDB の機能 | 分散すると |
|---|---|
| **JOIN** | 2つのテーブルが別サーバにあると、ネットワーク越しにデータを集める必要がある。通信量がデータ量に比例 |
| **トランザクション** | 複数サーバにまたがると **2相コミット**が必要。参加者が1台でも遅い/落ちると全体が待つ。**台数が増えるほど可用性が下がる** |
| **任意の WHERE 句** | どんなクエリが来るか分からないので、どう配置しても最適にならない（スキャッター・ギャザー） |
| **セカンダリインデックス** | 分割軸と違う軸のインデックスは、必ず全ノードに跨る |

**「何でもできる」ことと「水平に並ぶ」ことは、原理的に両立しない。**

### KV ストアの答え: 機能を捨てる

「キーを指定して1件取る」だけに絞ると:

- キーのハッシュで置き場所が**一意に決まる** → **どのサーバに聞けばいいか計算で分かる**（探索が不要）
- 1つの操作が**1台で完結する** → 台数を増やせばスループットがそのまま増える
- JOIN がない → ネットワーク越しのデータ集約が発生しない

**これが「水平スケールする」の正体。** 魔法ではなく、**できることを減らした結果**。
各ノードが何も共有しないので **シェアードナッシング** と呼ばれる。

→ 以降の全部がこの帰結。

### 設計要素①: 置き場所の決め方（コンシステントハッシング）

素朴な `hash(key) % ノード数` は**台数が変わると破綻する**。
4台→5台で約 80% のキーの置き場所が変わり、全データの引っ越しが始まる。

```
     ハッシュ空間を輪にする (0 〜 2^128)

            ノードA
          ↗        ↘
    key1 ●          ● ノードB      key のハッシュから時計回りに
        ↑            ↓             最初に出会ったノードが担当
    ノードC ●      ● key2
          ↖        ↙
            ノードD
```

**ノードを1台足しても、影響を受けるのは隣接する範囲だけ。** 全体の引っ越しが起きない。

実際にはさらに **仮想ノード（vnode）** を使い、1つの物理ノードを輪の上に何十個も配置する。
担当範囲の偏りが減り、ノード追加時の負荷分散も均等になる。

### 設計要素②: レプリケーション

1台だとそのノードが死んだらデータが消える。輪の上で**次の N 台にもコピー**する（N=3 が定番）。

### 設計要素③: クォーラム ← 本質

**N台のうち何台に書けたら成功とするか（W）**、**何台から読むか（R）** をダイヤルとして持つ。

> **W + R > N なら、読み取りは必ず最新の書き込みを含む**（集合として重なりが保証される）

N=3 のとき:

| 設定 | 性質 |
|---|---|
| W=3, R=1 | 読みは速いが、**1台落ちると書けない** |
| W=1, R=1 | 最速だが、**古いデータを読むことがある**（W+R=2 ≤ 3） |
| **W=2, R=2** | バランス型。1台落ちても読み書きでき、整合性も保たれる（W+R=4 > 3 ✓） |

**CAP 定理は「3つから2つ選べ」という標語より、このクォーラムのダイヤルとして理解するほうが正確。**
一貫性と可用性は二択ではなく、連続的なつまみ。

### 設計要素④: 障害時にどうするか（Dynamo 論文の選択）

2007 年の **Amazon Dynamo 論文**（ショッピングカート用）は、**可用性を極端に優先**した。

> カートに商品を追加できないのは、そのまま売上の損失

- **Sloppy quorum** — 担当ノードが落ちていたら別のノードが代理で受け取る（後で本来の持ち主に渡す = hinted handoff）
- **リーダーレス** — どのノードにでも書ける
- **結果整合性 + ベクタークロック** — 衝突は検出だけして、**解決はアプリに投げる**（カートなら「両方マージ」で正しい）

この設計が **Cassandra / Riak / Voldemort** の祖先になった。

### 重要: DynamoDB は Dynamo 論文の直系ではない

よくある誤解。**名前は継いでいるが、設計は別物。**

Dynamo は Amazon 社内ですら評判が良くなかった。理由は **使うのが難しすぎた**こと:

- 結果整合性しかない
- 衝突解決をアプリが書かなければならない
- クラスタの運用を各チームが自分でやる必要があった

2012 年の DynamoDB はそこを**全部ひっくり返している**。

| | Dynamo (2007) | **DynamoDB (2012)** |
|---|---|---|
| 書き込み | リーダーレス（どこでも） | **リーダー経由**（Paxos で選出） |
| 衝突解決 | アプリがやる | **起きない**（リーダーが順序を決める） |
| 整合性 | 結果整合性のみ | **強整合性を選べる** |
| 運用 | 各チームが自前 | **フルマネージド** |

「Dynamo 論文を読めば DynamoDB が分かる」は成り立たない。
**継承したのはコンシステントハッシングと分散の思想だけ**で、一貫性モデルは真逆に振っている。

### DynamoDB の実際の姿

```
テーブル
  └ パーティションキーをハッシュ → パーティション（＝物理的な区画）
       └ 各パーティションは 3つのレプリカ（3AZ に分散）
            ├─ ★リーダー★  ← Paxos で選出
            ├─ フォロワー
            └─ フォロワー
```

- **書き込み** — 必ずリーダーへ。リーダー + もう1台に書けた時点で成功（W=2 / N=3）
- **結果整合性読み取り** — どのレプリカから読んでもよい
- **強整合性読み取り** — **リーダーから読む**

ここから料金表の謎が解ける。

| | コスト | 理由 |
|---|---|---|
| 結果整合性読み取り | **0.5 RCU** | どのレプリカでもいいので負荷が3台に分散する |
| 強整合性読み取り | **1 RCU** | **リーダー1台に集中する**ので実質3倍の負荷 |
| トランザクション読み取り | **2 RCU** | 2相コミットが要る |

**「強整合性読み取りが倍額」は課金ポリシーではなく、物理的な負荷の反映。**
デフォルトが結果整合性なのも、そちらが自然だから。

### そして物理的な壁

パーティションは論理的な概念ではなく、**実在するサーバ上の区画**。だから1台分の性能上限を持つ。

```
1パーティションの上限
├─ 3,000 RCU
├─ 1,000 WCU
└─ 10 GB
```

テーブル全体のキャパシティに余裕があっても、**特定のパーティションキーにアクセスが集中すれば
そのパーティションだけがスロットリング**する（ホットパーティション問題）。

厄介なのは **パーティションの分割は不可逆**なこと。
データ量やスループットが増えると自動で分割されるが、一度分かれたら統合されない。
スパイクで分割が起きると、**その後は各パーティションの取り分が減った状態が残る**。

### まとめ

**「機能を捨てたから水平に並べた。並べた結果、1台分の壁が論理設計に露出した」**
—— この一本の筋で DynamoDB の癖はほぼ説明できる。

## Q2: コンシステントハッシングの意味がよくわからない

### 解きたい問題

**「キーを N 台のサーバに振り分けたい。ただし N は増減する。」**

後半の条件がすべて。台数が固定なら難しくない。

### 素朴な方法とその破綻

`hash(key) % サーバ台数` — 一見これで十分に見える。

キー6個、サーバ3台（0, 1, 2）:

| キー | ハッシュ値 | `% 3` | 配置先 |
|---|---|---|---|
| user1 | 15 | 0 | サーバ0 |
| user2 | 22 | 1 | サーバ1 |
| user3 | 8 | 2 | サーバ2 |
| user4 | 33 | 0 | サーバ0 |
| user5 | 19 | 1 | サーバ1 |
| user6 | 26 | 2 | サーバ2 |

きれいに分散している。ここで**サーバを1台追加**して 4 台にすると:

| キー | ハッシュ値 | `% 4` | 配置先 | 変化 |
|---|---|---|---|---|
| user1 | 15 | 3 | サーバ3 | **移動** |
| user2 | 22 | 2 | サーバ2 | **移動** |
| user3 | 8 | 0 | サーバ0 | **移動** |
| user4 | 33 | 1 | サーバ1 | **移動** |
| user5 | 19 | 3 | サーバ3 | **移動** |
| user6 | 26 | 2 | サーバ2 | 据え置き |

**6個中5個（83%）が引っ越し。** 1台足しただけでほぼ全データがネットワークを流れる。

原因は **`%` の答えが N に対して連続性を持たない**こと。
`15 % 3 = 0` と `15 % 4 = 3` の間に何の関係もない。N が変わると全部が無関係な値に飛ぶ。

しかも**台数が多いほど悲惨**。N→N+1 で据え置きになるのは約 `1/(N+1)` だけ。100台なら 99% が移動する。

### 発想の転換

問題は **「サーバの番号を計算している」**こと。番号は N に依存するので、N が変われば全部変わる。

そこで**サーバとキーを同じ土俵に置く**。

> **サーバもハッシュにかけて、キーと同じ空間の上に配置する。
> キーは自分より「先」にいる一番近いサーバが担当する。**

サーバの位置は**そのサーバの名前だけで決まる**ので、他のサーバが増減しても動かない。これが肝。

### リングを作る

ハッシュ空間を輪にする（実際は 0〜2^32 などだが、ここでは 0〜100）。
サーバ名もハッシュにかけて配置する。

- `hash("サーバA")` = 10
- `hash("サーバB")` = 40
- `hash("サーバC")` = 70

```
  0        10          40           70         100 (=0に戻る)
  ├────────●───────────●────────────●───────────┤
           A           B            C
  └─ Aが担当┘└─ Bが担当 ─┘└─ Cが担当 ─┘└─ Aが担当 ┘
   (0〜10)     (11〜40)     (41〜70)     (71〜100)
                                          ↑ 一周してAに戻る
```

**ルール: キーのハッシュ値から右（時計回り）に進んで、最初に出会ったサーバが担当。**
端まで行ったら 0 に戻る（＝輪）。

| キー | ハッシュ値 | 右に進んで最初のサーバ | 配置先 |
|---|---|---|---|
| user3 | 8 | A(10) | **A** |
| user1 | 15 | B(40) | **B** |
| user5 | 19 | B(40) | **B** |
| user2 | 22 | B(40) | **B** |
| user6 | 26 | B(40) | **B** |
| user4 | 33 | B(40) | **B** |
| user7 | 60 | C(70) | **C** |
| user8 | 90 | 一周して A(10) | **A** |

### サーバを追加してみる

`hash("サーバD")` = 25 とする。**D は 25 の位置に入るだけ**で、A も B も C も動かない。

```
  0        10     25    40           70         100
  ├────────●──────●─────●────────────●───────────┤
           A      D     B            C
  └─ A ────┘└─ D ─┘└ B ─┘└─── C ────┘└─── A ────┘
            (11〜25)(26〜40)
```

D が入ったことで、**B が持っていた範囲 (11〜40) が (11〜25)=D と (26〜40)=B に割れた**。

| キー | 前 | 後 | |
|---|---|---|---|
| user3 (8) | A | A | 据え置き |
| user1 (15) | B | **D** | 移動 |
| user5 (19) | B | **D** | 移動 |
| user2 (22) | B | **D** | 移動 |
| user6 (26) | B | B | 据え置き |
| user4 (33) | B | B | 据え置き |
| user7 (60) | C | C | 据え置き |
| user8 (90) | A | A | 据え置き |

**動いたのは 3個だけ。しかも B からしか動いていない。** A と C は完全に無傷。

> **新しいノードは、輪の上で「自分の直前の区間」だけを、既存の1台から引き継ぐ。**

移動量は全体の約 `1/N`。100台なら 1%。`%` 方式の 99% とは別世界。

削除も対称で、**B が落ちたら B の範囲を時計回りの次（C）が引き継ぐだけ**。他は無関係。

### 残る問題: 偏る

上の表では **B に 5個、A に 2個、C に 1個**と偏っている。
サーバの位置はハッシュ次第でランダムに決まるので、**担当範囲の幅が揃わない**。

さらに悪いことに:

> **B が落ちると、B の負荷が丸ごと C 1台に乗る。**

障害時に負荷が分散せず、**次のサーバも共倒れする**（カスケード障害）。

### 解決: 仮想ノード（vnode）

**1つの物理サーバを、輪の上に何十〜何百個配置する。**

```
hash("サーバA#1")  = 3
hash("サーバA#2")  = 17
hash("サーバA#3")  = 52
...
hash("サーバA#128") = 91
```

輪の上には点が大量に並び、**それぞれの小さな区間の合計**がサーバ A の担当分になる。

```
0                                                    100
├─A─B─C─A─C─B─B─A─C─A─B─C─C─A─B─A─C─B─A─C─B─A─C─B─A──┤
   細かく交互に並ぶ
```

効果は2つ:

**① 均等になる**
区間の数が多いほど、合計は大数の法則で平均に近づく。128個も置けばほぼ均等。

**② 障害時の負荷が分散する** ← こちらが本命
A が落ちると、**A の 128 個の区間はそれぞれ別のサーバに引き継がれる**。1台に集中しない。

おまけとして、**性能の高いサーバには vnode を多く割り当てる**ことで重み付けもできる。

### DynamoDB での実際

正確に言うと、**DynamoDB は教科書どおりのコンシステントハッシングではない。**

継承したのは「**パーティションキーをハッシュして、ハッシュ空間の位置で置き場所を決める**」という発想の部分。
実装は**ハッシュ空間を範囲で区切る**方式に近い。

```
ハッシュ空間
├── 範囲1 → パーティション1（レプリカ3つ）
├── 範囲2 → パーティション2
└── 範囲3 → パーティション3
```

パーティションが 10GB や上限スループットを超えると、**その範囲を2つに割る**（split）。

```
範囲2 (0x4000〜0x8000)
      ↓ 分割
範囲2a (0x4000〜0x6000)  範囲2b (0x6000〜0x8000)
```

Q1 の「**分割は不可逆**」はこれで、一度切った範囲を再び1つに戻す操作を DynamoDB は行わない。
だから**スパイクで分割が起きると、その細かい区画割りがずっと残る**（各区画の取り分は減ったまま）。

そして重要な帰結:

> **ハッシュ値の分布 = パーティションへの分布。
> だからパーティションキーの選び方が、そのまま物理的な負荷分散を決める。**

`userId` のようにばらけるキーなら均等に散るが、`status`（"active" / "inactive" の2値）のようなキーだと、
**ハッシュ値が2種類しかないので2つのパーティションに全部集中する**。これがホットパーティションの正体。

### まとめ

コンシステントハッシングは **「サーバの番号を計算する」のをやめて「サーバに定位置を与える」ことで、
台数変更の影響を局所化する技法**。
vnode はその上で、偏りと障害時の負荷集中を潰す実装上の工夫。

## Q3: ソートキーはどのように実現している？なぜ PK と一緒に指定しないと動かない？

### 前提: PK ではソートできない

PK はハッシュされるので、**ハッシュした時点で元の順序が完全に壊れる**。
`user#1` と `user#2` が隣り合う保証はどこにもなく、別ノードにある。

| | 条件 | ソート |
|---|---|---|
| **PK** | `=` のみ（完全一致必須） | ❌ |
| **SK** | `=` `<` `>` `between` `begins_with` | ✅ `ScanIndexForward` で昇順/降順 |

### 一言で言うと

**同じ PK のアイテムは必ず同じパーティションに置かれ、その中で SK 順にソート済みで格納されている。**

役割が完全に分かれている。

| | 役割 | 手段 |
|---|---|---|
| **PK** | 分散させる軸 | ハッシュ（順序を壊す） |
| **SK** | 順序を作る軸 | ソート済み格納（順序を保つ） |

### 物理的な格納の姿

各ストレージノードはアイテムを **B-tree** で保持している
（2022年の USENIX ATC 論文 "Amazon DynamoDB: A Scalable, Predictably Performant, and Fully Managed NoSQL Database Service" に明示）。
そのキーが **`(hash(PK), SK)` の複合キー**になっている。

```
パーティション内の B-tree（キー順に並んでいる）

 hash("user#123") | 2026-01-05 | {order data}  ┐
 hash("user#123") | 2026-02-11 | {order data}  │ 同じPKのものが
 hash("user#123") | 2026-03-02 | {order data}  │ 物理的に連続している
 hash("user#123") | 2026-08-07 | {order data}  ┘
 hash("user#456") | 2026-01-20 | {order data}  ← 別のPKの塊
 hash("user#456") | 2026-05-30 | {order data}
```

**先頭が `hash(PK)` なので、同じ PK のアイテムは B-tree 上で必ず隣り合う。**
そしてその塊の中では SK が昇順に並んでいる。

### Query が何をしているか

```
Query: PK = "user#123" AND SK BETWEEN "2026-02" AND "2026-04"
```

```
① hash("user#123") を計算
② B-tree をその値で探索 → 塊の先頭にジャンプ        … O(log n)
③ SK = "2026-02" の位置まで進む
④ ★そこから葉ノードを順に辿るだけ★                  … シーケンシャル
⑤ SK が "2026-04" を超えたら終了
```

**④ が本質。** 範囲クエリが速いのは賢いアルゴリズムのおかげではなく、
**欲しいデータが物理的に隣接しているから**。SSD を順に舐めるだけで済む。

### なぜ PK は完全一致必須なのか

同じ理屈の裏返し。B-tree のキーの**先頭が `hash(PK)`** なので:

- **hash(PK) が確定しないと探索の開始位置が決まらない**
- `user#1` 〜 `user#5` のような範囲を指定されても、**ハッシュ後の値は空間上でバラバラ**なので連続した範囲にならない

「PK は `=` のみ、SK は範囲可」という API 仕様は、**このデータ構造がそのまま表に出たもの**。
仕様というより物理の反映。

### なぜ SK 単独では検索できないのか

**SK の順序は「グローバルな順序」ではなく「PK ごとのローカルな順序」**だから。

テーブル全体を SK で並べた1本のリストは**どこにも存在しない**。
PK ごとの小さなソート済みリストが、バラバラのノードに散らばっているだけ。

```
ノードX:  user#123 | 2026-01-05
          user#123 | 2026-02-11   ← この中では並んでいる
          user#123 | 2026-08-07

ノードY:  user#456 | 2026-01-03
          user#456 | 2026-06-20   ← この中でも並んでいる

          ↑ この2つを統合した「全体の日付順リスト」は存在しない
```

「SK が `2026-01-05` のもの」を PK なしで聞かれても、**どのノードに行けばいいか決められない**。
全ノードに聞いて回るしかない ＝ それは `Query` ではなく `Scan`。

#### Scan + Filter のコストの罠

`Scan` + `FilterExpression` で代用はできるが、**課金は「読んだ量」であって「返した量」ではない**。

```
1,000万件のテーブルから、Scan + Filter で 10件ヒット
  → 10件分ではなく、1,000万件分の RCU を消費する
```

フィルタは**読んだ後に捨てているだけ**なので、コスト削減にはまったく寄与しない。

「グローバルに日付順で取りたい」なら、PK を意図的に粗くして
（`PK = "2026-08-07"` のような日付バケット、`PK = "ALL#" + hash%10` のようなシャーディング）、
**順序を持たせたい集合を1つのパーティションにまとめる**設計判断が要る。

> **順序を保ちたい ＝ 1箇所に集めたい ＝ 分散させたくない**
> ソートと分散は原理的に逆向き。

### Item Collection と 10GB の謎

同じ PK を共有するアイテムの集合を **Item Collection** と呼ぶ（上図の「塊」）。

> **Item Collection の上限は 10 GB。ただし、LSI があるテーブルに限る。**

この条件が謎に見えるが、**物理構造で説明がつく**。

**LSI がない場合** — DynamoDB は必要に応じて、**同じ PK の中を SK の範囲で分割**できる。

```
hash("user#123") の塊が巨大になった
      ↓ 分割
パーティションA: hash("user#123") | 2020-01 〜 2023-12
パーティションB: hash("user#123") | 2024-01 〜 2026-08
```

だから 10GB を超えても問題ない。

**LSI がある場合** — LSI は "Local" の名のとおり、**ベースアイテムと同じパーティションに同居していなければならない**
（だから強整合性で読める）。SK の範囲で分割すると、**別の SK 軸で並んでいる LSI が引き裂かれる**。

だから分割できず、**10GB が硬い上限になる**。

### LSI と GSI の違いも、これで説明がつく

| | LSI | GSI |
|---|---|---|
| **PK** | ベースと同じ | **別のものを指定できる** |
| **物理的な位置** | **同じパーティション**に同居 | **完全に別のパーティション**（別テーブル同然） |
| **整合性** | **強整合性で読める** | **結果整合性のみ** |
| **キャパシティ** | ベーステーブルと共有 | **専用に必要** |
| **作成タイミング** | **テーブル作成時のみ** | いつでも追加可能 |
| **Item Collection 10GB 制限** | **かかる** | かからない |

**GSI が結果整合性でしか読めないのは、ケチっているからではない。**
GSI の PK は別物なので**ハッシュ値が違い、物理的に全然別のノードに置かれる**。
書き込みは非同期でそちらにレプリケートされるので、原理的にラグが生じる。

同様に **GSI に別途キャパシティが要るのも、実体が別テーブルだから**。書き込みコストが二重にかかるのも同じ理由。

### 実務上の注意: SK の並び順はバイト順

SK が **String 型なら辞書順（UTF-8 のバイト比較）**。数値順ではない。

```
❌ "9", "10", "100"  →  "10" < "100" < "9"   （辞書順）
✅ "009", "010", "100"  →  期待どおり         （ゼロパディング）
```

日付に **ISO 8601（`2026-08-07T12:34:56Z`）が定番なのは、辞書順がそのまま時系列順になるから**。
この性質を狙って設計されたフォーマットなので SK と相性がいい。

Number 型なら数値順に並ぶのでパディングは不要。

### まとめ

- **PK = ハッシュして散らす軸、SK = ソート済みで並べる軸**。役割が真逆
- **同じ PK は物理的に隣接**しているので、範囲クエリはシーケンシャルアクセスになる
- **API の制約（PK は完全一致、SK は範囲）は B-tree の複合キー構造がそのまま出たもの**
- **SK の順序は PK ごとにローカル**。だから PK なしでは検索の開始点が決まらない
- **LSI は同居、GSI は別居**。整合性・キャパシティ・10GB 制限の違いは全部そこから来る

## Q4: リレーショナルに扱いたいケースで困った。トレードオフを再検討したい。「Scan してから」「PK で全部取ってコード側でオミット」でも RDS より強い部分がありそう

### 結論を先に

> **★最重要★ 採用判断の第一条件は「アクセスパターンを事前に全部書き出せるか」。**
> ここで詰まったら、性能の議論をする前に RDS。

### 仮説の評価: 「全部取ってコードで絞る」は正しいか

**条件付きで正しい。しかもかなり強い戦術。**

正しい理由は Q3 の物理構造そのもの。

```
Query: PK = "ORDER#123"
  → B-tree 上で隣接した領域を、1回のシーケンシャルアクセスで読む
```

RDB で `orders JOIN order_items` をやると2つのインデックスを探索してから結合する。
DynamoDB は **JOIN が不要なのではなく、JOIN 済みの状態で物理的に隣り合わせて保存してある**。
だから「関連するものを丸ごと取る」は原理的に RDB より速くて当然。

さらに RDS に勝つ点:

| | DynamoDB | RDS |
|---|---|---|
| **件数が増えたときのレイテンシ** | **変わらない**（B-tree の該当区画だけ読む） | プランが変わる、インデックスが効かなくなる、統計情報が古くなる |
| **同時実行** | **コネクション概念なし**（HTTP） | コネクションプール枯渇、ロック競合 |
| **p99** | **予測可能** | 他クエリの影響を受ける（うるさい隣人） |

特に **Lambda から叩くならコネクション問題がないだけで採用理由になる**（RDS Proxy が不要）。

### ただし成立条件がある: Item Collection が有界であること

```
1回の Query の上限は 1MB
  → 超えると LastEvaluatedKey でページング（ラウンドトリップが増える）

RCU は「読んだ量」で課金
  → 100件取って1件使うなら、100件分払う
```

| | 消費 |
|---|---|
| 4KB のアイテムを1件 | 1 RCU（強整合性） / 0.5 RCU（結果整合性） |
| 1MB を Query | **128 RCU** / 64 RCU |

- **Item Collection が数十〜数百件で有界** → 「全部取って絞る」は**最適解**。RDB より速い
- **際限なく増える**（ユーザーの全注文履歴が10年分など） → 破綻する。SK で範囲を絞るか設計を変える

**分岐点は「有界かどうか」で、件数そのものではない。**
1万件でも上限が保証されているなら問題ないし、平均10件でも上限がないなら設計欠陥。

### Scan は別格で悪い

```
Scan + FilterExpression で 1,000万件から 10件ヒット
  → 1,000万件分の RCU を消費（フィルタは読んだ後に捨てているだけ）
```

**テーブルが成長するほど毎回のコストが上がり続ける。**
Query は該当区画しか読まないので成長の影響を受けないが、Scan は真正面から受ける。

例外は「テーブルが小さいと保証されている」場合（マスタデータ、設定テーブルなど数百件）。そこは Scan で問題ない。

### 本当の分岐点は性能ではない

> **DynamoDB と RDS の選択は、性能の話ではなく「アクセスパターンをいつ決めるか」の話。**

| | いつアクセスパターンを決めるか |
|---|---|
| **RDS** | **実行時**。後から `WHERE` を足せる。インデックスも後から張れる |
| **DynamoDB** | **設計時**。キー設計 = アクセスパターンの確定。後から変えるのは実質マイグレーション |

RDB の「柔軟性」の対価が、スケール時の予測不可能性
（どんなクエリも受け付ける ＝ どんなクエリでも遅くなりうる）。
DynamoDB は柔軟性を前払いで捨てる代わりに、予測可能性を買っている。

だから **「リレーショナルに扱いたいケースが出てきて困った」は、使い方を間違えたのではなく
そもそも要件が合っていなかった**可能性が高い。
仕様が固まりきっていないプロダクトや、社内向けで後から「この軸でも見たい」が来る類のものは素直に RDS。

### シングルテーブル設計への率直な評価 → 推さない

**利点**
- 1回の Query で複数エンティティが取れる（親子を一発で）
- テーブル数が増えない

**欠点（こちらが重い）**
- **可読性が壊滅する** — `PK="USER#123"`, `SK="ORDER#2026-08-07"`, 属性が `GSI1PK`, `GSI2SK`。コンソールで生データを見ても何も分からない
- **GSI は20個まで** — アクセスパターンが増えると使い切って詰む
- **チームの学習コストが高い** — 設計者以外がメンテできなくなる
- **マイグレーションが地獄** — キー構造を変える ＝ 全アイテムの書き換え

Alex DeBrie（『The DynamoDB Book』著者）も近年は
「**ほとんどのアプリケーションはシングルテーブルにする必要はない**」と明言。
提唱者の Rick Houlihan も「特定のケース向け」と位置づけを戻している。

**エンティティごとにテーブルを分ける（マルチテーブル）で全く問題ない。**
特にチームが DynamoDB に習熟していないなら、そちらのほうが総合的に速い。

### 「リレーショナルに扱いたい」への処方箋（優先度順）

#### ① CQRS — 書き込みと読み取りを分離する ★実務の本命

```
アプリ → DynamoDB（書き込み、単純な読み取り）
              ↓ DynamoDB Streams
           Lambda
              ↓
    OpenSearch（全文検索・ファセット）
    Aurora / RDS（複雑なJOIN・集計）
```

**書き込みの強さは DynamoDB のまま、複雑なクエリは別のストアに投影する。**
Streams は変更をほぼリアルタイムで流すので、これが定石。
「DynamoDB で無理やり全部やる」より圧倒的に健全。

#### ② 分析系は S3 にエクスポート

`Export to S3`（PITR ベース）は **RCU を一切消費しない**。
エクスポートして Athena や Glue で集計する。日次・月次のレポートならこれで十分。
Scan で集計するくらいなら必ずこちら。コストが桁で違う。

#### ③ 素直に RDS に移す

**これが正解のことは普通にある。**
「DynamoDB を選んだから使い続けなければ」という理由で歪んだ設計を維持するのは、ほぼ常に損。

#### ④ Aurora DSQL を検討する

**「スケールと SQL の両立」を狙う新しい選択肢。**
DynamoDB を選ぶ動機が「スケールが読めない」だけだったなら、今は DSQL が答えになりうる。
→ `aurora-dsql/` 参照

### 採用判断のチェックリスト

1. **アクセスパターンを全部書き出せるか？** — 書けないなら RDS ← ★最重要
2. **それは今後1年変わらないか？** — 変わりそうなら RDS
3. **Item Collection のサイズは有界か？** — 無界なら設計をやり直す
4. **1つのキーにアクセスが集中しないか？** — するならバケット化かシャーディングが要る
5. **チームは DynamoDB を保守できるか？** — 微妙なら RDS

**1 と 2 で引っかかったら、性能の話をする前に RDS。**
性能で DynamoDB が必要になる規模に到達するプロダクトは、実際にはそう多くない。
