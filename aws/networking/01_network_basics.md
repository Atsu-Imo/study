# Phase 1: ネットワークの基礎概念

AWS 固有の話は出てこない。VPC の設定画面に出てくる用語のほぼすべてがここに由来する。

---

## 1-1. ネットワークの階層構造

### なぜ階層に分けるのか

「東京のAさんから大阪のBさんへ手紙を届ける」を考えると、関心事が分かれている。

- **手紙の中身**（何を伝えたいか）
- **宛先の住所**（どの家に届けるか）
- **配送経路**（どのトラックでどの集配所を経由するか）
- **物理的な運搬**（トラック、飛行機、自転車）

配送手段がトラックから飛行機に変わっても、手紙の書き方は変えなくていい。逆に手紙の中身が変わっても配送業者は影響を受けない。**各層が自分の関心事だけに責任を持ち、上下の層の詳細を知らない** — これがネットワークを階層に分ける理由。

だから「Wi-Fi でも有線でも同じアプリが動く」「HTTP でも SSH でも同じルータを通る」が成立する。

### TCP/IP の4階層モデル

実務ではこちらを使う。OSI 参照モデルは7階層だが、教科書的なモデルで実装とはズレがある。

| TCP/IP 4階層 | OSI | 役割 | 代表的なもの | 「宛先」の表現 |
|---|---|---|---|---|
| アプリケーション層 | L5-7 | アプリ同士の会話の中身 | HTTP, DNS, TLS | URL など |
| トランスポート層 | L4 | どのプロセスに届けるか、信頼性 | TCP, UDP | **ポート番号** |
| インターネット層 | L3 | どのマシンに届けるか、経路選択 | IP, ICMP | **IP アドレス** |
| ネットワークインターフェース層 | L1-2 | 隣の機器へ物理的に届ける | Ethernet, Wi-Fi | **MAC アドレス** |

重要なのは **層ごとに「宛先」の呼び方が変わる** という点。この3つ（MAC / IP / ポート）が何のためにあるのかを区別できると、以降がすべて楽になる。

> 会話で「L4 ロードバランサ」「L7 で振り分ける」と言うときは OSI の番号を指している。AWS だと NLB が L4、ALB が L7。

### カプセル化

データが層を降りるたびに、その層のヘッダが前に付く。

```
アプリ層        [ HTTPリクエスト                          ]
トランスポート層 [TCPヘッダ][ HTTPリクエスト               ]
インターネット層 [IPヘッダ][TCPヘッダ][ HTTPリクエスト     ]
リンク層        [Ethヘッダ][IPヘッダ][TCPヘッダ][ HTTP   ]
                    ↓ 物理的に送出
```

受信側は逆に、外側から順にヘッダを剥がして上の層に渡す。ルータは IP ヘッダまでしか見ない（見る必要がない）、スイッチは Ethernet ヘッダしか見ない、という役割分担もここから来る。

## 1-2. IP アドレスと CIDR

### IP アドレスの正体

IPv4 アドレスは **32bit の数値**。人間が読みやすいように8bitずつ4つに区切って10進数で書いているだけ。

```
192.168.1.10
 ↓ 各オクテットを2進数に
11000000 . 10101000 . 00000001 . 00001010
```

32bit なので全部で約43億通り。これが「IPv4 アドレス枯渇」の原因。

### ネットワーク部とホスト部

IP アドレスは **前半＝ネットワーク部（どの区画か）** と **後半＝ホスト部（その区画の何番目か）** に分かれる。電話番号の市外局番と加入者番号の関係に近い。

どこまでが前半かを示すのが **サブネットマスク**。CIDR 表記では `/24` のようにビット数で書く。

```
192.168.1.10/24

/24 = 先頭24bitがネットワーク部
11000000 10101000 00000001 | 00001010
└────── ネットワーク部 ──────┘ └ホスト部┘
      192.168.1              .10
```

つまり `192.168.1.0/24` は「`192.168.1.0` 〜 `192.168.1.255` の範囲」を意味する。

### CIDR の計算感覚

**ホスト部のビット数 n に対して 2^n 個のアドレス**が入る。暗記より、この対応表の感覚を持っておくほうが実用的。

| CIDR | ホスト部 | アドレス数 | 感覚 |
|---|---|---|---|
| `/8` | 24bit | 約1677万 | でかすぎる |
| `/16` | 16bit | 65,536 | VPC の標準的なサイズ |
| `/20` | 12bit | 4,096 | 大きめのサブネット |
| `/24` | 8bit | 256 | サブネットの標準的なサイズ |
| `/28` | 4bit | 16 | 最小クラス |
| `/32` | 0bit | 1 | 単一ホストの指定 |

覚え方: **数字が小さいほど範囲が広い**。`/24` を2つに割ると `/25` が2つ、4つに割ると `/26` が4つ。1増えるごとに半分になる。

**特殊な CIDR:**
- `0.0.0.0/0` — 全アドレス。「デフォルトルート」「どこからでも」の意味で頻出
- `10.0.1.5/32` — 単一の IP を指す書き方

### プライベート IP とパブリック IP

インターネット上で一意である必要があるのがパブリック IP。一方、組織内で自由に使ってよい範囲が RFC1918 で予約されている。

| 範囲 | CIDR | 使われ方 |
|---|---|---|
| `10.0.0.0` 〜 `10.255.255.255` | `10.0.0.0/8` | 大規模。AWS VPC で最も一般的 |
| `172.16.0.0` 〜 `172.31.255.255` | `172.16.0.0/12` | 中規模。Docker のデフォルトもここ |
| `192.168.0.0` 〜 `192.168.255.255` | `192.168.0.0/16` | 家庭用ルータでおなじみ |

プライベート IP はインターネットにそのままでは出られない（ルータが転送しない）。だから NAT が必要になる（→ 1-6）。

> **設計上の注意:** プライベート IP は「自由に使える」が、**後で他の組織や VPC と繋ぐときに範囲が重複していると詰む**。VPC Peering も Transit Gateway も CIDR 重複を許さない。オンプレや将来の買収先まで見越して重複しない番地を割り当てておく、というのが実務のセンス。

## 1-3. サブネットとルーティング

### サブネットに分ける理由

大きなネットワークをそのまま使わず、小さく区切る。理由は3つ。

1. **障害・ノイズの範囲を限定する** — L2 のブロードキャストは同一サブネット内にしか飛ばない
2. **セキュリティ境界にする** — 「DB のサブネットには Web サブネットからしか入れない」といった制御ができる
3. **管理単位にする** — 用途ごとに範囲が分かれていると把握しやすい

### ルーティングテーブル

ルータ（や OS）が持つ「この宛先ならこっちへ送れ」という対応表。

```
宛先                  次の転送先（ネクストホップ）
10.0.0.0/16      →   local（直接届く）
172.31.0.0/16    →   Peering接続
0.0.0.0/0        →   インターネットゲートウェイ
```

パケットを受け取ったら宛先 IP をこの表と照合し、マッチした転送先へ送る。それだけの仕組み。

### デフォルトゲートウェイと `0.0.0.0/0`

表にない宛先すべてを引き受ける「それ以外は全部こっち」のエントリが `0.0.0.0/0`。家庭の PC なら「Wi-Fi ルータへ」、AWS のパブリックサブネットなら「Internet Gateway へ」になる。

### ロンゲストマッチ（最長一致）

複数のエントリにマッチした場合、**より具体的な（プレフィックス長が長い）ほうが勝つ**。

```
宛先 10.0.5.20 のパケットが来た場合

0.0.0.0/0     → IGW          （マッチするが /0）
10.0.0.0/16   → local        （マッチする /16）
10.0.5.0/24   → Peering接続   （マッチする /24）← これが勝つ
```

この原則があるので、「基本はインターネットへ出すが、特定の範囲だけ VPN へ流す」といった設計が自然に書ける。逆に「なぜかトラフィックが意図しない方向へ行く」ときは、より長いプレフィックスのルートが存在していないかを疑う。

## 1-4. L2 と L3 — スイッチとルータ

### L2（データリンク層）: MAC アドレスとスイッチ

**MAC アドレス**は NIC（ネットワークカード）に焼き付けられた48bitの識別子。`00:1A:2B:3C:4D:5E` のように書く。IP アドレスが「住所」なら MAC アドレスは「機器のシリアル番号」に近く、原則として変わらない。

**スイッチ**は同一セグメント（＝同一サブネット）内で、MAC アドレスを見てフレームを転送する機器。「どのポートの先にどの MAC がいるか」を学習した表を持っている。

### ARP — IP から MAC を引く

通信相手を IP で指定しても、実際に送出するには MAC アドレスが要る。そこで **ARP**（Address Resolution Protocol）を使う。

```
A（10.0.0.5）が B（10.0.0.9）に送りたい

1. A: 「10.0.0.9 の人、MACアドレス教えて」とセグメント全体にブロードキャスト
2. B: 「私です。MACは 00:1A:2B:... です」とAに返す
3. A: そのMAC宛にフレームを送出（以後はキャッシュを使う）
```

ARP はブロードキャストなので同一サブネット内にしか届かない。ここが L2 の境界。

### L3（ネットワーク層）: ルータ

サブネットをまたぐ通信を担う。ルータは複数のサブネットに足を突っ込んでいて、ルーティングテーブルを見て次のサブネットへパケットを渡す。

### 同一サブネット内 vs サブネットをまたぐ通信

送信元は、宛先 IP が**自分と同じサブネットに属するか**をサブネットマスクで計算して判断する。

```
自分: 10.0.1.5/24（＝ 10.0.1.0〜10.0.1.255 が自分のサブネット）

宛先 10.0.1.20  → 同じサブネット
  → ARP で相手の MAC を引き、直接送る（ルータを通らない）

宛先 10.0.2.30  → 別のサブネット
  → デフォルトゲートウェイ（ルータ）の MAC 宛に送る
  → IPヘッダの宛先は 10.0.2.30 のまま、Ethernetヘッダの宛先だけルータ
```

ポイントは **IP アドレスは終点まで変わらないが、MAC アドレスは1ホップごとに書き換わる** こと。IP は「最終目的地」、MAC は「次に渡す相手」を表している。

> ここが理解できていると、「セキュリティグループは通っているのにルートテーブルで詰まっている」といった切り分けが自然にできるようになる。

## 1-5. トランスポート層 — TCP と UDP

### ポート番号

IP アドレスで「どのマシンか」までは決まるが、そのマシンでは複数のプロセス（Web サーバ、SSH、DB）が動いている。**どのプロセスに渡すか**を決めるのがポート番号（16bit = 0〜65535）。

| ポート | サービス |
|---|---|
| 22 | SSH |
| 53 | DNS |
| 80 | HTTP |
| 443 | HTTPS |
| 3306 | MySQL |
| 5432 | PostgreSQL |

通信は **「送信元IP:送信元ポート」と「宛先IP:宛先ポート」の4つ組**で識別される。クライアント側の送信元ポートは OS が自動で空きを割り当てる（エフェメラルポート、おおむね 32768〜60999）。

### TCP — 信頼性のある通信

接続を確立してからデータを送る。

**3ウェイハンドシェイク:**
```
クライアント              サーバ
    | ---- SYN --------->  |   「接続したい」
    | <--- SYN + ACK ----  |   「いいよ、こちらも接続したい」
    | ---- ACK --------->  |   「了解」
    |                      |
    |  ここから通信が成立    |
```

TCP が提供するもの:
- **順序保証** — 順番が入れ替わっても受信側で並べ直す
- **再送** — 届かなかったパケットを送り直す
- **フロー制御 / 輻輳制御** — 相手や経路の処理能力に合わせて送信量を調整

代わりにオーバーヘッドがある。接続の確立に往復が必要なので、レイテンシの大きい経路では最初の1往復が効いてくる。

### UDP — 速さ優先

接続を確立せず、投げっぱなし。順序保証も再送もない。その代わり軽い。

DNS（1往復で終わる）、動画/音声のリアルタイム配信（再送するより次のフレームを送るほうが良い）、QUIC（HTTP/3 の土台。信頼性は UDP の上に自前で実装している）などで使われる。

### 「コネクションの状態」とは

TCP は「今この接続がどの段階にあるか」（確立中 / 確立済み / 切断中）を両端が覚えている。この**状態を機器側でも追跡するかどうか**が、次のステートフル / ステートレスの分岐になる。

なお UDP にはコネクションの概念がないが、ファイアウォールは「さっき出ていった通信の対」を一定時間覚えることで疑似的にステートフルに扱う。

## 1-6. NAT

### NAT が生まれた理由

IPv4 の43億アドレスでは足りない。そこで「組織内ではプライベート IP を使い、インターネットに出る瞬間だけパブリック IP に書き換える」という方式が生まれた。

### NAPT（IP マスカレード）

単純な NAT は 1対1 の変換だが、実際に広く使われているのは **ポート番号も併せて書き換えることで、1つのパブリック IP を多数の端末で共有する** 方式。厳密には NAPT だが、口語ではまとめて NAT と呼ぶ。

```
社内                     NATルータ                    インターネット
10.0.1.5:51000  ──→  [変換表]  ──→  203.0.113.1:40001 ──→ サーバ
10.0.1.9:52000  ──→            ──→  203.0.113.1:40002 ──→ サーバ

変換表
10.0.1.5:51000 ⇔ 203.0.113.1:40001
10.0.1.9:52000 ⇔ 203.0.113.1:40002
```

戻りのパケットは、宛先ポート（40001 か 40002 か）を見てどちらに返すか判断する。

### なぜ NAT 越しには外から繋げないのか

変換表のエントリは **内側から外へ出た瞬間に作られる**。外から突然パケットが来ても、変換表に対応がないので誰に渡せばいいか分からず破棄される。

これは制約であると同時に、「内側からの通信だけが成立する」という素朴なセキュリティ効果も生んでいる。

> **AWS との対応:** NAT Gateway はまさにこれ。プライベートサブネットの EC2 が外部 API を叩けるが、外部からその EC2 に接続はできない、という挙動の理由がここにある。

### SNAT と DNAT

| 種類 | 何を書き換えるか | 用途 |
|---|---|---|
| SNAT（送信元 NAT） | 送信元 IP | 内 → 外。上記の NAT Gateway |
| DNAT（宛先 NAT） | 宛先 IP | 外 → 内。ポートフォワード、ロードバランサ |

ロードバランサは「宛先を実サーバに書き換える」という意味で DNAT の一種と捉えると腑に落ちる。

## 1-7. DNS

### 名前解決の流れ

`www.example.com` を IP アドレスに変換する仕組み。ルートから順に「その先を知っている人」を辿る。

```
クライアント
   │ www.example.com ください
   ↓
[キャッシュDNSサーバ（リゾルバ）]
   │ ① .com を管理してるのは誰？
   ↓  → [ルートサーバ] 「.com のサーバはこれ」
   │ ② example.com を管理してるのは誰？
   ↓  → [.com TLDサーバ] 「example.com のサーバはこれ」
   │ ③ www.example.com の IP は？
   ↓  → [example.com 権威サーバ] 「93.184.216.34」
   │
   ↓ 93.184.216.34 です（結果をTTLの間キャッシュ）
クライアント
```

リゾルバがこの往復を代行し、結果をキャッシュする。だから2回目以降は速い。

### 主なレコードタイプ

| タイプ | 意味 |
|---|---|
| A | ホスト名 → IPv4 アドレス |
| AAAA | ホスト名 → IPv6 アドレス |
| CNAME | 別名 → 正式名（別の名前へ転送）。ゾーン頂点には置けない |
| NS | このゾーンを管理する権威サーバ |
| MX | メールの配送先 |
| TXT | 任意の文字列。ドメイン所有権証明や SPF に使う |

> `security-agent/` の Q1 でやったドメイン所有権の検証は、この TXT レコードの仕組みを使っている。

### TTL とキャッシュ

各レコードには TTL（キャッシュしてよい秒数）が付く。TTL が長いと問い合わせが減って効率的だが、**変更が世界中に反映されるまで最大 TTL 秒かかる**。

DNS でフェイルオーバーする設計が「切り替えが遅い」と言われるのはこれが理由。切り替え予定があるなら事前に TTL を短くしておく、というのが定石。

### 内部 DNS と分割ホライズン

同じ `api.example.com` でも、社内から引けばプライベート IP、外から引けばパブリック IP を返す、という構成ができる。これを **分割ホライズン DNS** と呼ぶ。

VPC 内の名前解決や Route 53 Private Hosted Zone はこの考え方に基づいている（→ Phase 2-6）。

## 1-8. ファイアウォールとステート

### パケットフィルタリングの基本

通過するパケットを見て、許可するか破棄するかを決める。判断材料は基本的にこの4つ組。

- 送信元 IP
- 宛先 IP
- プロトコル（TCP / UDP / ICMP）
- ポート番号

### ステートレス vs ステートフル

**ここが VPC を理解する上で最重要の概念。** セキュリティグループとネットワーク ACL の違いはこれに尽きる。

**ステートレス** — 1パケットずつ独立に判定する。過去の通信を覚えていない。

```
[内 10.0.1.5] ──── HTTPリクエスト ────→ [外 203.0.113.9:443]
   ↑ 出ていく通信を許可するルールが必要

[内 10.0.1.5] ←──── HTTPレスポンス ──── [外 203.0.113.9:443]
   ↑ 戻りの通信も別途、明示的に許可するルールが必要 ★
```

戻りのパケットは送信元ポートがエフェメラルポート（32768〜）なので、その範囲を許可するルールを書かなければならない。設定が煩雑になる。

**ステートフル** — 「行った通信」を記録し、その戻りは自動的に許可する。

```
[内 10.0.1.5] ──── HTTPリクエスト ────→ [外]
   ↑ 出ていく通信を許可するルールだけ書けばよい
   （この時点で「この通信の戻りは通す」と記憶される）

[内 10.0.1.5] ←──── HTTPレスポンス ──── [外]
   ↑ ルール不要。自動的に通る ★
```

| | ステートレス | ステートフル |
|---|---|---|
| 戻りの通信 | 明示的に許可が必要 | 自動的に許可 |
| リソース消費 | 少ない | 接続表を持つので多い |
| 設定の分かりやすさ | 煩雑 | 直感的 |
| AWS での対応 | ネットワーク ACL | セキュリティグループ |

> **これを押さえると Phase 2-5 が一瞬で終わる。**
> 「セキュリティグループでアウトバウンドを絞ったら通信できなくなった」「ネットワーク ACL でインバウンドだけ許可したのに応答が返ってこない」といった典型的なハマりは、すべてこの違いから来る。

### 許可リストと拒否リスト

- **セキュリティグループ** は許可ルールしか書けない（書いていないものは通らない）
- **ネットワーク ACL** は許可と拒否の両方が書け、番号順に評価して最初にマッチしたルールが適用される

「特定の IP だけをブロックしたい」はセキュリティグループでは表現できず、ネットワーク ACL の出番になる — という使い分けの根拠がここにある。

## Phase 1 のまとめ — VPC の用語との対応

| Phase 1 の概念 | VPC での姿 |
|---|---|
| CIDR / サブネットマスク | VPC CIDR、サブネット CIDR |
