# networking Q&A

記録開始日: 2026-08-10

## Q1: IPアドレスとMACアドレスの関係がわからない。IPアドレスとMACアドレスは一対一？

**一対一ではない。** 別レイヤの別概念であり、対応関係は「その瞬間・そのセグメント内でだけ成立する一時的な紐付け」でしかない。

### 正体が違う

| | MAC アドレス | IP アドレス |
|---|---|---|
| 誰が付ける | NIC の製造元（またはハイパーバイザ） | 管理者 / DHCP / AWS |
| 何に紐づく | 物理的な口（NIC） | ネットワーク上の論理的な位置 |
| 変わるか | 原則変わらない | 引っ越せば変わる |

MAC は「機器のシリアル番号」、IP は「今どこの住所にいるか」。マイナンバーと現住所の関係に近い。

### 一対一が崩れるパターン

- **1つの MAC に複数の IP（1 : N）** — セカンダリ IP。AWS では ENI 1つに複数のプライベート IP を割り当てるのがこれ。MAC は1つのまま
- **同じ IP が別の MAC に移る** — DHCP リースの回し、フェイルオーバーでのセカンダリ IP 付け替え、EIP の付け替え。IP はそのままで MAC だけ変わる
- **IP がユニークとは限らない** — プライベート IP は組織ごとに自由。別 VPC にも同じ `10.0.1.5` が存在しうる（CIDR 重複問題の根）
- **MAC もユニークとは限らない** — 仮想 NIC の MAC はソフトで生成・変更できる

### 最重要: 紐付けはローカルかつ一時的

```
A(10.0.1.5) → ルータ → B(10.0.2.30)

A が送出するフレーム:
  IP 宛先  = 10.0.2.30      ← 最終目的地
  MAC 宛先 = ルータのMAC     ← 次に渡す相手

ルータが転送するフレーム:
  IP 宛先  = 10.0.2.30      ← 変わらない
  MAC 宛先 = B のMAC         ← 書き換わる
```

同じ `10.0.2.30` でも、対応する MAC は見る場所によって違う。グローバルな対応表は存在しない。

さらに、送信元が持っている対応は ARP で引いた結果を数十秒〜数分キャッシュしているだけで恒久的ではない。IP が別マシンに移ってもキャッシュ失効後に追従できる。この「一時的な紐付けを信じている」性質を突くのが ARP スプーフィング。

### 唯一「一対一っぽく」見える条件

同一サブネット内・ある一時点では、1つの IP に対応する MAC は1つだけでなければならない（2つあると ARP 応答が競合＝IP アドレス重複エラー）。この「局所的・瞬間的な一意性」を「恒久的な一対一」と読み違えやすい。

### AWS での姿

`ENI = 仮想 NIC = MAC アドレス1つ` と考えると整理しやすい。

- ENI に IP を複数付ける → 1 MAC : N IP
- ENI ごとインスタンス間で付け替える → MAC と IP がセットで移動
- セカンダリ IP だけ別 ENI に移す → IP だけ移動、MAC は変わる

「EC2 を作り直したのに同じ IP でアクセスできる」「ENI を付け替えたら設定を引き継げる」はこの分離があって成立している。

## Q2: トランスポート層はデータの送り元から送り先まで統一されている？ ルータまで／スイッチまでで違ったりしない？

**原則としてトランスポート層は端から端まで一貫していて、途中の機器は触らない。** ただし現代のネットワークでは NAT とロードバランサがこの原則を破っている。

### どの層が「端から端」でどの層が「1ホップごと」か

| 層 | スコープ | 途中の機器は |
|---|---|---|
| L2 (Ethernet) | 1ホップごと | ホップのたびに剥がして付け直す |
| L3 (IP) | 端から端（アドレスは不変） | 見て転送先を決める。TTL は減らす |
| L4 (TCP/UDP) | 端から端 | 本来は見ないし触らない |
| L7 (HTTP) | 端から端 | 見ない |

ルータがやっているのはこれだけ:

```
受信フレーム [Ethヘッダ][IPヘッダ][TCPヘッダ][ HTTP ]
                ↓ 剥がす      ↓ 見る    ↓ 素通り
送出フレーム [新Ethヘッダ][IPヘッダ][TCPヘッダ][ HTTP ]
              作り直す      TTL-1     そのまま
```

TCP ヘッダから内側は、ルータにとって中身のわからないペイロード。開封しない。

### なぜそうなっているか — エンドツーエンド原則

TCP の状態（シーケンス番号、再送待ち、輻輳ウィンドウ、コネクション状態）を持っているのは**両端の2台だけ**。途中のルータは一切持っていない。

- 途中でパケットが落ちても再送するのは送信元。ルータは再送しない
- 3ウェイハンドシェイクの相手は最終的な通信相手であって途中のルータではない
- 経路が途中で変わっても TCP コネクションは切れない

「ネットワークの中心は単純に、賢さは端に置く」という設計思想。

### 例外

**① NAPT（NAT Gateway）— 送信元ポートを書き換える**

```
10.0.1.5:51000  →  203.0.113.1:40001
                        ↑ ポート番号（L4）が書き換わる
```

TCP チェックサムは IP アドレスも含めて計算されるため、NAT は TCP ヘッダのチェックサムも再計算して書き直している。「ルータは L3 までしか見ない」が破れる典型例。

**② L4 ロードバランサ（NLB）** — 振り分けのためにポート番号を参照し、必要なら書き換える。

**③ L7 ロードバランサ / プロキシ（ALB, CloudFront）— TCP を2本に分断する**

ALB はクライアントとの TCP をいったん終端し、バックエンドへ別の TCP コネクションを新しく張る。

```
クライアント ══TCP①══ [ALB] ══TCP②══ EC2
             別コネクション   別コネクション
```

- 送信元 IP も引き継がれない → バックエンドから見た送信元は ALB
- クライアント IP を知るには `X-Forwarded-For`（L7）で運ぶしかない
- TLS も ALB で終端される
- 「ALB 経由だとアクセスログのクライアント IP が全部 ALB になる」の理由

**④ MSS クランプ** — 途中の機器が TCP ヘッダのオプション（MSS 値）を書き換える。VPN 経由で「ping は通るのに HTTP が固まる」の原因。

### プロトコルの種類自体は絶対に変わらない

TCP で送ったものが途中で UDP になることはない。IP ヘッダの Protocol フィールド（6=TCP, 17=UDP, 1=ICMP）は書き換わらない。セキュリティグループで「TCP 443 を許可」と書けば経路のどこでもその意味が通じるのはこのため。

### まとめ

- MAC は1ホップごとに必ず書き換わる（仕様）
- IP とポートは原則 端から端まで不変。ただし NAT / LB という意図的に破る装置がある
- TCP コネクションそのものは原則1本。ただし L7 プロキシは2本に切る

トラブルシュート時は「今どの装置がどの層まで触っているか」を思い浮かべる。IP が変わっているなら NAT か LB、コネクションが切れているなら L7 終端がいる。
