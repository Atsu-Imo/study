# RDS / IAM DB認証 Q&A

記録日: 2026-07-03

## Q1: IAM DB認証はコネクションを作るたびに認証が走る？コネクションは使い回せない？

認証が走るのは **「新しいコネクションを張る瞬間」だけ**。コネクションは使い回せるし、使い回すのが正解。

### 仕組み
IAM DB認証はパスワードの代わりに**一時トークン**を使う方式。

1. AWS認証情報から `generate-db-auth-token` でトークンを生成（**有効期限15分**）
2. そのトークンを「パスワード」としてDBに接続
3. **接続が確立したら、それ以降トークンの期限は無関係**。セッションは張りっぱなしのまま生き続ける

認証コストがかかるのは接続確立のハンドシェイク時のみ。開きっぱなしのコネクションは再認証しない。トークンが15分で切れても既存接続は切れない（次に「新規接続」するときだけ新しいトークンが要る）。

### だから使い回す（コネクションプール）
- 長寿命のプールを持てば認証は最初の数本を張るときだけ。以降はプール内接続を再利用 → 認証はほぼ発生しない。
- 逆に困るのが Lambda 等の「毎回新規接続を開いて捨てる」パターン。接続の作り直し＝毎回認証になる。

### 背景（2026-07-01のニュース）
「RDS Enhances IAM Database Authentication with Connection Rate Scaling」がこの話。IAM認証には歴史的に「**新規接続/秒**の上限」があり（従来 MySQL で ~200 new connections/sec 程度）、接続を高頻度で開閉するワークロードだとここでスロットリングしていた。今回それが緩和された。

### 実務での定石
- アプリ側でコネクションプールを持つ（＝そもそも張り直さない）
- サーバーレス等で使い回しが難しいなら **RDS Proxy** を挟む。Proxyがウォームな接続プールを維持し、IAM認証やフェイルオーバーも肩代わりする。

## Q2: 「開閉頻度が高い」ってどういう状況？それをせざるを得ないってこと？

高頻度で開閉「せざるを得ない」のは、**コンピュート側が短命 or 大量スケールする構成**に限られる。普通の常駐型サーバーではまず起きない。

### 開閉頻度が高くなる典型
1. **Lambda / サーバーレス**（本命）— 実行環境が使い捨てで、同時に数百〜数千インスタンスに水平スケール。各インスタンスが自前で接続を張る → 全体として接続の生成・破棄が絶えず発生。
2. **バッチ / cronジョブ / CLI** — プロセスが起動→接続→処理→終了を繰り返す。プロセス寿命が短く接続も短命。
3. **リクエスト毎プロセス型（古典的PHP-FPMなど）** — 1リクエスト＝1接続で閉じる素朴な作り。
4. **コンテナの急激なオートスケール** — Pod/タスク起動の度に新規接続の波が来る。

対して **Goの常駐サービス等の長寿命プロセス**は、起動時にプールを張ってプロセスが生きてる間ずっと使い回すので churn はほぼゼロ。この問題に無縁。

### 「せざるを得ない」は半分正しい
- Lambdaでは構造的にある程度避けられない。
- 緩和策として「接続をハンドラの外で宣言」すれば**同じウォーム環境の中では使い回せる**。
- ただし**数千の並行インスタンス間ではプールを共有できない**し、コールドスタートでは新規に張る。だから全体で見ると churn は残る。

### 本質的なジレンマ
> DB側は同時接続数に上限がある（Postgres/MySQLは特に）。なのにサーバーレスは横に無限に増える。→ 素直に繋ぐと「churnで認証スロットリング」か「接続数上限を食い潰す」のどちらかにぶつかる。

### だからProxyを挟む
**RDS Proxy（や PgBouncer）** がこの矛盾を吸収する。
- アプリ側の大量・短命な接続を Proxy が受け止め、
- DB側には少数・安定したウォームな接続プールだけを維持する。

「churnせざるを得ない層」と「churnされたくないDB」の**間に緩衝材を置く**のが定石。Connection Rate Scaling は、緩衝材なしでも耐えられる上限を引き上げた改善という位置づけ。
