### 📝 深掘りメモ（2026-06-23）— AWS Lambda MicroVMs

#### 0. 結論：「Lambdaの新OS」ではない
- **MicroVM = OSではなく、起動が速い極小の仮想マシン（VM）そのもの**。中身では普通にゲストOS（Linuxカーネル）が動いている＝「OSを丸ごと閉じ込めた箱」。
- Lambda MicroVMs = 「Lambdaの実行単位を、関数1回きりではなく**ユーザー/セッションごとに隔離されたVMサンドボックス**として貸す新プリミティブ」。
- 基盤は **Firecracker**（Rust製のVMM。従来のLambdaも元々これで動作）。

#### 1. なぜ「VM隔離」が重要か（隔離の強さ）
```
プロセス分離 → OSのプロセス境界（カーネルは共有）
コンテナ     → namespace/cgroup（ホストカーネルを共有）
MicroVM      → 仮想ハードウェア境界（各VMが専用カーネルを持つ）
```
- 公式の売り＝ **no shared kernel / no shared resources**。コンテナはホストカーネル共有のためカーネル脆弱性で隣テナントに波及しうるが、MicroVMはカーネルごと分離。
- → **信頼できないコード（他人やAIが書いたコード）を1人ぶんずつ完全隔離**できる。

#### 2. 従来Lambda関数との違い
| | 従来の Lambda 関数 | Lambda MicroVMs |
|---|---|---|
| 実行モデル | イベント→1回実行→終了 | セッション単位でVMを起動し**生かしておける** |
| 状態 | 基本ステートレス | **suspend/resume で状態保持（最大8時間）** |
| 想定 | APIバックエンド/イベント処理 | **ユーザー/AI生成コードのサンドボックス実行** |

- 「最大8時間 suspend/resume」が肝。対話的にコードを打ち込む環境を「1セッション＝1VM」として維持するための機能。

#### 3. 想定ユースケース（＝マルチテナントで他人のコードを動かす系）
- ブラウザ上のIDE/REPL、データ分析プラットフォーム（任意クエリ実行）
- **コーディングアシスタント / AIエージェントが生成したコードの実行**
- 脆弱性スキャナのような「怪しいものを動かす」基盤
- 東京（ap-northeast-1）含むリージョンで提供。

### 📝 深掘りメモ（2026-06-23）— AWS WAF と Network Firewall の棲み分け＋今回の更新

#### 0. 結論
- WAFとNetwork Firewallは**層が違う**ので competitor ではなく役割分担。**単一Webサービスを守るならWAFで十分**で、Network Firewallは「VPC全体の通信を関所で検査したい」ときに足すもの。

#### 1. 棲み分け（どこを守るか）
| | AWS WAF | AWS Network Firewall |
|---|---|---|
| 守る層 | **L7（HTTP/HTTPS）** | **L3/L4（IP/ポート/TCP）＋一部L7** |
| 取付先 | CloudFront/ALB/API Gateway/AppSync | **VPC（サブネット境界）** |
| 見るもの | HTTPリクエストの中身 | VPC出入りの**ほぼ全パケット/コネクション** |
| 典型ルール | SQLi/XSS、レート制限、Bot対策、IP遮断 | ドメイン/IP許可遮断、IPS、**egress制御** |
| エンジン | AWS独自 | **Suricata**（OSS IDS/IPS）互換 |
| 方向 | 主にインバウンド | **アウトバウンド制御が得意** |

- ざっくり：**WAF = 悪意あるHTTPリクエストを止める** / **Network Firewall = ネットワーク全体の通信を検査する関所（HTTP以外も全部）**。

#### 2. Network Firewall を使うケース（WAFでは届かない要件）
- **アウトバウンド（egress）制御**：「このVPCは特定ドメイン/IPにしか外部通信させない」。データ持ち出し・C2通信遮断。WAFでは不可。
- **HTTP/HTTPS以外の検査**：任意TCP/UDP、SSH、DBポート等。
- **複数VPC/オンプレ横断の集中検査**（Inspection VPC × Transit Gateway）。
- **IDS/IPS・コンプライアンス要件**（Suricataシグネチャ）。
- **FQDN（ドメイン名）ベースの許可リスト**。

#### 3. 今回の更新＝ステートフルのデフォルトアクションが "Drop established（server-directed only）" 寄りに
- **背景の問題**：strict-order＋default-deny構成だと「許可ルールに当たらないパケットは全ドロップ」。だがTCPはアプリ層の許可ルールが効く前に**握手（SYN/ACK）やフロー制御パケット**が飛び、それまで落として**コネクションが確立できない/切れる**。回避には下位層を通すルールを自前追加が必要で面倒だった。
- **"Drop established" の挙動**：クライアント→サーバの**確立済み接続上のパケット**だけドロップ対象にし、**L3/L4の握手は通す**＋**サーバ→クライアントの戻り通信も通す**。→ アプリ層の許可ルールだけ書けば下位層/戻りは自動で通る。
- **意味**：この挙動がデフォルト寄りになり、新規ポリシーで余計な握手許可ルール無しで**正当な通信が誤ってドロップされにくく**＝接続の信頼性向上。

#### 4. 自分への影響
- **WAFしか使っていない → 影響なし**（Network Firewallの設定の話）。
- Network Firewall利用中なら：✅ default-deny構成が組みやすくなる ／ ⚠️「デフォルト挙動が変わる」ので**ステートフルのデフォルトアクション設定を一度確認**（特にstrict-order/アラート設定）。
- 残る注意点：確立後にどの許可ルールにも当たらないパケットが来るとそのコネクション全体を落とすため、**許可ルールの網羅性は引き続き要設計**。
