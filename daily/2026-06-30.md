### 🧠 今日の深掘りメモ

#### pnpm 大量 CVE 群（2026-06-26〜27 / 約16本）
- 共通の根っこは「**信頼できない lockfile（`pnpm-lock.yaml` / `pnpm-workspace.yaml`）を信頼してしまう**」こと。攻撃面が lifecycle スクリプトではなく**インストール・解決ロジックそのもの**にある。
- そのため定番防御の **`--ignore-scripts` を付けても防げない**のが今回の肝。例：CVE-2026-55700 は `configDependencies` の `../` で `node_modules/.pnpm-config` 外に任意ファイル/symlink を作成、スクリプト無効でも `pnpm install` だけで発火。
- 系統：path traversal（55700 等）/ integrity 検証バイパス（50021, 50573, 48995）/ git 引数インジェクション（50014）/ シークレット漏洩（50017, 55180）。
- 危険地帯は **CI が信頼できない PR を `pnpm install` する構成**（フォーク PR ビルド等）。
- **対応：pnpm `10.34.2` / `11.5.3` 以降へ更新**。`--ignore-scripts` は今回の防御には不十分と認識する。
- 出典: [GitHub Advisory DB (pnpm)](https://github.com/advisories?query=pnpm) / [CVE-2026-55700](https://cvereports.com/reports/CVE-2026-55700)

#### S3 server access log の新配信先（CloudWatch Logs / S3 Tables）
- **server access log = S3 へのデータアクセス1件1件の記録**（誰が・いつ・どのオブジェクトに・どの操作・結果）。CloudTrail（API 管理操作）とは別物。
- 従来は**別 S3 バケットに生テキストがバラバラ配信**され、数時間遅れ・分析は Athena で自前構築が必要だった。
- 新たに **(1) CloudWatch Logs へ直接配信**（即 SQL クエリ・監視）、**(2) S3 Tables = Apache Iceberg 形式へミラー**（Athena/Redshift で本格分析、**追加コスト無料**）。即時調査と大規模分析の両取り。
- 保持期間は CloudWatch ロググループの retention に揃う。「無料」は S3 Tables 連携部分の話（CloudWatch Logs 自体は取り込み・保存課金あり）。
- 出典: [CloudWatch Logs S3 Tables Integration](https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/s3-tables-integration.html)

#### CloudTrail と S3 server access log の使い分け
- CloudTrail は2層：**管理イベント**（設定操作・デフォルトON・無料）と**データイベント**（オブジェクト操作・要有効化・**リクエスト課金**）。
- 「オブジェクトに誰がアクセスしたか」を取る手段が **CloudTrail データイベント** と **server access log** で重複するのが混乱の元。
- **CloudTrail データイベント**：完全性保証・IAM 主体が明確・数分・EventBridge 連携 → **監査/コンプライアンス/リアルタイム検知**向き（ただし高コスト）。
- **server access log**：ベストエフォート（稀に欠落）・HTTP 詳細（ステータス/転送量/レイテンシ/リファラ）・安い → **アクセス傾向・運用分析**向き。
- 覚え方：設定変更を追う→管理イベント / 機密データ監査→データイベント / 安く広く傾向分析→server access log。両者併用も一般的。
