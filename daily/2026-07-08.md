## 🔬 深掘りメモ: better-auth 脆弱性クラスタ（2026-07-07公開）

**結論:** 全12件、すべて **`better-auth@1.6.11`**（+ `@better-auth/*` プラグイン）で修正済み。テーマは一貫して「**自前 OAuth/OIDC プロバイダ実装の落とし穴**」。

### 深刻度順の主なCVE
- **CVE-2026-53513 — `@better-auth/sso` SSRF** (`CVSS 9.6 / Critical`)
  - `POST /sso/register`・`/sso/update-provider` で `skipDiscovery: true` の時、`userInfoEndpoint`/`tokenEndpoint`/`jwksEndpoint` の URL を origin 検証なしで登録可能→OIDCコールバックでサーバーがフェッチし応答がプロフィールに反映される非ブラインドSSRF。
- **CVE-2026-53512 — リフレッシュトークンのリプレイ** (`CVSS 9.1 / Critical`)
  - レガシー `oidcProvider()`/`mcp()` が refresh_token グラント時に confidential client の `client_secret` を検証しない（RFC 6749 §6 違反）。code グラント側は検証しているのでリグレッション。refresh token 1つで失効まで無期限にアクセストークン再発行。
- **CVE-2026-53516 — OAuth auto-link でのアカウント乗っ取り** (`CVSS 8.3 / High`)
  - `handleOAuthUserInfo` がプロバイダの `email_verified:true` だけで暗黙リンクを許し、ローカル側 `emailVerified` を確認しない。被害者メールで事前登録→OAuthログインで乗っ取り。Microsoft "nOAuth" (2023)・Sign in with Apple (2020) と同型。
- **CVE-2026-53514** — organization プラグインで未検証メール一致だけで組織招待を受諾可（High）。
- **CVE-2026-53517 / -53518** — リフレッシュトークンローテーションのトークンファミリー分岐／認可コードの同時引き換えレース（High）。
- **GHSA-9h47** 暗号デフォルトが緩い（`alg=none`・平文PKCE許容）、**GHSA-86j7** `javascript:` リダイレクトURIで保存型XSS、**GHSA-j8v8** 非組織SCIMでプロバイダ乗っ取り（いずれもHigh）。

### 持ち帰り: 自前で OAuth/OIDC を実装する際のチェックリスト（言語非依存）
1. プロバイダの主張（`email_verified` 等）を鵜呑みにせず、ローカルの検証状態と突き合わせる（nOAuth対策）。
2. refresh/token エンドポイントでも client 認証を必ず行う（code グラントだけ検証して refresh を素通しにしない）。
3. 登録された外部URLは必ず origin 検証。discovery スキップ設定は SSRF の温床。
4. トークンローテーションは並行リクエスト前提で設計（単発想定のレース検知は破られる）。
5. 安全なデフォルト: `alg=none` 禁止、PKCE は S256 必須、リダイレクトURIスキームを許可リスト化。

> 補足: これらは「自前IdP（＝OP / Authorization Server）」実装のバグに集中。IdP側が実装する部品は authorization / token / userinfo / jwks / discovery エンドポイント + client登録・トークン発行/署名/失効。自前で建てるなら Ory Hydra / Keycloak / dex 等の実績ある実装が推奨。今回は使用していないため影響なし。

## 🔬 深掘りメモ: CloudWatch Application Signals — Service Events（2026-07-07）

**何か:** Application Signals は AWS ネイティブの **APM**（ADOT / OpenTelemetry で計装するとレイテンシ・エラー率・依存関係マップを自動可視化。Datadog APM の AWS版イメージ）。今回の **Service Events** は、追加コードなしで **①Errors（例外スナップショット）②Performance anomalies（レイテンシイベント）③Deployment events（デプロイ）** を自動キャプチャする機能。

**価値:** コンソールで同一タイムライン上にデプロイ境界とエラー/レイテンシ悪化が並ぶ → **「このデプロイで例外が入った」を即断**できる（deployment marker による回帰検知）。リリース直後のスモークチェックやロールバック判断の材料に向く。

### 対応環境（環境レベルでは EC2 / ECS / Lambda いずれも可）
| 環境 | 対応 | 補足 |
|---|---|---|
| Amazon EKS | ✅（最も手厚い） | サービス名・クラスタ名を自動検出 |
| Amazon ECS | ✅ | 名前は手動指定 |
| Amazon EC2 | ✅ | CloudWatchエージェント + ADOT。名前は手動指定 |
| AWS Lambda | ✅ | 専用手順あり |
| ネイティブ Kubernetes | ✅ | — |

- テスト済みは EKS / ECS / EC2。リージョンは Canada West (Calgary) を除く全商用リージョン。
- Change Events（デプロイ相関）はインフラ側リソース単位でも取得: ASG / EKSクラスタ・ワークロード / ECSクラスタ・サービス / ELB / Lambda関数 / BedrockAgentCore。

### ⚠️ 言語制約（Goユーザーとして重要）
- Application Signals の自動計装がサポートするのは **Java / Python / Node.js / .NET のみ。Go は非対応**。
- → 環境（EC2/ECS/Lambda）としては使えるが、**Go アプリの APM（自動トレース/例外スナップショット）はそのままは乗らない**。Go の可観測性は ADOT Collector + X-Ray + 手動 OpenTelemetry 計装で別途組む必要あり（詳細は後日調査）。
- ただし **ECSサービスやLambda関数のデプロイイベント自体は言語非依存で記録される**（アプリ内部の例外情報だけが計装依存）。

## 🔬 深掘りメモ: GLM 5.2 と "AI margin collapse"（2026-06-13リリース）

**何か:** 中国 **Zhipu AI（Z.ai）** のフラッグシップLLM。GLM-5ファミリーの最新版。**Claude Opus / GPT-5.5 に迫る品質を、桁違いに安く、オープンウェイト（MIT）で出した**のが話題の核心。

### モデル仕様
- **約750B の Sparse MoE**、トークンあたりアクティブ約40B（規模の割に軽い）。
- **コンテキスト100万トークン**、`IndexShare` スパースアテンションで1M推論コストを抑制。
- 出力最大 **131,072トークン**（マルチファイル diff を一発生成可）。
- コーディング・推論・**エージェント（ツール呼び出し/長期プランニング）**特化。ウェイトは **MIT**（自前ホスト可）。

### 性能・価格
- Artificial Analysis Intelligence Index **51**：**オープンウェイト世界1位**、全体4位（Fable 5=60, Opus 4.8=56, GPT-5.5=55 に次ぐ）。
- 弱点: **ビジョン非対応・Web検索が弱い・推論が遅め**。

| モデル | 入力/出力（$/1Mトークン） |
|---|---|
| **GLM 5.2** | **$1.40 / $4.40** |
| Claude Opus | $5 / $25 |
| GPT-5.5 | $5 / $30 |

出力で **Opus の約1/6**。トークン消費増を割り引いても同等品質を50%以上安く出せる（記事著者評）。

### "AI margin collapse" の論点
- フロンティアラボ（OpenAI/Anthropic）は推論の**高粗利（〜90%）**前提のビジネスモデル。
- そこへ**同等品質・激安・オープンウェイト**の GLM 5.2 が登場。
- Z.ai も Fireworks も **OpenAI/Anthropic 互換エンドポイント**提供 → **乗り換えコストほぼゼロ**。
- → 高マージン前提が崩れる、というのが主張（Part 2 で業界影響を予定）。

### 実務での意味
- バッチ処理・大量コード生成・長コンテキスト解析など「品質は要るが Opus 級の値段は不要」なワークロードで互換エンドポイント経由で試す価値。
- 判断軸: ビジョン不要 / レイテンシ許容か / データを中国系プロバイダに投げてよいか（センシティブなら**オープンウェイトを自前 or Fireworks でホスト**）。
