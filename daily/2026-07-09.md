### AWS Security Hub Network Scanning
- **位置づけ**: 独立サービスではなく Security Hub の capability のひとつ。Essentials に追加料金なしで含まれる。使う = Security Hub（新コンソール v2 / `console.aws.amazon.com/securityhub/v2/home`）を有効化してこの capability を ON にする、ということ。
- **従来との違い**: VPC Reachability Analyzer / Network Access Analyzer / 既存の network reachability findings はすべて **設定を机上解析**して「到達しうるか（could be reachable）」を出す。Network Scanning は **AWS が実際にインターネット側からプローブを打って「実際に到達したか（actual reachability）」** を確認する。開いていても listen していなければ攻撃面でない／SG を絞ったつもりでも別経路で刺さる、を実測で捌ける。
- **対象と出力**: パブリック IP・仮想マシン・ロードバランサー（AWS + Azure）。到達できたポートごとに finding が1件立ち、裏で動くサービスの証拠が付く。Security Hub の用語だと、これは Reachability trait を持つ signal になり、他の signal（例: Inspector の脆弱性）と相関して exposure finding（例:「インターネット到達可能 かつ 高悪用性の脆弱性を持つ EC2」）を生成する。
- **有効化**: 単一アカウントは v2 コンソールの Get started →「Enable all / Customize capabilities」→ Regions 選択 → Enable。Organizations は ①管理アカウントで委任管理者を指定（Trusted access にチェック）②委任管理者アカウントで自身を有効化 ③configuration policy でメンバーアカウントに展開。有効化すると `AWSServiceRoleForSecurityHubV2`、サービスリンク設定レコーダー（`AWSConfigurationRecorderForSecurityHubAssets`）、IAM Access Analyzer（90日未使用検出、us-east-1）が自動生成される。
- **注意/未確認**: 自分の把握リソースに対するスキャンで、任意ホストへ撃つ汎用スキャナではない。到達可否は分かるが認証突破・悪用可否までは見ない（侵入テストの代替ではない）。CLI/API での単体有効化コマンド、スキャン頻度・走査ポート範囲、IaC 対応はドキュメントで確認できず（要裏取り）。

### GitLost — GitHub Agentic Workflows へのプロンプトインジェクション
- **概要**: Noma Security が公表。攻撃者が対象組織の**公開**リポジトリに Issue を1本立てるだけで、同組織の**プライベート**リポジトリの中身を漏洩させられる。コード・クレデンシャル・アクセス権すべて不要。
- **前提（Agentic Workflows）**: ワークフローを Markdown で書く→YAML Actions にコンパイル→実行時に AI エージェントが動く。エージェントは設定可能な権限を持ち、Issue を読み・ツールを呼び・組織内リポジトリにアクセスできる。検証対象は `issues.assigned` で起動し、Issue のタイトル/本文を読んでコメントを返す設定。PoC のエージェントが公開・プライベート両方への read 権限を持っていたのが攻撃価値の源。
- **攻撃フロー**: ①公開リポに無害を装った Issue を立てる ②本文に AI への隠し命令を平文で仕込む ③エージェントが本文を「指示」と解釈 ④自分の権限でプライベートファイルを読む ⑤**公開 Issue のコメントとして投稿**（＝正規権限の使用なので怪しい通信は出ない）。攻撃者は立てて待つだけ。
- **"Additionally" バイパス**: GitHub はこのシナリオ用のガードレールを実装済みだったが、要求の前に "Additionally" を置くとエージェントが「追加の正規タスク」として再解釈し、拒否せず実行した。言い回し一つで信頼境界が崩れる、プロンプトインジェクションの本質。
- **対応状況**: **修正もドキュメントも出ていない**（記事時点）。コードで完全に塞げない種類の問題。Noma の「API キー共有戦略を見直す旨のドキュメント callout」提案すら未実装。CVE なし。
- **防御策**: ユーザー由来コンテンツを全て untrusted 扱い／エージェント権限を最小化（公開リポのワークフローにプライベート read を与えない）／公開投稿できる範囲を制限／モデルに渡す前に入力をサニタイズ。教訓は「エージェントが読める範囲 = 攻撃者が読める範囲」。

### TypeScript 7.0 の並列型チェッカー
- **前提**: 7.0 は `tsc` を Go にネイティブ書き換えした実装（`tsgo`）。8〜12倍の内訳は「ネイティブ化で約3〜4倍」＋「goroutine 共有メモリ並列で約2〜3倍」。速度の半分は Go の並行モデルが型チェック並列化を可能にしたことに由来。
- **なぜ Rust でなく Go**: コンパイラ内部の AST / シンボルテーブルは循環参照だらけ。Rust の所有権モデルは循環を素直に持てず作り直しが必要。Go は GC + 共有メモリで循環も OK、goroutine が単一シンボルテーブルへの安価な共有メモリ並列を与える。→ 同日の Bun（メモリ安全性のため Zig→Rust）と真逆だが両方合理的、という好対照。
- **仕組み**: 型チェックは本来プログラム全体を見る処理。ファイル集合を N 等分し独立した型チェッカー worker に割り当てる。各 worker は**不変な AST を共有**し、**型状態は worker ごとに独立**構築。共通依存は各 worker が重複計算するが、そのぶん同期不要で決定性を確保（同じ入力→同じ結果）。Node.js worker threads は隔離 V8 間のシリアライズ通信で巨大共有構造を跨げず原理的に不可能だった点が Go で解けた。
- **フラグ**: `--checkers`（既定4、線形トレードオフ。4で7.7〜11.9倍、8で10.6〜16.7倍だがメモリ増。CI 等の低リソースは 1 推奨で重複作業を排除）／`--builders`（モノレポの project reference 並列数、`--checkers` と掛け算で最大同時数が決まる）／`--singleThreaded`（全並列化を無効、デバッグ・比較用）。
- **注意**: 型チェックは情報の相対順序に依存する部分があり、worker はファイルを常に同一分割し同一結果を出す必要がある。`--checkers` 数を変えると稀に順序依存の結果が表面化しうる（ローカルと CI で checkers 数が違う構成に留意）。
- **学習視点**: Go の並行設計サンプルとして良教材。「不変は共有・可変状態は worker ごとに分離」「同期を減らすため意図的に重複計算を許す」は Go の fan-out ワーカープールの王道。共有メモリ並列（goroutine）と メッセージパッシング隔離（Node worker / Rust 傾向）の対比も。
