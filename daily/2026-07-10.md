## 📝 深掘りメモ

### Rust 1.97.0 — 何が変わったか

言語機能ではなく、**ビルドとデバッグの体験**が変わるリリース。コードの書き方は変わらないが、CI とプロファイラの見え方が変わる。

**① symbol mangling v0 がデフォルト化**

リンカのシンボルテーブルは C 時代の名残でフラットな名前空間しか持たない。だからコンパイラは `std::path::PathBuf::new` のような構造付きの名前を、リンカが扱える文字だけの1本の文字列に符号化する。これが name mangling。

旧 (legacy) 方式の問題は、ジェネリック関数の具体化 (monomorphization) の扱いにあった。`example::<i32>` と `example::<u64>` は別々の関数として実体化されるが、legacy ではシンボル名に**どの型で具体化されたかが残らず、末尾のハッシュで区別されるだけ**だった。バックトレースやプロファイラに同名の関数が並び、どれがどの型か判別できない。加えて legacy は Itanium C++ ABI に「部分的にしか」従っておらず、`c++filt` では正しく読めなかった。

v0 (RFC 2603) はジェネリック引数を**可逆にエンコードする**。`_R` で始まる。

```
_RINvCsgStHSCytQ6I_7mycrate7examplelKj1_EB2_
```

これは `fn example<T, const N: usize>(x: [T; N])` を `T = i32, N = 1` で具体化したもの。`l` = i32、`Kj1_` = 「usize の const 値 1」。demangle すると `mycrate::example::<i32, 1>` と**具体型がそのまま復元される**。型は1文字で符号化 (`l`=i32, `h`=u8, `j`=usize, `e`=str, `b`=bool …)、`I...E` がジェネリック引数を囲み、`B` は後方参照（圧縮）。

> Go との対比: Go のジェネリクスは GC shape stenciling なので `main.Foo[go.shape.int]` のように shape 単位でしか実体化されない。Rust は型ごとに完全実体化するぶんシンボルが増え、だからこそ「どの型のインスタンスか」がシンボル名に残る価値が大きい。

実務上の注意:
- `perf` / `gdb` / `lldb` / バックトレースの関数名の見た目が変わる。古いツールだと `_R...` の生シンボルが出る可能性があるので、プロファイリング環境のツールチェーンを確認する。
- **シンボル名を自前でパースしている CI やスクリプトは壊れる**（バイナリサイズ計測、`nm` の出力を grep する類）。
- legacy は nightly 限定になり、将来完全削除予定。

**② `CARGO_BUILD_WARNINGS` — 警告レベルをキャッシュを壊さずに切り替える**

従来の `RUSTFLAGS=-Dwarnings` は、値を変えると**ビルドキャッシュが無効化される**のが難点だった。1.97 からは Cargo 設定で `allow` / `warn`(既定) / `deny` を切り替えられ、これは**キャッシュを無効化しない**。

```bash
# リファクタ中、エラーだけ潰したいので警告のノイズを一時的に消す
CARGO_BUILD_WARNINGS=allow cargo check

# CI では警告をエラー扱い。--keep-going で全部集めてから落とす
CARGO_BUILD_WARNINGS=deny cargo build --keep-going
```

「ローカルは warn、CI は deny」を同じキャッシュを共有したまま運用できる。

**③ リンカのメッセージが既定で表示される**

これまでリンク成功時はリンカの stderr が握り潰されていた。1.97 からは `linker_messages` lint として warning 表示される。

```
warning: linker stderr: ignoring deprecated linker optimization setting '1'
  |
  = note: `#[warn(linker_messages)]` on by default
```

抑制は `Cargo.toml` の `[lints.rust] linker_messages = "allow"`。**注意: この lint は `warnings` グループの影響を受けない**ので、`-Dwarnings` や `CARGO_BUILD_WARNINGS=deny` を設定しても自動では deny にならない。

**④ 安定化API — ビット操作系**（整数型と `NonZero` 系の両方）

「値を返すもの」と「インデックスを返すもの」が対になっている。

```rust
let n: u32 = 0b_0110_0100;

// 値を返す（該当ビットだけ立てた値、0 なら 0）
n.isolate_highest_one();  // 0b_0100_0000
n.isolate_lowest_one();   // 0b_0000_0100

// インデックスを返す（0 なら None）
n.highest_one();          // Some(6)
n.lowest_one();           // Some(2)

// 表現に必要な最小ビット数（0 なら 0）
0b111_u32.bit_width();    // 3
u32::MAX.bit_width();     // 32
```

これまで `1 << (31 - n.leading_zeros())` と手で書いていた式が名前付きになった。ゼロのときの挙動（`isolate_*` は `0`、`*_one` は `None`）が型で表現されているぶん境界条件のバグを踏みにくい。ほかに `Default for RepeatN`、`Copy for ffi::FromBytesUntilNulError`、UEFI 上での `Send for std::fs::File`、`char::is_control` の const 安定化。

**まとめ**: アップグレードでコードが壊れることはまずないが、**シンボル名を前提にしたツールが壊れる**のと、**プロファイラ出力の見た目が変わる**のが要注意点。リンカ警告が急に出るようになったら、1.97 が今まで隠れていたものを見せているだけなので内容を読む価値がある。

### pgrust — 「本家テストをオラクルにした書き換え」

> 注記: 「100%通過」の記事**自体は方法論をほとんど書いていない**（何をもって100%とするか、どのスイートを走らせたかの定義がない）。以下は 67%時点の記事＋初期記事＋Postgres のテスト基盤の仕組みから組み立てたもの。性能の数字は一切公表されていない。

**オラクルとは何か**

テストにおける oracle は「その入力に対する正解は何か」を教えてくれるもの。普通のユニットテストではこれを人間が手で書く（`assert.Equal(t, 5, Add(2,3))` の `5` が書き下したオラクル）。25万行の Postgres を書き換えるとき、全クエリの正解を人間が書き下すのは不可能。

pgrust は**オラクルを書かずに、既に存在するものを借りた**。Postgres 本家のリグレッションスイート (`pg_regress`) は、`.sql` を流して出力を**リポジトリにコミットされた `.out` 期待値ファイルと diff する**作り。46,000件超のクエリに対する正解がテキストとして揃っている。それをそのまま自分の正解定義にした。

これは **golden file testing / characterization testing** そのもの。`assert x == 5` ではなく「出力が参照実装と1バイトも違わないこと」を正しさの定義にする。

さらに **isolation test**（並行セッションの操作順序 permutation を仕様として書き、実行結果を期待値と突き合わせる）も通している。並行性の正しさを決定論的に検証する、自前で用意するのが極めて面倒な資産。実際、記事では並行性のデバッグが最も時間を食ったとある（「ディスクに書いた後にメモリ上で更新され、永続化されない」バグなど）。

**なぜ AI 支援と噛み合ったか**

67%時点の記事にある通り、エージェントに「**特定のテスト失敗を1つ指さす**」("point each agent at a specific test failure")。テストスイートをオラクルにすると、副産物として同時に手に入るものがある。

| 得られるもの | 中身 |
|---|---|
| 作業キュー | 失敗テスト一覧がそのままタスクリスト |
| 完了の定義 | 機械が判定できる。人間のレビュー待ちが不要 |
| 進捗メトリクス | 通過率（1/3 → 67% → 100%） |
| 並列化の単位 | 失敗テストごとにエージェントを割り当て |

著者は Codex を8アカウント、同時10〜20セッションで回している。成立するのは**各エージェントが自分の成否を人間に聞かずに判定できる**から。密で自動的なフィードバック信号がある領域だから並列エージェントが機能した。

もう一つ。「**時間とともにリグレッションテストを通すのに必要なトークンが減っていった**」。理由は先に土台（プランナ、バッファキャッシュ、PL/pgSQL）を作ったので後半のタスクが「小さくて非常に具体的」になったから。**最初から動くものを常に維持する**（3時間で SQL が動く骨格を作った）方針が効いている。

一方でコスト。「機能は独立しているのに共有コンポーネントを触る」のでマージ衝突の解決が直列化してボトルネックに。GitHub merge queue の導入とビルド時間短縮（生成文法コードを別コンパイル単位に切り出し 60秒→36秒）で対処。**テスト以外のフィードバックループの速度が律速になる**。

**この手法が保証しないこと**

著者自身が明示している（production-ready でない / 性能最適化していない / 既存エクステンション非互換）。構造的な限界:

- **カバー範囲は上流が選んだものに限られる。** 46,000クエリを通っても「Postgres開発者がテストを書いた振る舞い」を再現しただけ。テストされていない挙動は野放し。
- **バグごと固定する。** 参照実装の出力を正解と定義する以上、参照実装のバグも「正解」になる。
- **内部不変条件は検査されない。** 出力が一致してもロック順序やメモリ寿命が同じとは限らない。並行性バグに一番苦労したのはまさにこれで、`.out` の diff は「たまたま今回は正しい順序で動いた」を通す。
- **非機能要件は射程外。** 性能・メモリ・拡張性。性能の数字が一切出ていないのは、テストスイートがそこを何も言わないから。

つまり **「テストが全部通った」は「正しい」ではなく「参照実装と観測可能な範囲で区別がつかない」** という意味でしかない。書き換えプロジェクトの足場としては十分に強力だが。

**Go で活かせるところ**

**1. golden file テスト（characterization test）** — `testdata/` に期待値を置き、`-update` フラグで再生成する。

```go
var update = flag.Bool("update", false, "update golden files")

func TestRender(t *testing.T) {
    for _, name := range []string{"simple", "nested", "empty"} {
        t.Run(name, func(t *testing.T) {
            got := Render(loadInput(t, name))
            golden := filepath.Join("testdata", name+".golden")

            if *update {
                os.WriteFile(golden, got, 0644)
                return
            }
            want, err := os.ReadFile(golden)
            if err != nil {
                t.Fatal(err)
            }
            if diff := cmp.Diff(string(want), string(got)); diff != "" {
                t.Errorf("mismatch (-want +got):\n%s", diff)
            }
        })
    }
}
```

最も効くのは**リファクタリング前に現状の振る舞いを固定するとき**。仕様書が無いレガシーコードに手を入れる前に、現在の出力を golden に焼き付ける（Feathers の characterization test）。pgrust がやったことのミニチュア版。

罠は2つ。**golden が腐る**（差分が出るたび中身を読まずに `-update` を叩くようになるとテストは何も守らない）。**なぜ失敗したかを教えてくれない**（diff は「違う」としか言わない）。golden は「振る舞いを固定する網」として使い、意図を表現するアサーションは別に持つ。

**2. 差分テスト（differential testing）** — pgrust の発想を最も直接持ち込める。**新旧2実装に同じ入力を流して出力を比較する。オラクルは旧実装。** 移行やリライトで強力。本番ではリクエストを新実装にも複製して流し (shadow / dark traffic)、差分だけ記録する運用ができる。テストコードを書かずに本番トラフィックがテストケース生成器になる。

**3. ファジング × 差分テスト** — Go のネイティブファジングと組み合わせる。

```go
func FuzzParserParity(f *testing.F) {
    f.Add([]byte("a=1&b=2"))
    f.Fuzz(func(t *testing.T, data []byte) {
        oldResult, oldErr := oldparser.Parse(data)
        newResult, newErr := newparser.Parse(data)

        if (oldErr == nil) != (newErr == nil) {
            t.Fatalf("error disagreement: old=%v new=%v", oldErr, newErr)
        }
        if oldErr == nil && !reflect.DeepEqual(oldResult, newResult) {
            t.Fatalf("output mismatch on %q", data)
        }
    })
}
```

入力は自動生成、正解は旧実装が教える。**人間はオラクルを一切書いていない**のに境界条件を掘り当てられる。

> 今日の digest に載せた `async-tar` の PAX 脆弱性（GNU tar と展開結果が食い違う）は、まさに**この差分ファジングを GNU tar をオラクルにして回していれば見つかった**類のバグ。パーサを書いたら参照実装と差分を取る、というのは実際にセキュリティ上の意味を持つ。

**持ち帰る一行**: **「オラクルを書くな、既にあるものを探せ」**。参照実装、旧バージョン、本家のテストスイート、別言語の同等ライブラリ。それが手に入るなら正しさの定義を書き下すコストがゼロになり、テストが同時に**作業キュー・完了条件・進捗メトリクス**として機能しはじめる。AI エージェントを並列で回せたのはその副産物。

同時に、**それは「観測可能な出力の一致」しか保証しない**。並行性の内部不変条件・性能・拡張互換性はすべて別腹で、pgrust が今そこに直面している。
