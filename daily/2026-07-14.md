## 📝 深掘りメモ

### Apple SpeechAnalyzer — 実体と、字幕パイプラインでの位置づけ

**これは何か（誤解しやすい点）**

- **音声のみ**を扱う。映像の内容解析ではない。動画に使うなら、まず音声トラックを demux して食わせる。
- **サービスではなく、OS 同梱のライブラリ**。iOS 26 / iPadOS 26 / macOS 26 以降に入っている API を Swift から呼ぶ。完全にオンデバイス動作で、**サーバー側の経路は存在しない**＝ Apple ハードウェアの上でしか動かない。

**解析結果はどこに格納されるのか → どこにも格納されない**

DB でもストレージでもなく、**呼び出しの戻り値をメモリ上で返すだけ**。永続化は完全に自前の仕事。

- 音声バッファを流し込むと、結果が**非同期ストリーム**で返ってくる。
- 返却物は `AttributedString`（属性付き文字列）で、各部分に **`audioTimeRange`（音声のどの時間範囲に対応するか）が属性として埋まっている**。字幕生成にはこれが決定的に重要。
- 結果は2段階。**volatile（暫定・速い）** → **finalized（確定）**。リアルタイム字幕なら暫定を即表示して確定で差し替え、バッチなら確定だけ拾う。

```
音声 → SpeechAnalyzer → (テキスト + 時間範囲) → 自分で WebVTT に整形 → S3 に .vtt を置く
                                              → 全文を検索用に DB へ
```

WebVTT にしておけば HLS のプレイリストから字幕トラックとして参照できるので、既存の配信構成にそのまま乗る。

**対応デバイス（※一部未確認）**

- OS ライン: **iOS 26 / iPadOS 26 / macOS 26 以降**（WWDC 2025 で導入）。Apple Silicon が性能面で推奨。
- 書き起こしエンジンは**2種類**あり、Apple 自身が「SpeechTranscriber が使えないデバイスがある」前提で設計している：
  - **`SpeechTranscriber`** — 高精度な新エンジン（WER 2.12% を出しているのはこれ）
  - **`DictationTranscriber`** — **非対応の言語・非対応デバイス向けのフォールバック**
- ⚠️ **未解決**: そのゲートの具体的な線引き（A17 Pro 以降 / M1 以降など）を一次情報で裏取りできず。Apple 公式ドキュメントが JS レンダリングで取得できなかった。
  - 注意: 検索で出てくる **「iPhone 15 Pro 以降」は Apple Intelligence の要約モデルの要件**であり、SpeechTranscriber の要件として確認できたものではない。混同しないこと。
- **確かめ方**: 機種リストを持つ必要はなく、実行時に問い合わせる設計になっている。
  - `SpeechTranscriber.supportedLocales` を叩けば対応ロケールが分かる（日本語対応の有無もこれで確定できる。※未確認）
  - モデル本体は端末に同梱されておらず **`AssetInventory` 経由でダウンロード**。これが失敗する＝そのデバイスでは使えない、が実質的な可否判定。
  - → 実装は「**SpeechTranscriber が使えるなら使い、ダメなら DictationTranscriber に落とす**」という分岐にするのが正しい。機種を条件分岐にハードコードするのは API 設計に逆らう書き方。
  - 要件が明示されている可能性が高い一次情報: [WWDC25 — Bring advanced speech-to-text to your app with SpeechAnalyzer](https://developer.apple.com/videos/play/wwdc2025/277/)

**配信パイプラインへの結論**

用途で答えが真逆になる。

- **エンドユーザー端末で完結させる場合 → 強い。** サーバーコストゼロ、音声が端末外に出ない（プライバシー）、ネットワーク往復なし。WER 2.12% が効いてくるのはここ。
  - ただし**字幕品質が端末依存でばらつく**（古い端末はフォールバックエンジンに落ちる）というプロダクト上のリスクを伴う。
- **サーバー側でバッチ処理したい場合 → 面倒。** Mac が要る。EC2 Mac インスタンスは**専有ホストで最低24時間課金**のため、必要な時だけスケールさせたい動画処理と相性が悪い。素直に Linux + GPU で Whisper か、マネージド ASR のほうが運用は普通。
- 対応ロケールは約30。多言語配信なら結局 Whisper（100+言語）が必要。

> つまりこのニュースは「**サーバー側の Whisper を置き換える**」話ではなく、「**クライアント側でできることが増えた**」話として読むのが正しい。既存のサーバー側字幕生成を置き換える動機にはなりにくい。

### MongoDB / DocumentDB — 使いどころ（結論: 当面は出番なし）

- 本質は「**ドキュメント = アグリゲート境界**」。常に丸ごと読み書きされる塊（注文＋明細など）が1ドキュメントに収まるなら強い。トランザクション境界とクエリ境界がドキュメントに収まらないと途端に弱くなる（`$lookup` は SQL の JOIN とは比較にならない）。
- **2026年時点では Postgres の JSONB が大半のニーズを吸収済み**。迷ったら Postgres。
- Mongo が残る領域: レコードごとに本当にスキーマが違う（商品カタログ、CMS、異種テレメトリ）／Change Streams（CDC 組み込み）／Atlas Search。
- 最大の落とし穴: **スキーマレスのコストは書き込み時ではなく、数年後の読み取り時に来る**。同じコレクションに歴史的に異なる形が混在し、読む側が全部の形を処理する羽目になる。マイグレーションが「ALTER TABLE 一発」ではなく「全ドキュメント書き換えバッチ」になる。
- ⚠️ **AWS DocumentDB は MongoDB ではない**。Mongo API を模倣した別実装（2018年の SSPL ライセンス移行を受けて AWS が独自開発）。**「MongoDB で動く」は「DocumentDB で動く」を意味しない** — wire protocol のバージョンや一部演算子に欠落あり。使うなら互換性リストの確認が先。
