# drill-01: 並行取得と部分失敗

| 項目 | 内容 |
|---|---|
| タイプ | 実装 |
| 想定時間 | 90〜120分 |
| 使ってよいもの | 標準ライブラリのみ |

## 状況

商品詳細ページを1枚返すために、3つのバックエンドサービスを呼ぶ必要がある。

```
                         ┌──────────────────┐
                    ┌───▶│ 商品サービス       │  必須
                    │    └──────────────────┘
  BuildProductPage ─┼───▶┌──────────────────┐
                    │    │ 在庫サービス       │  任意
                    │    └──────────────────┘
                    └───▶┌──────────────────┐
                         │ レビューサービス    │  任意
                         └──────────────────┘
```

商品情報が取れなければページは成立しない。一方、在庫やレビューは
**落ちていてもページは出したい**（在庫欄・レビュー欄が空のまま表示される）。

`catalog.go` に型定義とインターフェースがすでにある。
`fetch.go` の `BuildProductPage` を実装する。

## 要件

### 並行性

1. 3本の取得は**並行に実行する**。逐次だと全体のレイテンシが3倍になる
2. 関数から戻ったあと、**goroutine を残さない**

### 必須データの失敗

3. 商品情報が取得できなかったら、ページを返さずエラーを返す
4. そのエラーは `errors.Is(err, ErrProductUnavailable)` で判別できること
5. 同時に、**元の原因も `errors.Is` で辿れる**こと
6. 商品情報の失敗が確定した時点で、**残りの取得をキャンセルする**。
   不要になった結果を待たない

### 任意データの失敗

7. 在庫・レビューの取得が失敗しても、**エラーにせずページを返す**
8. 失敗した項目の値はゼロ値のままにし、項目名を `ProductPage.Degraded` に入れる
   （定数 `DegradedInventory` / `DegradedReviews` を使う）
9. `Degraded` は**昇順ソート**されていること。並行実行の完了順で結果が変わってはいけない

### ctx と期限

10. 呼び出し元の ctx がキャンセルされたら、それを尊重して速やかに返る
11. `Service.Timeout` が 0 より大きければ、それを組み立て全体の上限とする
12. 期限切れの時点で**必須データが取れていなければ**エラー
    （`errors.Is(err, context.DeadlineExceeded)` が真になること）
13. 期限切れの時点で**必須データが取れていれば**、残りを縮退させてページを返す

## 実行

```bash
mise x -- go test ./01-concurrent-fetch/    # drill/ 直下から
mise x -- go test -race ./01-concurrent-fetch/
mise x -- go test -run TestBuildProductPage_AllSucceed -v ./01-concurrent-fetch/
```

テストは10本。上から順に通していくのが進めやすい。

`-race` は最後だけでなく途中でも回すこと。並行部分を書き換えるたびに確認する。

## この課題で踏む罠

実装が終わったあとに答え合わせをするためのリスト。先に読まないこと。

<details>
<summary>ネタバレ（実装後に開く）</summary>

- キャンセル後に goroutine が結果を書き込んで race になる
- キャンセルしたが `wg.Wait()` を忘れて goroutine が残る
- `Degraded` への append を複数の goroutine から同時に行う
- 完了順に append するため `Degraded` の順序が実行ごとに変わる
- `context.WithTimeout` の `cancel` を defer し忘れる
- 任意項目の失敗と、必須項目の失敗の区別が実装に混ざって読めなくなる
- 期限切れを一律にエラー扱いしてしまい、縮退して返すべきケースを落とす

</details>

## 補足: 実務では

この課題は標準ライブラリのみに縛っているが、実務なら
`golang.org/x/sync/errgroup` を使うのが普通。ただし errgroup は
「最初のエラーで全体を止める」モデルなので、この課題のように
**必須と任意が混ざる**ケースはそのままでは表現できず、結局どこかで
自前の分岐が要る。自分で書いておくと、errgroup が何を肩代わりしていて
何を肩代わりしていないかが分かる。

goroutine リークの検出も、実務では `go.uber.org/goleak` を使う。
このドリルでは `runtime.NumGoroutine()` の前後比較で代用している。
