# drill-02: リトライと冪等性

| 項目 | 内容 |
|---|---|
| タイプ | 実装 |
| 想定時間 | 90〜120分 |
| 使ってよいもの | 標準ライブラリのみ |

## 状況

注文サービスから決済プロバイダ **Stellapay** に課金を投げる。
プロバイダは混雑時に 429 を返し、まれに 5xx を返す。ネットワーク断も起きる。

```
                        再試行してよい            再試行してはいけない
                    ┌──────────────────┐   ┌──────────────────┐
  Charge ──POST──▶  │ 5xx / 429 / 送信失敗 │   │ 4xx (カード拒否など) │
                    └──────────────────┘   └──────────────────┘
                              │
                       同じ冪等キーで送る
                    （キーが変わると二重課金）
```

課金は**金が動く操作**なので、素朴な再送は許されない。
「同じ課金の再送」だとプロバイダ側に伝える手段が冪等キー (`Idempotency-Key` ヘッダ) で、
プロバイダは同じキーのリクエストを2回受け取っても課金を1回しか行わない。

`client.go` に型・エラー・設定と `NewClient` がすでにある。`charge.go` の `Charge` を実装する。

## プロバイダの API

```
POST {BaseURL}/v1/charges
Content-Type: application/json
Idempotency-Key: <キー>

{"order_id": "order-1", "amount_jpy": 4980}
```

| レスポンス | ボディ |
|---|---|
| 200 | `{"charge_id": "ch_123", "status": "succeeded"}` |
| 4xx / 5xx | `{"code": "card_declined", "message": "カードが拒否されました"}` |

429 のときは `Retry-After` ヘッダに待つべき秒数（整数）が入ることがある。

## 要件

### 送信

1. 上記の形で POST する。ボディは `ChargeRequest` の内容
2. `Idempotency-Key` ヘッダを必ず付ける。値は `Client.NewIdempotencyKey` が発行したもの
3. 呼び出し元の ctx をリクエストに紐づける
4. 2xx ならボディをデコードして `*ChargeResult` を返す

### 冪等性

5. **1回の `Charge` 呼び出しで使うキーは1つ**。再試行しても同じキーを送る
6. 別の `Charge` 呼び出しでは別のキーを使う
7. 再試行のたびにボディを最初から送り直す

### 再試行の可否

8. 5xx は再試行する
9. 429 は再試行する
10. それ以外の 4xx は再試行しない。`*APIError` を返し、`errors.As` で取り出せること。
    `StatusCode` とボディの `code` / `message` が埋まっていること
11. 送信そのものが失敗した場合（ネットワーク断など）は再試行する

### 待機

12. n 回目の試行が失敗した後の待機は `BaseDelay * 2^(n-1)`。ただし `MaxDelay` で頭打ち
13. 429 で `Retry-After` が秒数として読めるなら、12 の計算より**そちらを優先**する。
    読めない値だった場合は 12 に従う
14. 待機は `Client.Sleeper` を通す
15. **最後の試行の後には待たない**（`MaxAttempts` 回試行するなら待機は `MaxAttempts - 1` 回）

### 打ち切り

16. `MaxAttempts` は初回を含む。使い切っても成功しなければエラーを返す
17. そのエラーは `errors.Is(err, ErrRetryExhausted)` で判別でき、
    かつ**最後の失敗の原因も辿れる**こと
18. 成功したら、それ以上リクエストを送らない

### ctx

19. 呼び出し時点で ctx が終了していたら、リクエストを1本も送らずに ctx のエラーを返す
20. 待機が ctx の終了で中断されたら、次の試行に進まずそのエラーを返す
    （`errors.Is(err, context.Canceled)` が真になること）

### リソース

21. 受け取ったレスポンスのボディは、再試行して捨てる分も含めて必ず閉じる

なお設定の既定値は `NewClient` が解決済みなので、`Charge` の中で未設定を気にする必要はない。
ただし試行回数や待機時間は定数ではなく `Client` のフィールドを見ること。

## 補足: 実務では

この課題では待機時間を決定的にしているが、実務では**ジッタ**（乱数によるばらつき）を
入れるのが普通。同時に落ちた多数のクライアントが同じタイミングで一斉に再試行すると、
回復しかけたサーバをもう一度倒す（thundering herd）。

`Retry-After` は秒数のほかに HTTP-date 形式も許されている。実際のクライアントは両方を扱う。

冪等キーは「プロセスが落ちて再起動した後の再送」でも同じ値である必要があるため、
実務では発注レコードと一緒に DB に保存しておくことが多い。メモリ上で発行して終わりだと、
プロセスが落ちた瞬間に冪等性が切れる。

再試行そのものは `cenkalti/backoff` や `hashicorp/go-retryablehttp` といったライブラリがある。
ただしライブラリが肩代わりするのは待機とループだけで、
**「何を再試行してよいか」の判断はドメイン側にしか書けない**。
自分で一度書いておくと、その境界が見える。

### この関数は実務ではこう分解される

この課題は1つの API 呼び出しの中に再試行を閉じ込めているが、実務でエンドポイントごとに
同じループを書くことはない。普通は次のどちらかに寄せる。

- **`http.RoundTripper` をラップする層**に置いて、全リクエストに横断的に効かせる
- **汎用のリトライ関数**（`retry.Do(ctx, policy, func() error { ... })` のような形）を用意し、
  判定だけを引数で渡す

ただしどちらの形にしても、「このリクエストは再送してよいか」の判断は呼び出し側に残る。
冪等キーを付けてあるから 500 でも再送してよい、カード拒否は何度送っても同じ、
`Retry-After` は待つ — これは HTTP の一般則ではなく Stellapay というドメインの知識で、
汎用層は知りようがない。汎用層に移せるのはループと待機だけである。

この課題で書かせているのはその**判断のほう**で、ループはその文脈として付いている。
