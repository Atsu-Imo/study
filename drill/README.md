# drill — コードを書く筋トレ

コーディングエージェントに任せていると落ちる筋肉を、意図的に鍛えるための練習場。

- **読解** — 他人のコードを読んで頭の中にモデルを作る
- **設計判断** — どこに境界を引くか、何をどこに置くか
- **デバッグ** — 症状から仮説を立てて絞り込む
- **接続** — 既存の書き方・慣例に合わせて1ピースを埋める

純粋なアルゴリズム（ソート・探索・DP）は扱わない。そこはエージェントに任せてよい領域。

## 設計の考え方

実務のコードで一番重いのは**文脈のロード**であって、書く行為そのものではない。
一方、練習用に小さい題材を自作すると文脈がゼロなので、アルゴリズム練習に退化する。

そこでこのディレクトリでは、**すでに動いているコードベースを文脈として与え、
その中の1ピースだけを抜いて埋める**形を取る。文脈読解は強制されるが、
書く量は 60〜120分で閉じる。

言語は Go。言語仕様との格闘に時間を取られないため。

## ドリルの3タイプ

| タイプ | 渡されるもの | 鍛わるもの | 答え合わせ |
|---|---|---|---|
| **実装** | 足場 + 落ちるテスト + `panic("not implemented")` | 接続・設計判断 | `go test` |
| **デバッグ** | 一見動くコード + 落ちるテスト | 読解・原因特定 | `go test` |
| **リファクタ** | 動くコード + 通るテスト | 設計判断 | Claude のレビュー |

## ルール

- **Claude に実装を書かせない**。詰まったら段階的にヒントをもらう（詳細は `CLAUDE.md`）
- 正解の定義は**テスト**であって Claude ではない
- 終わったら各ドリルの `NOTES.md` に詰まった箇所を書き残す
- 頻度は毎日少しずつより **週1で2時間まとめて**。文脈ロードのコストがあるので細切れは効率が悪い

## 実行

Go は mise 管理（`mise.toml` で固定）。`go` は PATH に出ていないので `mise x --` を挟む。

```bash
mise x -- go test ./...
mise x -- go test -race ./01-concurrent-fetch/
mise x -- go vet ./...
```
