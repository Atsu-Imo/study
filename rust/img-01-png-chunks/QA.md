# Q&A — img-01-png-chunks

記録開始: 2026-08-10

## Q1: 全体構成の図はファイルのヘッダのこと？ IDAT が画像本体でいい？ チャンクはどこからどこまで？

**図はヘッダではなく、`sample.png` というファイル全体（209バイト）を先頭から末尾まで1本の帯にしたもの。**
横軸がファイル内のバイト位置（オフセット）で、`8 + 25 + 44 + 120 + 12 = 209` とファイルサイズにぴったり一致する。

### 型名の意味

| 型 | 何の略 | 中身 |
|---|---|---|
| `IHDR` | Image Header | 幅・高さ・色の表現形式。後続データの取扱説明書 |
| `tEXt` | text | メモ書き。無くても画像は出る |
| `IDAT` | Image Data | **画像本体**（zlib 圧縮済み） |
| `IEND` | Image End | 終端マーカー。data は空 |

→ **IDAT が本体で合っている。** IHDR がその取扱説明書、IEND が終端、tEXt はおまけ。

### チャンクの範囲

チャンクは `length(4) + type(4) + data(length) + CRC(4)` の4要素1セット。

- 開始 = `length` の1バイト目
- 終了 = `CRC` の4バイト目
- 次のバイトからもう次のチャンクが始まる（隙間も区切り文字もない）

`length` は **data 部だけの長さ**なので、ファイル上の占有サイズは `length + 12`。
`IEND` は length 0 なのに12バイト占めるのはこれが理由。

### 「ヘッダ／ボディ」という構造ではない

固定のヘッダ領域に相当するのは**先頭の署名8バイトだけ**。
そこから先は同じ形のチャンクが対等に並んでいるだけで、`IHDR` も名前が header なだけの1個目のチャンクにすぎない。
だからデコーダは「8バイト飛ばしたら、あとは length を頼りに順に舐める」だけで済み、
知らない型が来ても読み飛ばせる（＝前方互換性）。

> README の「PNG のファイル構造」節は、この質問を受けて
> チャンク1個の分解 → 実バイトで1個追う → 型名の意味 → 全体の並び、の順に書き直した。

## Q2: 「チャンクは4要素1セット」と言われても、IHDR はその図のどこにあたるのか

**`IHDR` は `type` フィールドの中身**。4バイトの ASCII 文字列 `49 48 44 52` がそこに入っているだけ。

`IHDR` `IDAT` `IEND` `tEXt` はチャンクと並列の存在ではない。
「IHDR チャンク」= 「type に `"IHDR"` と書かれたチャンク」という意味。

```
  ┌─────────── これ全体で「IHDR チャンク」（25 バイト）─────────┐
  +----------+----------+------------------------------+----------+
  | 0000000d | 49484452 | 幅・高さ・ビット深度…(13byte) | 4b6d29dc |
  +----------+----------+------------------------------+----------+
    length      type                data                  CRC
                ~~~~~~
                ここだけが「IHDR」
```

ここから導かれること:

- **4要素の並び（形）は全チャンク共通**。IHDR でも IDAT でも変わらない
- **型ごとに違うのは `data` の中身の解釈だけ**（IHDR → 幅・高さ / IDAT → zlib 圧縮された画素）
- 全体図で `IHDR` `IDAT` とラベルが付いた箱は、**4要素すべてを含んだ塊**であって type の4バイトのことではない

パーサ実装で言うと、`type` を読むまでは全チャンクを同じコードで扱え、
`match chunk_type { b"IHDR" => ..., ... }` で分岐するのは `data` の解釈だけ、という構造になる。

## Q3: つまり PNG 全体は「署名 + IHDR チャンク + tEXt チャンク + IDAT チャンク + IEND チャンク」で構成されている、ということ？

**その通り。** そしてこれが最初に言うべき結論だった。

```
PNG 全体 = 署名 + IHDR チャンク + tEXt チャンク + IDAT チャンク + IEND チャンク
```

- 先頭の **署名8バイトだけが特別**（固定値。チャンクではない）
- それ以降はすべて「チャンク」という**同じ形の部品**が並んでいるだけ
- **全体図の箱ひとつひとつが「チャンク1個」**。この対応が書かれていなかったのが分かりにくさの原因だった

一般の PNG も同じ形で、署名の後に必要なだけチャンクが並ぶ（`tEXt` が無い / `IDAT` が複数個に分かれる、など）。

> README の「PNG のファイル構造」節の冒頭に「先に結論」を新設し、
> 帯グラフに「この箱ひとつひとつがチャンク1個」の注釈を入れた。
> ステップ4は同じ帯グラフの重複を消し、1行=1チャンクの表に統一した。

## Q4: CRC32ってなに？

**Cyclic Redundancy Check（32ビット）**。データから計算する32ビットの「指紋」で、用途は**偶発的なビット化けの検出**。

- ネットワーク転送やディスク保存でビットが壊れていないかのチェックに使う
- **暗号学的ハッシュではない**。同じCRCになるデータを意図的に作れるので、改ざん検知には使えない（そこは SHA-256 の仕事）
- 代わりに**速い**。テーブル引き＋XOR のループだけで済み、CPU の専用命令もある

### 仕組み（ざっくり）

データのビット列を「多項式」とみなし、決められた生成多項式で割り算して**その余り**を32ビットとして取り出す。
足し算・引き算がすべて XOR（mod 2 の世界）なので、実装上は「シフトして XOR」の繰り返しになる。

この構成のおかげで「**連続する31ビット以内のバースト誤りは100%検出できる**」といった保証が数学的に付く。
単純な合計値チェックサムより誤り検出力が高いのはこれが理由。

### PNG での使われ方

PNG の各チャンクは `[length: 4B][type: 4B][data: N B][CRC: 4B]`。
CRC は **type + data** に対して計算する（**length は含まない**）。
読み込み側で再計算して一致しなければ、そのチャンクは壊れていると判断する。

### 亜種に注意

「CRC32」と言っても複数ある。ビット反転の有無・初期値・生成多項式で結果が変わるため、仕様に合わせないと値が合わない。

| 名前 | 多項式(reflected) | 使われる場所 |
|---|---|---|
| CRC-32/IEEE | `0xEDB88320` | **PNG**, zlib, zip, Ethernet |
| CRC-32C (Castagnoli) | `0x82F63B78` | iSCSI, ext4, SSE4.2 の `crc32` 命令 |

PNG が使うのは前者。Rust なら `crc32fast` クレート、Go なら `hash/crc32` の `crc32.ChecksumIEEE()` に相当。

## Q5: 転送元と転送先の両方で CRC32 をチェックする必要がある？ そのデータはどこにあるの？

**両側で計算する。ただし役割が違う。**

- **送信側（書く側）** — データから CRC32 を計算して、**データにくっつけて送る**
- **受信側（読む側）** — 受け取ったデータから**自分でもう一度計算**し、くっついてきた値と比べる

### CRC値はどこにあるか → データと一緒に運ばれる

別チャネルで送るのではなく、**データの一部として同じ経路を流れる**。

```
送信側:
  data ──[CRC32を計算]──> 0x4b6d29dc
  送るもの: [ data ][ 4b6d29dc ]   ← 連結して1本のバイト列にする
                        ↓ 転送（ここでビット化けが起こりうる）
受信側:
  受け取り: [ data' ][ 4b6d29dc ]
  data' から自分で計算 ──> 0x9f2a1130
  4b6d29dc ≠ 9f2a1130  →  壊れている！
```

つまり **CRC の付いたデータは自己完結している**。
受信側は「正しい元データ」を知らなくても、届いたものだけで検証が完了する。だから送信側に問い合わせる必要がない。

### PNG の場合、「転送」は誰から誰へか

相手はネットワークの向こう側とは限らない。

- **送信側** = PNG を書き出したプログラム。チャンク生成時に CRC を計算して末尾4バイトに埋め込む
- **転送** = ファイルとして保存・コピー・ダウンロードされる期間（何年でもありうる）
- **受信側** = その PNG を読むデコーダ、つまり本トピックで書いているコード

`sample.png` の中の4バイトの CRC は、**そのファイルが作られた瞬間に焼き込まれた値**。
`broken-crc.png` はデータ側か CRC 側をわざと書き換えてあるので、再計算すると不一致になる。

### CRC の4バイト自体が壊れたら？

その場合も**不一致になるので「壊れている」と判定できる**。
CRC の仕事は「どこがどう壊れたか」の特定ではなく「壊れているかどうか」を言うことなので、これで目的は達成されている。

### 層ごとに別々の CRC がある

1枚の PNG を HTTP でダウンロードするだけでも、チェックは何重にもかかっている。

| 層 | チェック | 守備範囲 |
|---|---|---|
| Ethernet | FCS（CRC-32、フレーム末尾） | ケーブル1区間 |
| TCP | チェックサム（ヘッダ内） | 端から端までのセグメント |
| PNG | チャンクごとの CRC-32 | **そのファイルの一生涯** |

下の層は「その区間の転送」しか守らない。ディスク保存後の劣化や、途中のプログラムのバグで壊れたケースはカバーできない。
だから**ファイルフォーマット自身が自前の CRC を持つ**。
