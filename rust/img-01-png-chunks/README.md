# img-01: PNG チャンクパーサ

## 概要

最初に扱うのは PNG の「入れ物」の構造。圧縮もフィルタもピクセルも全部「入れ物の中身」の話なので、
まず入れ物だけを見る。

PNG を読み込んでチャンクを一覧表示し、CRC-32 を自前で計算して検証するダンプツールを作る。

## 実行

```bash
# ワークスペースのどこからでも実行できる
cargo run -p img-01-png-chunks

# CRC を意図的に壊したファイル
cargo run -p img-01-png-chunks -- rust/img-01-png-chunks/broken-crc.png
```

`sample.png` は 8×8 のグラデーション画像（209バイト）。小さいので全バイトを目で追える。

```bash
xxd rust/img-01-png-chunks/sample.png   # 13行で全部見える
```

## PNG のファイル構造

### 全体の並び

`sample.png` の全体は、署名と4つのチャンクが順に並んでいるだけ。

```
署名 + IHDR チャンク + tEXt チャンク + IDAT チャンク + IEND チャンク
```

```
  0    8         33         77                        197        209
  ┌────┬──────────┬──────────┬─────────────────────────┬──────────┐
  │ 署名│  IHDR    │  tEXt    │        IDAT             │  IEND    │
  └────┴──────────┴──────────┴─────────────────────────┴──────────┘
   8byte  25byte     44byte          120byte              12byte
```

上の数字がファイル先頭からのバイト位置、下の数字が各区間の長さ。
`8+25+44+120+12 = 209` でファイルサイズと一致する。

読み方は2点だけ。

- 先頭の署名8バイトだけが固定値で、チャンクではない
- 残りの4つの箱が、それぞれ「チャンク1個」。中身は違っても構造は同じ

つまり PNG にヘッダ領域とボディ領域という区別はなく、署名の後は同じ形の部品が対等に並ぶ。
一般の PNG も同様で、必要なだけチャンクが並ぶ（`tEXt` が無い、`IDAT` が複数個に分かれる、など）。

4つの型の役割は次の通り。名前は全部略語。

| 型 | 略語 | 中身 | 無いとどうなる |
|---|---|---|---|
| `IHDR` | Image Header | 幅・高さ・色の表現形式。後続データをどう解釈するかの指定 | 画像として読めない |
| `tEXt` | text | メモ書き（作者名やコメント） | 何も困らない。画像は普通に出る |
| `IDAT` | Image Data | 画像本体。ピクセル値を zlib 圧縮したもの | 絵がない |
| `IEND` | Image End | 終端マーカー。中身は空 | 終わりが分からない |

IDAT が本体、IHDR がその取扱説明書、IEND が終端、tEXt はおまけ、という関係。

### チャンク1個の構造

チャンクは4つの要素がこの順に並んだ1セット。長さは可変だが、並びは常に同じ。

```
  +----------+----------+------------------+----------+
  | length   | type     | data             | CRC      |
  | 4 byte   | 4 byte   | length byte      | 4 byte   |
  | BE u32   | ASCII×4  |                  | BE u32   |
  +----------+----------+------------------+----------+
       │          │                              │
       │          │                              └─ type + data の CRC-32
       │          │                                 (length は含まない)
       │          └─ "IHDR" "IDAT" など。大文字小文字に意味がある（後述）
       └─ data 部だけの長さ。type と CRC は含まない
```

`IHDR` `IDAT` `IEND` `tEXt` はチャンクと並ぶ別物ではなく、**`type` に入る4バイトの文字列**。
「IHDR チャンク」とは「type に `"IHDR"` と書かれたチャンク」のこと。
全体図で `IHDR` とラベルの付いた25バイトの箱は、4要素すべてを含んだ塊であって type の4バイトではない。

型ごとに変わるのは `data` の中身の解釈だけで、4要素の並びは全チャンク共通。

境界は次のように決まる。

- 開始 = `length` の1バイト目
- 終了 = `CRC` の4バイト目
- 次のバイトからもう次のチャンクが始まる（隙間も区切り文字もない）

間違えやすいのが `length` の意味で、これは data 部だけの長さ。
チャンクがファイル上で占めるサイズは `length + 12`（length 4 + type 4 + CRC 4）になる。
`length` が 0 の `IEND` でも12バイトあるのはこのため。

この形が固定されていることが効いていて、デコーダは型を知らなくても
`length` を読めば次のチャンクの位置がわかる。知らないチャンクを安全に飛ばせるので、
新しい型が追加されても古いデコーダが壊れない。

### バイト列で確かめる

`sample.png` のオフセット 8 から始まる IHDR チャンク。

```
オフセット 8         12        16                              29        33
           ↓         ↓         ↓                               ↓         ↓
  ...1a0a  0000000d  49484452  0000000800000008 08 02 00 00 00  4b6d29dc  00000020...
           ~~~~~~~~  ~~~~~~~~  ~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~  ~~~~~~~~  ~~~~~~~~
  署名の終  length    type      data (13 バイト)                 CRC       次チャンクの
            = 13      ="IHDR"                                             length
```

`type` の `49 48 44 52` は ASCII で `IHDR`。型は生バイトのまま読めるので、
`xxd` の右カラムを眺めるだけで拾える。

data の13バイトを IHDR の決まりに従って分解すると:

```
  00000008  幅 8 px
  00000008  高さ 8 px
  08        ビット深度 8
  02        カラータイプ 2 (RGB)
  00 00 00  圧縮方式 / フィルタ方式 / インタレース
```

占有サイズは `4 + 4 + 13 + 4 = 25` バイトなので、次のチャンクは `8 + 25 = 33` から始まる。
これを最後まで繰り返した結果が次の表で、1行が1チャンク、`占有サイズ` が全体図の箱の幅にあたる。

| 開始 | length | type | data の中身 | 占有サイズ | 次の開始 |
|---|---|---|---|---|---|
| 0 | — | （署名） | `89 50 4E 47 0D 0A 1A 0A` | 8 | 8 |
| 8 | 13 | `IHDR` | 8×8 / RGB / 8bit | 25 | 33 |
| 33 | 32 | `tEXt` | `Comment\0study/rust img-01 sample` | 44 | 77 |
| 77 | 108 | `IDAT` | `78 da ...`（zlib 圧縮された画素） | 120 | 197 |
| 197 | 0 | `IEND` | なし | 12 | 209 = EOF |

`次の開始` が `開始 + 占有サイズ` になっている。パーサはこの表を上から順に埋めるだけで、
`length` さえ読めれば `data` の中身を理解しなくても末尾までたどり着ける。

IDAT の data が `78 da` で始まっているのは zlib のヘッダ。
中身は圧縮済みバイト列で、展開して初めてピクセルが出てくる（img-03/04 で扱う）。

### シグネチャ 8バイトの意図

```
  89 50 4E 47 0D 0A 1A 0A
  ↑  └──┬──┘ └─┬─┘ ↑  ↑
  │     │      │   │  └ LF: CRLF に膨らませる転送を検出
  │     │      │   └─── Ctrl-Z: MS-DOS の TYPE で表示が止まる
  │     │      └─────── CRLF: LF に潰す転送を検出
  │     └────────────── "PNG": 人間向けの目印
  └──────────────────── 非ASCII: 7bit伝送路を通ると壊れるので検出できる
```

単なるマジックナンバーではなく、テキストモードで転送されて壊れた事故を検出する仕掛けが
1バイトずつに込められている。FTP のアスキーモードが日常だった時代の設計。

### チャンク型の大文字小文字がフラグになっている

4文字それぞれの5ビット目（大文字と小文字の差）が意味を持つ。

| 位置 | 大文字 | 小文字 | 意味 |
|---|---|---|---|
| 1文字目 | 必須 (critical) | 補助 (ancillary) | 知らなければ捨ててよいか |
| 2文字目 | 公開 (public) | 私用 (private) | 仕様に登録された型か |
| 3文字目 | （予約・常に大文字） | — | 将来拡張用 |
| 4文字目 | コピー不可 | コピー可 (safe-to-copy) | 編集ツールがそのまま残してよいか |

例:

- `IHDR` — 全部大文字 → 必須・公開・コピー不可
- `tEXt` — 1文字目が小文字なので補助（無くても画像は出る）。
  4文字目が小文字なのでコピー可（画像を加工しても注釈は残してよい）
- `gAMA` — 補助だがコピー不可（ガンマ値は画像を加工したら無意味になるため）

`chunk_type[0].is_ascii_uppercase()` を見るだけで
「知らないチャンクをエラーにすべきか、無視すべきか」が判断できる。
既知の型名テーブルとの照合が要らない。

### 主要チャンク

`sample.png` に出てくる4種類以外も含めた一覧。

| 型 | 必須 | 役割 |
|---|---|---|
| `IHDR` | ✅ | 画像ヘッダ。幅・高さ・ビット深度・カラータイプ。必ず最初 |
| `PLTE` | 条件付き | パレット（カラータイプ3のとき必須） |
| `IDAT` | ✅ | 画像データ本体。複数に分割されうる |
| `IEND` | ✅ | 終端マーカー。データ長0。必ず最後 |
| `tEXt` / `zTXt` / `iTXt` | | テキスト注釈 |
| `gAMA` / `sRGB` / `iCCP` | | 色空間情報 |
| `tRNS` | | 透過情報（パレット画像のアルファ等） |
| `acTL` / `fcTL` / `fdAT` | | APNG（アニメーション）。PNG 本来の仕様外の拡張 |

## 実行結果の読み方

```
--- ② チャンク一覧 ---
  offset  type  length  CRC         判定  属性
  ------  ----  ------  ----------  ----  --------------------
       8  IHDR      13  0x4b6d29dc  OK    必須/公開/コピー不可
      33  tEXt      32  0x62234618  OK    補助/公開/コピー可
      77  IDAT     108  0x573936f2  OK    必須/公開/コピー不可
     197  IEND       0  0xae426082  OK    必須/公開/コピー不可
```

`IEND` の CRC `0xae426082` はどの PNG でも同じ値になる。データ長0・型 `IEND` で固定なので、
計算結果も常に同じ。バイナリを眺めていて `00 00 00 00 49 45 4E 44 AE 42 60 82` が出てきたら、
そこがファイル末尾だと分かる。

```
--- ③ IHDR (画像ヘッダ) ---
  幅          : 8 px
  高さ        : 8 px
  ビット深度  : 8 bit / チャンネル
  カラータイプ: 2 (トゥルーカラー RGB)
  ...
  → 1ピクセル 3 チャンネル × 8 bit = 24 bit
  → 1行 25 バイト (先頭1バイトはフィルタタイプ)
  → zlib 展開後の想定サイズ: 200 バイト  ← img-03/04 で実際に確認する
```

ここで出た 200 バイトが次のトピックの答え合わせに使える。
IDAT を展開すると 200 バイト出てくるはずで、内訳は
1行 `[フィルタタイプ][RGB×8]` = 25バイト × 8行。

行の先頭に付く1バイトのフィルタタイプが PNG 圧縮の肝で、img-04 で扱う。

## CRC-32 について

CRC は「ビット列を多項式とみなして割り算し、その余りを付ける」誤り検出符号。
数学の中身は追わなくてよく、押さえるのは次の3点。

- 目的は改ざん防止ではなく事故検出（ビット化け・転送ミス）。暗号学的ハッシュではない
- 対象は type + data。length は含まない（ここを間違えると必ず一致しなくなる）
- PNG が使うのは IEEE 802.3 と同じ多項式。Ethernet や zip と同じもの

実装は「256エントリのテーブルを先に作り、1バイトごとにテーブルを引いて混ぜる」定番形。
`main.rs` の `crc32_table()` / `crc32()` を参照。

> 学習用に毎回テーブルを作り直しているが、実用コードなら `OnceLock` などで
> 一度だけ作るのが普通。

## Go との比較

### バイナリ読み取り

```go
// Go: encoding/binary が用意されている
length := binary.BigEndian.Uint32(data[pos : pos+4])
```

```rust
// Rust: 標準に「バイト列 → 整数」の便利関数はなく、配列にしてから変換する
let length = u32::from_be_bytes([data[pos], data[pos+1], data[pos+2], data[pos+3]]);

// あるいは TryInto でスライス → 固定長配列
let length = u32::from_be_bytes(data[pos..pos+4].try_into().unwrap());
```

Go の `encoding/binary` に慣れていると最初は面倒に感じるが、
「4バイトあることを型で保証してから変換する」という筋の通し方になっている。

### CRC-32

```go
// Go: 標準ライブラリにある
crc := crc32.ChecksumIEEE(append(chunkType, data...))
```

```rust
// Rust: 標準ライブラリにはない。実用では crc32fast クレートを使う
// （このトピックでは学習目的で自前実装している）
```

Go の「標準ライブラリが分厚い」文化との差が出るところ。
Rust は標準を薄く保ち、`crates.io` に任せる方針。

### スライスの借用

```go
// Go: スライスは元の配列を暗黙に参照する。GC が面倒を見るので寿命を気にしない
type Chunk struct {
    Data []byte  // 元データを参照しているが、型からは読み取れない
}
```

```rust
// Rust: 借用であることが型に現れる
struct Chunk<'a> {
    data: &'a [u8],  // 「元のバイト列より長生きできない」がコンパイル時に保証される
}
```

`'a` が付くのは面倒に見えるが、意味は「この構造体は元のバイト列を参照しているだけで、
コピーしていない」の明示。ファイル全体を1回だけ読み、チャンクはその中を指すだけ、
という省メモリな作りがそのまま型に出ている。

Go で同じことをすると「元の `[]byte` を握り続けているせいで GC されない」問題が
静かに起きうるが、Rust ではその関係が型に書いてある。

### エラー処理

```go
func parseChunks(b []byte) ([]Chunk, error) {
    if len(b) < 8 {
        return nil, fmt.Errorf("too short")
    }
    // ...
}
```

```rust
fn parse_chunks(bytes: &[u8]) -> Result<Vec<Chunk<'_>>, String> {
    if bytes.len() < 8 {
        return Err("短すぎる".to_string());
    }
    // ...
}
```

構造はほぼ同じ。呼び出し側が `if err != nil` を書く代わりに `?` で伝播する点が違う。
（本格的にやるなら `String` ではなく独自のエラー型 + `std::error::Error` 実装。
`09-error-handling` を参照）

## 「他人が書いた数値」を信用しない

`parse_chunks()` の中で `length` に対して2つチェックを入れている。

```rust
if length > 0x7FFF_FFFF { /* 仕様上限を超えている */ }
if data_end + 4 > bytes.len() { /* ファイル末尾を超えている */ }
```

形式的なバリデーションではなく、画像デコーダの脆弱性でよくある攻撃への対処。

- 巨大な `length` を書いた PNG を投げ、境界チェックのないパーサに範囲外読み取りをさせる
- `pos + length` を検証前に計算させて整数オーバーフローを起こす

Rust では範囲外アクセスがパニックで止まるので C ほど致命的ではないが、
それでもサービスを落とせる（DoS）。
ファイルから読んだ長さは使う前に検証する、というのは言語を問わない。

## 演習

`src/main.rs` の末尾にコメントで雛形が入っている。

### 演習1（基礎）: チャンク型でフィルタする

`--only IDAT` のように、特定の型だけ表示するオプションを追加する。

### 演習2（応用）: tEXt チャンクを読む

`sample.png` には `Comment` キーワードの tEXt が埋め込んである。
`キーワード + 0x00 + 本文` というレイアウトをパースして表示する。
文字コードが UTF-8 ではなく Latin-1 な点に注意。

### 演習3（チャレンジ）: CRC エラーを属性で扱い分ける

同梱の `broken-crc.png` は tEXt の CRC を1バイト壊してある。

- 必須チャンクの CRC 不一致 → エラー終了
- 補助チャンクの CRC 不一致 → 警告してそのチャンクだけ捨て、続行

という本来あるべき挙動に直す。
画像ビューアや ImageMagick に `broken-crc.png` を渡して、どちらの挙動をするか比べてみるとよい。
