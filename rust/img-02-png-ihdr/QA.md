# Q&A — img-02-png-ihdr

記録開始: 2026-08-12

## Q1: 「カラータイプごとに使える深度が違う」なら、IHDR も カラータイプ→深度 の並びのほうが自然では？ なぜ深度が先なのか

### 前提の補正: 深度はカラータイプから導出される値ではない

`ColorType::allowed_depths()` をカラータイプのメソッドにしたので従属関係に見えるが、
実態は**合法な組み合わせの表**であって片方向の依存ではない。逆にも引ける。

```
深度 2 と書いてあった  → カラータイプは 0 か 3 しかありえない
深度 24 と書いてあった → そもそも存在しない深度
```

「カラータイプ → 深度」という向きは README の説明の都合であって、仕様上の従属関係ではない。
実際には2次元の表で、どちらの軸から入ってもよい。

### 技術的には順序に意味がない

IHDR は**固定長13バイト**。

```
[幅 4][高さ 4][深度 1][色型 1][圧縮 1][ﾌｨﾙﾀ 1][ｲﾝﾀﾚｰｽ 1] = 13 固定
```

「先頭を読まないと次のフィールドの長さや解釈が決まらない」という TLV 的な構造ではないので、
パーサは13バイトを丸ごと読んでから検証する
（`parse_ihdr()` で全フィールドを構造体に詰め → `Layout::new()` で組み合わせを検証）。

**フィールドの並びを入れ替えても実装は1文字も変わらない。**
順序は技術的制約ではなく、仕様書の見せ方の問題。

### なぜこの並びなのか

**仕様書に理由は書かれていない。** 以下は後付けの読み方。

一貫した説明としては「小さい単位から大きい単位へ」の並びになっている、というもの。

```
幅・高さ          → 画像全体の形
深度              → 数値1個は何ビットか            ← 最小単位
カラータイプ       → 数値を何個どう並べて1ピクセルか
圧縮/ﾌｨﾙﾀ/ｲﾝﾀﾚｰｽ  → それをバイト列にする手順       ← 最大単位
```

この読みなら、深度 =「サンプル1個の精度」、カラータイプ =「サンプルの組み立て方」なので、
深度が先に来るのは筋が通る。人間に説明するときは逆（カラータイプが先）のほうが分かりやすいが、
データの構成単位としてはボトムアップになっている。

なお 1995 年の設計で PNG 1.0 以降変わっていない。互換性の都合で並び替えられないので、
「当時こう決めた」以上の答えはない。

### 順序が本当に効くのはチャンクレベル

フィールドの順序はどうでもいいのに、**チャンクの順序は仕様で強制されている**のが対照的。

`tRNS` はカラータイプによって中身の意味が丸ごと変わる
（グレー → 2バイト / RGB → 6バイト / パレット → Nバイト）。
可変長で解釈も変わるので、`IHDR` を先に読んでいないと処理できない。
だから「IHDR は必ず最初のチャンク」が仕様で決められている。

依存関係が本当にあるところだけ順序が縛られ、無いところ（IHDR 内部の13バイト）は
自由に決められた、という構造になっている。

## Q2: チャンネルとは何か。ビット深度についてもう少し

チャンネルとビット深度は掛け算の関係にあるので、セットで捉えると見通しが良い。

### チャンネル = 1ピクセルを表す数値の「本数」

色は1つの数値では表せない。「何本の数値で1ピクセルを表現するか」がチャンネル数。

| カラータイプ | チャンネル | 各数値の意味 |
|---|---|---|
| 0 グレースケール | 1 | 明るさ |
| 2 RGB | 3 | 赤の強さ / 緑の強さ / 青の強さ |
| 4 グレー+α | 2 | 明るさ / 不透明度 |
| 6 RGBA | 4 | 赤 / 緑 / 青 / 不透明度 |
| 3 パレット | 1 | **色ではなく「パレットの何番目か」という番号** |

### イメージは「モノクロ画像の重ね合わせ」。ただし格納はインターリーブ

RGB 画像は「赤だけの濃淡画像・緑だけ・青だけの3枚を重ねたもの」と考えると分かりやすい。
Photoshop のチャンネルパネルで各色が白黒で表示されるのはこれがそのまま見えているため。

ただし PNG のバイト列は3枚を別々には持たない。

```
プレーナー方式（PNG はこれではない）:
  [RRRRRRRR...][GGGGGGGG...][BBBBBBBB...]   ← チャンネルごとにまとめる

インターリーブ方式（PNG はこっち）:
  [RGB][RGB][RGB][RGB]...                   ← ピクセルごとに混ぜる
```

「重ね合わせ」は概念の話で、格納はピクセル単位で交互。
動画の YUV にはプレーナー方式のものがあるので、この区別は後で効いてくる。

### ビット深度 = 1本あたりの精度

| 深度 | 段階数 | 用途 |
|---|---|---|
| 1 | 2 | 白か黒か |
| 2 | 4 | |
| 4 | 16 | |
| 8 | 256 | 一般的な画像 |
| 16 | 65536 | 編集の中間段階 |

### 掛け算になる（実バイトで確認）

```
bits_per_pixel = channels × bit_depth
```

`sample-rgba16.png` (4ch × 16bit = 64bit = 8バイト) の展開後1行目:

```
00 | 00 00 00 00 75 30 ff ff | 3e 80 00 00 75 30 e0 bf | ...
↑    └─ px0 の8バイト ──────┘  └─ px1 の8バイト ──────┘
ﾌｨﾙﾀ   R=0    G=0  B=30000 A=65535   R=16000 G=0 B=30000 A=57535
```

1チャンネルが2バイト（ビッグエンディアン）で4本並ぶ。「本数」の意味がそのまま見える。

`sample-gray1.png` (1ch × 1bit) の展開後1行目はたった3バイト:

```
00 | 55 50
↑    ↑  ↑
ﾌｨﾙﾀ │  0101 0000 ← x=8,9,10,11 の4px + 詰め物4bit
     └─ 0101 0101 ← x=0〜7 の8px
```

`sample-palette4.png` (1ch × 4bit) は16進1桁が1ピクセルに対応するので一番読みやすい:

```
00 | 01 23 45 01 20
     ↑ パレット番号 0,1,2,3,4,5,0,1,2 + 詰め物
```

### なぜ 1bit と 16bit が両方あるのか

用途が正反対。

- **低い深度 (1/2/4) は容量のため** — 白黒の線画やアイコンに 8bit は無駄。1bit なら 1/8 になる
- **16bit は編集の中間段階のため** — 表示は 8bit で十分だが、明るさ調整を繰り返すと
  丸め誤差が蓄積してバンディング（グラデーションの縞）が出る。
  16bit で作業して最後に 8bit に落とすのが写真編集の定石

実務では「配信する PNG は 8bit、素材として持つなら 16bit」という使い分けになる。

### パレットの1チャンネルだけ別物

カラータイプ3の1チャンネルは明るさでも色でもなく、ただの番号。

```
展開後のデータ:      [3]              ← パレットの3番、という意味しかない
PLTE チャンクを引く:  3番 = (0, 200, 0)
最終的な色:          (0, 200, 0) の緑
```

深度4のパレット画像はデータ上1ピクセル4ビットだが、画面に出す段階では RGB 24bit
（tRNS があれば RGBA 32bit）になる。**展開後サイズとメモリ上のサイズが一致しない**
唯一のケースで、演習2で扱うのがこれ。

## Q3: パレットとは何か

**使う色の一覧表**。画像本体は色そのものを持たず「一覧表の何番目か」という番号だけを持つ。

```
色鉛筆セット（＝パレット / PLTE チャンク）
  0番 = 赤, 1番 = オレンジ, 2番 = 黄, ...

塗り絵の指示書（＝画像データ / IDAT）
  0 1 2 3 4 5 0 1 2
  1 2 3 4 5 0 1 2 3
```

指示書に「赤」とは書いていない。「0番」としか書いておらず、
色鉛筆セットと突き合わせて初めて絵になる。

### 実物で見る

`sample-palette4.png` の PLTE は18バイト。**3バイトで1色 (R,G,B)** なので 18÷3 = 6色。

```
PLTE (18 バイト): ff 00 00 | ff 80 00 | ff ff 00 | 00 c8 00 | 00 64 ff | 80 00 ff
                   0番 赤    1番 橙     2番 黄     3番 緑     4番 青     5番 紫
```

画像本体（IDAT 展開後）の1行目:

```
00 | 01 23 45 01 20
     ↑ 0番,1番,2番,3番,4番,5番,0番,1番,2番
```

16進1桁がそのまま「何番の色鉛筆か」。色の値はどこにも書かれていない。

### 何が得なのか

| 方式 | 1ピクセル | 展開後サイズ | パレット |
|---|---|---|---|
| パレット 4bit | 4 bit | 54 バイト | +18 バイト |
| RGB 8bit | 24 bit | 252 バイト | — |

1ピクセルあたり6分の1。画像が大きくなるほどパレット表の18バイトは誤差になる。
「使っている色数が少ないなら、色を毎回書かずに番号で参照したほうが安い」という発想で、
LZ77 の「繰り返しを参照に置き換える」と同じことを色に対してやっている。

### 制約: 256色まで

インデックスが最大8bit なので上限は256色。

| 深度 | 色数の上限 |
|---|---|
| 1 | 2 色 |
| 2 | 4 色 |
| 4 | 16 色 |
| 8 | 256 色 |

- ロゴ / アイコン / スクリーンショット / イラスト → 色数が少ないので大得意
- 写真 → 数万色使うのでそのままでは入らない

写真をパレット化するには**減色（色の量子化）**が必要で、これは不可逆な劣化。
グラデーションが縞（バンディング）になるのはこれが原因。だから写真は素直に RGB で持つ。

`sample-palette4.png` は6色なので深度4（16色まで）で足りている。
17色使いたければ深度8に上げる必要があり、1ピクセルが 4bit → 8bit に倍増する。

### 透過は tRNS で足す

PLTE は RGB だけでアルファを持てない。透過が必要なら tRNS を足す。

```
tRNS (6 バイト): 00 40 80 ff ff ff
                  ↑  ↑  ↑ 0番,1番,2番... のアルファ値
```

**PLTE と同じ順番で1バイトずつ**対応する。tRNS のほうが短くてよく、
足りない分は不透明 (255) 扱い。長いのは仕様違反。

### デコーダ側の仕事（＝演習2）

```
IDAT展開後:  [0][1][2][3]...              ← 4bit の番号列
                ↓ PLTE を引く
画面に出す:  [255,0,0,0][255,128,0,64]...  ← RGBA 32bit
```

**メモリ上では結局 32bit に膨らむ**点に注意。ファイル上で1ピクセル4bitでも、
表示には色に戻すので8倍のメモリを使う。「ファイルが小さい」と「メモリを食わない」は別の話。

検証すべきエラー:
- PLTE のエントリ数より大きい番号が来た → 壊れたファイル（範囲外アクセス）
- tRNS が PLTE より長い → 仕様違反

### おまけ: RGB 画像にも PLTE を置ける

カラータイプ2や6でも PLTE を付けられるが、意味が違う。
**推奨パレット (suggested palette)** といって「256色しか出せない環境ではこの色を使って」
というヒントにすぎず、画像の中身には影響しない。

同じ `PLTE` という型なのにカラータイプ3のときだけ意味が本質的に変わる。tRNS と同じ構造。

## Q4: パレットの色数は PNG 全体で統一されている？

**その通り。PNG 1ファイルにつき PLTE は最大1個**で、画像全体で共有される。
領域ごとに別のパレットを持つことはできない。

```
PNG ファイル
  └─ PLTE（1個だけ、最大256色）
       ↑ 画像の全ピクセルがここを参照する
```

1000×1000 の画像でも、左上と右下でまったく違う絵柄でも、
**使える色は全部あわせて256色まで**。これがパレット画像の根本的な天井。

写真がパレットに向かないのはこのせいで、部分ごとに最適な色を割り当てられない。
空のグラデーションと人物の肌色を同じ256色の中で分け合う必要がある。

### エントリ数は 2^深度 ちょうどでなくてよい

上限を超えなければ何色でもよい。`sample-palette4.png` は深度4（上限16色）で実際は6色だけ。
`main.rs` の検証もこの向きだけを見ている。

```rust
if layout.color == ColorType::Palette && entries > max {
    // 深度で表せる数を超えていたらエラー
}
```

6色しか使わないなら PLTE は18バイトで済み、余分な10色分を書く必要はない。

### 置く場所も決まっている

PLTE は **IHDR の後、最初の IDAT より前**。順序が本当に効く例で、
番号だけの画像データが流れてくる前に色鉛筆セットが手元にないとデコーダは何も描けない。

### GIF との違い

| | GIF | PNG |
|---|---|---|
| 全体のパレット | Global Color Table | PLTE（1個） |
| フレームごとのパレット | **Local Color Table を持てる** | なし |

GIF はアニメの各フレームが独自のパレットを持てるので、シーンが変わっても色を作り直せる。
PNG は静止画前提の設計なのでこの仕組みがない。APNG も PLTE は全フレーム共通。

APNG が GIF より画質が良いのは、そもそも256色制限のない RGB が使えるからであって、
パレットで勝っているわけではない。

### 色数が足りなければ

1. **深度を上げる** — ただし上限は 8bit = 256色。それ以上は行き先がない
2. **パレットをやめて RGB にする**（カラータイプ 2/6）

「257色使いたい」となった時点でパレット方式は破綻し、1ピクセル 8bit → 24bit に跳ね上がる。
この崖があるので、実務では「明らかに色数が少ない素材」以外は最初から RGB を選ぶのが無難。

## Q5: PNG 自体にカラーマネジメントの情報は埋め込まれているのか

**埋め込まれている。しかも4世代分の仕組みが積み重なって共存している。**

### 色に関するチャンク一覧

| チャンク | 中身 | サイズ | 世代 |
|---|---|---|---|
| `gAMA` | ガンマ値ひとつ | 4 B | 1995 |
| `cHRM` | RGB三原色と白色点の座標 | 32 B | 1995 |
| `sRGB` | 「sRGB です」+ レンダリング意図 | 1 B | 1999頃 |
| `iCCP` | ICC プロファイルを丸ごと埋め込み | 数百B〜数KB | 1999頃 |
| `cICP` | 色空間を規格番号の組で指定 | 4 B | PNG 3rd (HDR対応) |
| `mDCv` / `cLLi` | マスタリング環境の輝度情報 | 小 | PNG 3rd (HDR対応) |

`gAMA` + `cHRM` が最古の方法。「ガンマはいくつ、原色の座標はここ」という最小限の情報を
自前で書く方式で、当時 ICC プロファイルは重すぎたためこうなっている。

### 手持ちのサンプルで見える

```
$ cargo run -p img-02-png-ihdr
  gAMA  ガンマ値 0.45455 (整数 45455 / 100000)
  pHYs  物理解像度 2835×2835 px/m (≒ 72 DPI)

$ cargo run -p img-02-png-ihdr -- .../sample-palette4.png
  sRGB  sRGB 色空間。レンダリング意図 0 (Perceptual)
```

`0.45455` は `1 / 2.2`。sRGB のガンマ2.2をこの1個の数値で近似する古い方式がそのまま見える。

### なぜ4世代もあるのか

```
gAMA + cHRM  「ガンマと原色座標を自分で書く」   軽いが不正確
     ↓
sRGB         「sRGB です」の一言で済ませる       1バイト。一番よく使われる
     ↓
iCCP         ICC プロファイルを丸ごと入れる      正確だが重い
     ↓
cICP         規格番号の組で指定（HDR対応）       BT.2020/PQ などを4バイトで
```

`sRGB` チャンクが偉いのは、**たった1バイトで「gAMA + cHRM を厳密に書いたのと同等」を
意味できる**点。世の中の画像の大半は sRGB なので専用のショートカットを用意した設計。

`iCCP` は印刷用 CMYK プロファイルなどを正確に運ぶためのもの。数百バイト〜数KBあるので、
**小さい PNG だと画像本体よりプロファイルのほうが大きくなる**ことが普通に起きる。
Web アイコンから真っ先に剥がされるのがこれ。

### 優先順位

複数入っていた場合、実装はおおむねこの順で見る。

```
cICP  >  iCCP  >  sRGB  >  gAMA + cHRM
```

仕様上も `sRGB` と `iCCP` の同時使用は想定されておらず、`sRGB` があるなら
`gAMA` / `cHRM` はそれと矛盾しない値であるべきとされている。
実際には矛盾した組み合わせを持つ PNG が存在するので、デコーダは決め打ちが必要。

### 何も無かったら

**事実上 sRGB とみなされる。** 仕様上は未定義だが、そう扱わないと大半の画像が
正しく表示されないため、ブラウザもツールも sRGB を仮定する。

### レンダリング意図 = 「モニタが出せない色が来たときの妥協方針」

| 値 | 名前 | 方針 |
|---|---|---|
| 0 | Perceptual | 全体を圧縮。写真向け |
| 1 | Relative colorimetric | 出せる色はそのまま、出せない色だけ寄せる。ロゴ向け |
| 2 | Saturation | 鮮やかさ優先。グラフ・図表向け |
| 3 | Absolute colorimetric | 印刷校正用 |

モニタの色域（sRGB / DCI-P3 / Rec.2020）は物理的に決まっていて、範囲外の色は
どうやっても出せない。クリッピング（境界に貼り付け、ディテールが潰れる）か、
知覚的圧縮（全体をなだらかに縮める）かを選ぶ必要があり、その指示がこの1バイト。

### デコーダ実装としてどこまでやるか

**このカリキュラムの範囲外。**

```
img-01〜05 の担当:        バイト列 → ピクセル値 (R=255, G=128, B=0)
カラーマネジメントの担当:  そのピクセル値 → 実際に画面に出す色
```

自作デコーダは「IDAT を展開して RGB 値を取り出す」まででよい。取り出した値を
**どの色空間の値として解釈するか**は完全に別レイヤーで、実用では lcms のような
専用ライブラリに投げる。

img-02 のツールも `gAMA` / `sRGB` を**表示するだけで何も適用していない**。それで正しい。

## Q6: 「サブバイト深度」とは何か。README に説明がない

### 定義

**1ピクセルが1バイト（8bit）に満たないビット深度** — 具体的には深度 **1 / 2 / 4**。

```
深度 16 → 1サンプル 2バイト   ┐ バイト境界に乗る
深度  8 → 1サンプル 1バイト   ┘
深度  4 → 1バイトに 2ピクセル ┐
深度  2 → 1バイトに 4ピクセル ├ サブバイト深度
深度  1 → 1バイトに 8ピクセル ┘
```

該当するのは **カラータイプ 0（グレー）の 1/2/4** と **カラータイプ 3（パレット）の 1/2/4** のみ。
2 / 4 / 6 は 8・16 しか許されないので、そもそもサブバイトにならない。

### なぜ特別扱いが必要か

デコーダの前提「バイト単位で読めばいい」が崩れる唯一のケースだから。
以下4つがすべてサブバイト深度だけの話になる。

| 論点 | 通常（8/16bit） | サブバイト（1/2/4bit） |
|---|---|---|
| ピクセルの取り出し | バイトをそのまま読む | 1バイトからシフト+マスクで複数個取り出す（上位ビット側から） |
| 行の末尾 | ぴったり終わる | 端数ビットは詰め物として捨てる |
| 全体サイズ | `幅×高さ×bpp/8` で合う | 行ごとに切り上げないとずれる |
| フィルタの参照 | 左隣のピクセル = bpp バイト前 | 「1バイト前」固定 |

`filter_bpp = max(1, ceil(bits_per_pixel / 8))` の `max(1, ...)` は、
4番目のためだけに存在している。

### 用語について

PNG 仕様書にこの語はなく、仕様では単に "bit depths less than 8" と書かれる。
本教材内のローカルな呼び名（`main.rs` の `pixels_per_byte()` 周辺も同じ意味で使っている）。

## Q7: `(byte >> shift) & ((1 << depth) - 1)` はどういう操作か

演習1の雛形にある式。サブバイト深度のバイトから1ピクセル分を切り出す定番イディオム。

### 2段階の分解

深度2、`byte = 0b11_01_10_00` から px2 (=`0b10`) を取り出す場合。

```
      px0 px1 px2 px3
byte       =     1 1 0 1  1 0 0 0
byte >> 2  =     0 0 1 1  0 1 1 0     ← px3 は右端から溢れて消えた
mask       = &   0 0 0 0  0 0 1 1     ← (1 << 2) - 1
                 ─────────────────
結果       =     0 0 0 0  0 0 1 0     = 2
```

- `byte >> shift` — 目的のビットを最下位へ寄せる。値として使うには右端に揃っている
  必要があるため必須。同時に**下位側の隣接ピクセルが右端から溢れて消える**
- `(1 << depth) - 1` — 下位 depth ビットだけが1のマスク。`1 << n` は「n桁目だけ1」、
  1を引くと桁借りで「n桁分すべて1」になる（深度4なら `0x0F`）

**シフトは下位側、マスクは上位側**という分担。右シフトでは上位の隣接ピクセルが
残り続けるので、マスクなしでは値が壊れる。

### なぜシフトが先か

逆順でも書けるが、マスク自体を位置合わせする必要があり損をする。

```rust
(byte & (mask << shift)) >> shift   // マスク先行: シフトが2回に増える
(byte >> shift) & mask              // シフト先行: マスクが slot に依存しない定数になる
```

### 「マスクせず上位ビットを切り捨てる」ことはできないのか

**できない。というより、それがマスクそのもの。**

変数の値は常に8ビット全部で決まる。`byte >> 2` の時点でこの u8 は 54 であって
「下位2bitだけ有効」という中間状態は存在しない。よって「切り捨てる」は
「そのビットを0にする」以外の意味を持てず、特定ビットを0にする操作 = AND。

ビットが本当に消える唯一の経路は**型の幅からはみ出すこと**で、それがシフト。
ただし捨てられる境界は型の幅（8/16/32/64）に固定されており、「上位2bitだけ」の
指定はできない。左端まで押し出してから右へ戻す形になる。

```rust
(byte << (depth * slot)) >> (8 - depth)   // マスクを使わない別解（2シフト法）
```

これも正解。x86 ではどちらも2命令（shr+and / shl+shr）に落ちるので速度差はない。
マスク版を採用しているのは `(1 << depth) - 1` に**取り出す幅がそのまま現れて読める**ため。

Rust に `u4` があれば `as u4` で済むが、整数型は 8/16/32/64/128 のみ。
C のビットフィールドも実体はコンパイラが生成する shift + mask。

### 符号付き型での罠

`u8` の `>>` は論理シフト（上位に0）だが、**符号付き型は算術シフト**（符号ビットが伸びる）。

```
i8 の -40 = 0b1101_1000
>> 2   → 0b1111_0110    ← 上位に1が伸びてくる
& 0b11 → 0b0000_0010    ← マスクが吸収する
```

途中で `i32` にキャストしたコードで実際に踏む。Go も同じ（`byte` なら論理、`int` なら算術）。

### この関数の適用範囲

`depth = 8` を渡すと `(1u8 << 8) - 1` がオーバーフローして
デバッグビルドで panic する（Go はシフト量が幅以上なら 0 になるだけ）。

深度 8/16 では 1バイトから複数取り出す必要がそもそもなく `row[index]` を直接読めばよい。
**この関数はサブバイト深度 (1/2/4) 専用**。実装時は冒頭に
`debug_assert!(matches!(depth, 1 | 2 | 4))` を置くと意図が明確になる。
