# img-02: PNG ヘッダ解釈器 (IHDR)

## 概要

img-01 で「入れ物」を切り分けられるようになったので、次は中身の設計図を読む。

IHDR は13バイトしかないが、ここに書かれた **ビット深度** と **カラータイプ** の2つで
「展開後のバイト列がどういう形をしているか」が完全に決まる。逆に言うと、
この2つを読まないと IDAT を展開しても意味のあるデータとして解釈できない。

このトピックのゴールは次の2つの数字を全パターンで出せるようになること。

- **1ピクセルが何ビットか** (`bits_per_pixel`)
- **zlib を展開したら何バイト出てくるか** (`raw_size`)

前者は img-04（フィルタ復元）で、後者は img-03（inflate）の答え合わせで使う。

## 実行

```bash
cargo run -p img-02-png-ihdr                                    # sample-rgb8.png
cargo run -p img-02-png-ihdr -- rust/img-02-png-ihdr/sample-palette4.png
cargo run -p img-02-png-ihdr -- --all                           # 全サンプルを一覧比較
cargo run -p img-02-png-ihdr -- --table                         # 合法な組み合わせ表
```

### サンプル画像

代表的な組み合わせを1枚ずつ用意してある。どれも数十〜200バイトで、`xxd` で全部見える。

| ファイル | 内容 | 狙い |
|---|---|---|
| `sample-rgb8.png` | 8×8 RGB 8bit | 基準。img-01 の `sample.png` と同じ形 |
| `sample-gray1.png` | 12×8 グレー 1bit | 1バイトに8ピクセル。詰め物が出る |
| `sample-palette4.png` | 9×9 パレット 4bit | PLTE + tRNS。1バイトに2ピクセル |
| `sample-rgba16.png` | 4×4 RGBA 16bit | 1ピクセル8バイト。PNG の最大サイズ |
| `sample-interlaced.png` | 8×8 RGB 8bit Adam7 | サイズ計算式が通用しないケース |

## IHDR の13バイト

```
  +--------+--------+------+------+------+------+------+
  | 幅     | 高さ   | 深度 | 色型 | 圧縮 |ﾌｨﾙﾀ |ｲﾝﾀﾚｰｽ|
  | 4 byte | 4 byte | 1    | 1    | 1    | 1    | 1    |
  +--------+--------+------+------+------+------+------+
       0        4      8      9      10     11     12
                       └───┬───┘      └──────┬──────┘
                     ここで全部決まる      現行仕様では全部 0 固定
```

後半の3バイトは実質的に定数。**圧縮方式 0 = deflate**、**フィルタ方式 0 = adaptive** 以外は
仕様に存在せず、25年以上増えていない。インターレースだけが 0 か 1 の2値。

つまり読むべきは実質 **幅・高さ・深度・カラータイプ** の4つ。

## カラータイプ

「色をどう表現するか」の指定。値は5種類で、1 と 5 は欠番。

| 値 | 名前 | チャンネル | 展開後の1ピクセル |
|---|---|---|---|
| 0 | グレースケール | 1 | `[gray]` |
| 2 | トゥルーカラー RGB | 3 | `[R][G][B]` |
| 3 | パレット | 1 | `[index]` |
| 4 | グレー + アルファ | 2 | `[gray][A]` |
| 6 | トゥルーカラー + アルファ RGBA | 4 | `[R][G][B][A]` |

値がビットフラグになっているのが分かりやすい。

```
  bit 0 (1): パレットを使う
  bit 1 (2): カラー（RGB）である
  bit 2 (4): アルファチャンネルがある

  0 = 000 → グレー
  2 = 010 → カラー
  3 = 011 → カラー + パレット
  4 = 100 → グレー + アルファ
  6 = 110 → カラー + アルファ
```

欠番の理由もこれで説明がつく。`1` は「パレットだけどカラーではない」、
`5` は「パレット + アルファ」で、どちらも意味をなさない組み合わせ。

**パレットのチャンネル数が 1 なのが引っかかりやすいポイント。**
パレット画像の展開後データに入っているのは色そのものではなく **パレット番号1個** だけ。
実際の RGB は PLTE チャンクを引いて初めて分かる。

## ビット深度

1チャンネルあたりのビット数。ここが罠で、**カラータイプごとに使える値が違う**。

```
  型  ch  許される深度      1ピクセルのビット数
  --  --  ----------------  --------------------
   0   1  1, 2, 4, 8, 16    1, 2, 4, 8, 16
   2   3  8, 16             24, 48
   3   1  1, 2, 4, 8        1, 2, 4, 8
   4   2  8, 16             16, 32
   6   4  8, 16             32, 64
```

`cargo run -p img-02-png-ihdr -- --table` で同じ表が出る。

制限の理由は次の通り。

- **2 / 4 / 6 が 8・16 に限られる** — 1サンプルを必ずバイト境界に揃えるため。
  RGB を 4bit ずつ持つと1ピクセル12bitになり、実装が跳ね上がる割に得がない
- **3 が 8 止まり** — パレットは最大256色なので、9bit 以上のインデックスは意味がない
- **0 だけが全部使える** — 白黒2値の画像を1bitで持てる。FAX 的な用途がそのまま残っている

デコーダは組み合わせを検証しなければならない。「カラータイプ 2 / 深度 4」のような
存在しない組み合わせを書いた PNG は普通に作れるので、そのまま計算すると壊れた結果が出る。

## 1ピクセルのビット数

```
bits_per_pixel = channels × bit_depth
```

これだけ。`sample-rgba16.png` なら `4 × 16 = 64 bit`（1ピクセル8バイト）で、
これが PNG の最大値。`sample-gray1.png` なら `1 × 1 = 1 bit`。

### サブバイト深度とは

**1ピクセルが1バイト（8bit）に満たないビット深度** — つまり深度 **1 / 2 / 4** のこと。
深度 8・16 は 1サンプルが 1〜2バイトでバイト境界にきれいに乗るが、
サブバイト深度では **1バイトの中に複数ピクセルが詰め込まれる**。

該当するのは上の表のうち **カラータイプ 0 の 1/2/4** と **カラータイプ 3 の 1/2/4** だけ。
2/4/6 は 8/16 しか許されないのでサブバイトにはならない。

デコード時に「バイト単位で読めばいい」が崩れる唯一のケースなので、以降で個別に扱う。
なお PNG 仕様書にこの用語はなく（仕様では単に "bit depths less than 8"）、本教材内の呼び名。

### サブバイト深度の詰め方

1ピクセルが1バイト未満のとき、**上位ビット側から順に**詰める。

```
深度 4、幅 9 の場合（sample-palette4.png）

  px0 px1  px2 px3  px4 px5  px6 px7  px8 ....
  ┌───┬───┬───┬───┬───┬───┬───┬───┬───┬───┐
  │ 4 │ 4 │ 4 │ 4 │ 4 │ 4 │ 4 │ 4 │ 4 │ 0 │  ← 最後の4bitは詰め物
  └───┴───┴───┴───┴───┴───┴───┴───┴───┴───┘
   byte0     byte1     byte2     byte3     byte4
```

重要なのは **行はバイト境界で切り上げられ、次の行へまたいで詰めることはない** という点。
9ピクセル × 4bit = 36bit だが、行としては 5バイト（40bit）を占め、末尾4bitは捨てられる。

これを知らないと「幅×高さ×bpp / 8」で全体サイズを計算してしまい、
サブバイト深度の画像で必ずずれる。

### フィルタ用の bpp

もうひとつ、img-04 で使う値を IHDR から導いておく。

```
filter_bpp = max(1, ceil(bits_per_pixel / 8))
```

フィルタは「左隣のピクセル」を参照するが、1ピクセルが1バイト未満のときは
**1バイト前を見る**と仕様で決まっている。ピクセル単位ではなくバイト単位で動く。

| 画像 | bits_per_pixel | filter_bpp |
|---|---|---|
| グレー 1bit | 1 | 1 |
| パレット 4bit | 4 | 1 |
| RGB 8bit | 24 | 3 |
| RGBA 16bit | 64 | 8 |

## 展開後のサイズ

PNG の中身は「スキャンライン」という単位で並んでいる。

```
  ┌───┬────────────────────────────────┐
  │ f │ ピクセルデータ                   │  ← 1行目
  ├───┼────────────────────────────────┤
  │ f │ ピクセルデータ                   │  ← 2行目
  ├───┼────────────────────────────────┤
  │ f │ ...                            │
  └───┴────────────────────────────────┘
    ↑
    各行の先頭1バイトがフィルタタイプ (0〜4)
```

```
bytes_per_row = 1 + ceil(width × bits_per_pixel / 8)
raw_size      = bytes_per_row × height
```

先頭の `1` を忘れやすい。これは画素ではなく **その行にどのフィルタが掛かっているか** の指定で、
行数分だけ余計に増える。高さ1000の画像なら1000バイトがフィルタタイプに使われている。

`--all` で全サンプルの計算結果を並べられる。

```
  file                   幅×高さ  深度  型  ch  bpp  1行     展開後   詰め物/行
  sample-gray1.png        12×8      1   0   1    1     3 B     24 B      4 bit
  sample-interlaced.png    8×8      8   2   3   24    25 B    200 B      0 bit  ← Adam7
  sample-palette4.png      9×9      4   3   1    4     6 B     54 B      4 bit
  sample-rgb8.png          8×8      8   2   3   24    25 B    200 B      0 bit
  sample-rgba16.png        4×4     16   6   4   64    33 B    132 B      0 bit
```

この「展開後」の数字が img-03 の答え合わせに使える。
自作 inflate の出力バイト数がここと一致しなければ、どこかが間違っている。

### Adam7 だけ式が通用しない

`sample-interlaced.png` は `interlace = 1`。Adam7 は画像を7つのパスに分けて送るため、
**パスごとに独立したスキャンライン群**を持つ。つまりフィルタタイプの1バイトもパスの行数だけ付く。

同じ 8×8 RGB 8bit でも、非インターレースなら 200 バイト、Adam7 なら 207 バイトになる。
インターレースは「先に粗い絵を出す」ための仕組みで、サイズ的にはむしろ太る。
計算方法は演習3で扱う。

## 展開爆弾への防御

IHDR の幅・高さは **他人が書いた数値**。ここから導く `raw_size` は展開前に計算できるので、
「展開してみたら 17GB だった」を避けられる。

```
幅 65535 × 高さ 65535 × RGBA 8bit
  → 65535 × (1 + 65535 × 4) = 約 17.2 GB
```

全ピクセルが同じ色ならこれが数KBの IDAT に収まる。デコーダが素直に展開すると
メモリを食い尽くして落ちる（DoS）。ZIP 爆弾の画像版で、**展開する前に IHDR だけ読んで弾く**のが定石。

`main.rs` では `RAW_SIZE_WARN`（256 MiB）を超えたら警告を出している。
実用デコーダも同種の上限を持っていて、たとえばブラウザは
「幅・高さの上限」「総ピクセル数の上限」の両方を持つのが普通。

## 補助チャンク

IHDR を読んだ後でないと解釈できないチャンクがある。

| 型 | 中身 | IHDR への依存 |
|---|---|---|
| `PLTE` | パレット（3バイト×N） | カラータイプ3なら必須、0/4なら禁止。エントリ数 ≤ 2^深度 |
| `tRNS` | 透過情報 | **カラータイプで中身の意味が変わる** |
| `gAMA` | ガンマ値（u32 / 100000） | なし |
| `sRGB` | 色空間とレンダリング意図 | なし |
| `pHYs` | 物理解像度（px/m） | なし |

`tRNS` が分かりやすい例で、同じ型なのに解釈がまったく違う。

| カラータイプ | tRNS の中身 |
|---|---|
| 0 グレー | 2バイト。この輝度値を透明として扱う |
| 2 RGB | 6バイト。この RGB 値を透明として扱う |
| 3 パレット | Nバイト。パレット各エントリのアルファ値 |
| 4 / 6 | **禁止**（すでにアルファチャンネルがある） |

「IHDR を最初に読む」がなぜ仕様で強制されているかがここに出ている。
チャンクの順序が自由だったら、`tRNS` を読む時点で解釈方法が分からない。

## Go との比較

### 定数か enum か

```go
// Go: 名前付き定数。型は付くが値域は縛れない
type ColorType uint8

const (
    Grayscale      ColorType = 0
    TrueColor      ColorType = 2
    Paletted       ColorType = 3
    GrayscaleAlpha ColorType = 4
    TrueColorAlpha ColorType = 6
)

func (c ColorType) Channels() int {
    switch c {
    case Grayscale, Paletted:
        return 1
    // ...
    }
    return 0  // ← 「ありえない」ケースにも何か返さないとコンパイルが通らない
}
```

```rust
// Rust: enum は「この5つ以外は存在しない」を型で保証する
enum ColorType {
    Grayscale,
    Rgb,
    Palette,
    GrayscaleAlpha,
    Rgba,
}

fn channels(self) -> u32 {
    match self {
        Self::Grayscale | Self::Palette => 1,
        Self::Rgb => 3,
        Self::GrayscaleAlpha => 2,
        Self::Rgba => 4,
    }  // ← default 不要。列挙子を足すと match がコンパイルエラーになる
}
```

Go では `ColorType(7)` が普通に作れてしまうので、`default: return 0` のような
「起きないはずの分岐」を書く羽目になる。Rust は `from_u8() -> Option<ColorType>` の
一箇所だけで検証を済ませ、それ以降は不正な値が存在しないことを型で保証する。

これは**バイナリパーサとの相性が特に良い**。外から来た値を最初に一度だけ検証し、
以降は検証済みの型で扱う、という構造がそのまま書ける。

### 整数オーバーフロー

```go
// Go: オーバーフローは黙って回り込む（wrap around）
rowBits := width * uint32(bitsPerPixel)   // width が大きいと静かに壊れる
```

```rust
// Rust: debug ビルドならパニックで止まるが、それでは実用にならない。
// 最初から u64 に広げるのが正解
let row_bits = u64::from(ihdr.width) * u64::from(bits_per_pixel);
```

幅の上限は 2^31-1 なので、`width × 64bit` は u32 を確実に超える。
「攻撃者が選べる数値どうしの掛け算」は型を広げてから、が鉄則。

Rust は release ビルドだと Go と同じく wrap するので、
「debug で気づける」以上の保証はない。結局これは言語の問題ではなく設計の問題。

### スライスと配列の変換

```go
w := binary.BigEndian.Uint32(data[0:4])
```

```rust
let w = u32::from_be_bytes([data[0], data[1], data[2], data[3]]);
// もしくは
let w = u32::from_be_bytes(data[0..4].try_into().unwrap());
```

img-01 と同じ話。`encoding/binary` に相当するものが std にない。

## 演習

`src/main.rs` の末尾にコメントで雛形が入っている。

### 演習1（基礎）: サブバイト深度からピクセルを取り出す

深度 1/2/4 の行バイト列から「n番目のピクセル値」を取り出す関数を書く。
上位ビット側から詰まっている点と、行末の詰め物を読まないことに注意。

### 演習2（応用）: パレットを解決する

`sample-palette4.png` の PLTE と tRNS を読み、インデックス → RGBA に変換する。
「1ピクセル4bit の画像が、展開すると32bitになる」＝ 展開後サイズとメモリ上のサイズは別物、
という感覚を掴む。

### 演習3（チャレンジ）: Adam7 の展開後サイズを計算する

7パスそれぞれの幅・高さを求めて合計する。
`sample-interlaced.png` (8×8 RGB 8bit) で **207 バイト** になれば正解。
非インターレース版の 200 バイトと比べて「なぜ増えるのか」を説明できるようにする。
